Icarus: a virtual run platform

Web · Full-stack project · 2021

Next.jsExpressStrava APIAWS

Why it exists

Race platforms asked for a large minimum number of participants. That shut out smaller communities that wanted to run their own event. Icarus lets any community create a virtual run, walk or ride and invite people to join.

How an event works

A community asks us for an event. We set it up from one of our event templates, so each event can have its own format: running only or multisport, with its own scoring rules for how the winners are decided. Each event also has a distance, a date and a price. We review and approve every event before it goes live.

Participants sign up, join the event and connect their Strava account. After that they do not upload anything. When someone saves a run or a ride on Strava, Strava calls our webhook, and the API fetches the activity and counts it toward the event.

How it is built

In a small team, I worked on the full stack and the cloud architecture. The web app is Next.js, and the API is a separate Express service on Node.js. Because they are separate, we can deploy each one on its own. Both run on AWS EC2. Firebase Authentication handles sign-in. The Strava webhook is the core of the system, because it turns each participant’s normal training into event progress without any manual step.

Results

Real communities ran their events on it, and we served several clients, including Pharmarun 2022 and the IAE Virtual Run series. It grew to more than 3,000 registered users across 10 events. In a single event month, more than 500 participants logged their activities.

Learning Image Similarities on Clothing Images

Data science · KTH DD2430 course project · 2019

Deep learningComputer visionSiamese networksMetric learning

The task

A webshop shows “similar items” next to a product. This project taught a neural network what similar clothes means, so a photo can be matched to visually similar items. The model maps each image to a point in an embedding space, and the items closest to the query are ranked as the most similar. We compared two Siamese ranking networks, RankNet and a simplified Deep Ranking network. A Siamese network passes several images through the same weights, so their embeddings can be compared.

How it works

Training uses triplets: a query image, an item that matches it and one that does not. All three go through the same embedding network. The loss pulls the match closer to the query than the non-match. Inside the network, three paths look at the image at different levels. A VGG network pretrained on ImageNet captures what the item is. Two shallow convolutional networks capture simpler appearance. The three paths are merged into one embedding.

RankNet uses VGG19 and a contrastive loss. The Deep Ranking network uses VGG16 and a hinge loss. We simplified it from the original design with three VGG16 networks, because that one had too many parameters to train. For search, every catalogue image is embedded once, and Annoy, an approximate nearest-neighbour index, returns the items closest to the query.

Data

We used Street2Shop, which pairs street photos with the same product in an online shop. Its product IDs say which items are the same, so we did not need to label anything by hand. I wrote a downloader for it, because the dataset was published as image URLs. We used four classes: tops, dresses, skirts and pants. Early models mostly matched backgrounds, people and text instead of the clothes. Cropping each image to the garment with the dataset’s bounding boxes fixed that.

What we found

After cropping, colour still mattered more than style. RankNet did better than the Deep Ranking network, both by eye and on our rank measure: the position of the first result with the same product ID, on 10 validation queries. The two models differ in both the loss and the depth, so the result does not show which change helped. The next step in the report was to train both with the same loss.

A live chart of trending artists

Systems · Student team project · 2019

KafkaSpark StreamingCassandraDash

What it does

A classmate and I wanted to see which artists people were sharing on Twitter at that moment. The pipeline reads the live Twitter stream, keeps the tweets that carry a Spotify link, and counts the shares per artist. A chart shows the top 20 artists of the last 60 minutes and redraws every five seconds.

The pipeline

Each part has one job. A Tweepy listener keeps only tweets with a Spotify link and sends the time and the link to Kafka as a small message. Kafka sits between the Twitter stream and the processing, so the listener can keep reading while Spark catches up. A Spark Streaming job reads the topic, asks the Spotify Web API for the artist of each track and counts the shares per artist. Cassandra stores the counts as time-stamped rows, which fits a stream that writes all the time and is read by time. A Dash app adds up the last hour every five seconds and redraws the chart. The demo ran on one laptop with one copy of every component.

What I found when I reread it

Years later I reread the code and found two failures that the demo never showed. First, the consumer did not save its offsets, so after a crash it read the whole topic again. Second, the rows were keyed by artist and second, so two shares in the same second could overwrite each other. The write-up goes through both and how I would fix them.

Comparing tweet sentiment classifiers

Data science · KTH DM2583 course team project · 2019

Pythonscikit-learnKerasNLP

The task

The task was to label each tweet as positive or negative. With two classmates I compared four approaches on the same cleaned data. The baseline was TextBlob, a lexicon that scores the polarity of each word. The other three were Multinomial Naive Bayes, a linear SVM and a small CNN in Keras.

Data and cleaning

We used two public datasets. The main one was Sentiment140, with 1.6 million tweets. For contrast we also used Amazon product reviews, which are longer. Cleaning became its own experiment, because the text representation mattered as much as the classifier. We removed usernames, URLs and noise, expanded contractions, corrected spelling, removed stopwords and lemmatized with NLTK. Trigram TF-IDF features did better than plain word counts. The cleaned datasets are on Kaggle.

What the numbers said

The linear SVM did best, with 82% accuracy on the Twitter test set. The CNN reached 77.7% accuracy, but it was overfitting, so the comparison is weaker than it looks. The review goes through what I would change. On the Amazon reviews the same pipeline scored above 90%, which says more about longer texts than about the models.

Adding colour to grayscale images

Data science · KTH DD2424 course team project · 2019

TensorFlowKerasInception-ResNet-v2

What it does

The network takes a grayscale photo and predicts its colours. Our team of three reimplemented the approach of Iizuka et al. (2016) and Baldassarre et al. (2017) in TensorFlow and Keras, with some changes.

The network

It has four parts, as in the papers. An encoder takes mid-level features from the grayscale input. A pretrained Inception-ResNet-v2 gives high-level features about the whole scene. A fusion layer adds those scene features to the middle of the network. Then a decoder predicts the a* and b* channels of the Lab colour space. These are combined with the lightness of the input to give the colour image.

How far it got

First we trained the network on one image on purpose until it overfit. If it can recover a single training image, the wiring is correct. Then we trained on a small part of ImageNet, limited to 2,000 images by the project time. When we scaled up with precomputed features stored in TFRecords, the model produced brownish images. We suspected a bug in our TFRecords code but did not confirm the cause. The smaller model coloured grass and sky better than clothing. The repository has the training notebooks, the architecture figure, example outputs and the full report. The goal was to reproduce the papers at a small scale.

Downloading the Street2Shop dataset

Data science · Personal project · 2019

PythonHugging Face datasetsPillow

The problem

Street2Shop pairs photos of people wearing clothes with the same product in an online shop. It has eleven clothing categories and comes from an ICCV 2015 paper. The dataset was published as lists of image URLs plus JSON metadata. The metadata has the train and test pairs, the links from photos to products, and the bounding box of the worn item in each street photo. So to use it, you had to download every image yourself.

The tool

In 2019 I wrote a small Python command-line tool for that, for the clothing similarity project. It read the URL lists and metadata, downloaded the images per category with threads, and could crop street photos to their bounding boxes.

Since then the original hosts and many image URLs have gone offline. The exporter reads a community copy of the dataset on Hugging Face. It keeps the old folder layout and options, so code written for the 2015 files still works. Running an export again skips images already on disk, so an interrupted run can continue.

Limits

The Hugging Face copy is not an official release, and it lacks the original retrieval gallery of about 205k products. Spot checks against the archived original metadata matched.

Bookio: a community bookshelf

Web · KTH Interaction Programming course team project · 2019

ReactReduxFirebaseAlgoliaGoogle Maps

What it does

People post books they want to lend or give away, with a pick-up time and place. Others browse a searchable shelf and request a book. Then they meet at the pick-up point, and the exchange stays in both accounts’ history. Everyone needs an account, so people know who they are meeting. When someone adds a book, the Goodreads API fills in the author and the rating.

How it works

We wanted a serverless app, so Firebase is the whole backend. Authentication handles sign-in with a verified email or Facebook. Cloud Firestore holds the books and requests, and Storage keeps the cover photos. Firestore pushes every change to all open apps, so a new book or a new request shows up for other users in real time. Firestore has no full-text search, so Algolia keeps a synced index of the books for search and type filters. Google Maps shows the pick-up locations.

My part

We built it as a team for the Interaction Programming and Dynamic Web course at KTH. I proposed the core idea, worked across the full stack, built the accounts and designed the UI and UX.

Treki, a Bluetooth tracker for belongings

Mobile · Bootcamp final project · Hacktiv8 batch 16 · 2018

React NativeNode.jsBluetooth Low Energy

What it does

You attach a small Bluetooth Low Energy (BLE) device to something you do not want to lose, like your keys or wallet, and register it in the app. When the item is close, the near-finder screen reads the device’s signal strength (RSSI) and tells you whether you are getting closer. You can also add photos and mark an item as lost.

How it works

The Treki device only broadcasts its ID and signal strength. Any phone with the app that comes near it, yours or another user’s, sends the device ID and the phone’s location to the Treki server. The server stores the update in Firebase and sends a push notification to the owner. So a lost item gets its last-known location from other users’ phones, because the device itself has no internet connection.

The app is React Native, and a thin Node.js API with Firebase holds the users, devices and sightings.

The hard part

Crowd-sourced location only works if phones keep scanning for devices while the app is in the background. Keeping Bluetooth on in the background was the hardest part. Making it power efficient needs work on the hardware side too, not only in the app.

My role and the result

I proposed the idea, led the team of four and was the main developer. Treki won the best presentation award at the end of the bootcamp, and I received the Teacher’s Award for the best student.

Caprica: a connected-helmet safety system

Hardware · Hackathon project · 2017

React NativeBluetooth serialGoogle Maps

What it does

A device on a motorcycle helmet watches for two things: an accident, and the rider going faster than the maximum speed. When either happens, the rider’s phone shows an alert. After an accident, the app also sends the rider, time and location to a monitoring dashboard, which shows recent accidents on Google Maps.

How it works

The system has three parts: the helmet device, the rider app and the dashboard. The device is an ESP32 board with motion sensors and a GPS module. It pairs with the rider’s phone over Bluetooth serial. The React Native app shows the alerts and forwards accident reports to the cloud. The dashboard reads those reports and puts them on a map. So the app on the phone stays thin, and the monitoring happens in the dashboard.

Detecting an accident

The device measures speed, acceleration and location. Speeding is the simple check: the speed goes above the set maximum. For an accident, the device looks for two signals. The first is acceleration over a threshold, which means a hard impact. The second is an abrupt change in deceleration, which is what a fall looks like.

The team and the result

We built it in two days as the SSX_Ceria team at a Gojek hackathon, and it won 2nd place. I built the IoT device, and my teammates built the React Native client and the dashboard.
