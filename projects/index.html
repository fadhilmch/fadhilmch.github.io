Icarus: a virtual run platform

Web · Full-stack project · 2021

Next.jsExpressNode.js

Why it exists

Race platforms asked for a large minimum number of participants. That shut out smaller communities that wanted to run their own event. Icarus lets any community create a virtual run, walk or ride and invite people to join.

Results

Real communities ran their events on it, and we served several clients. It grew to more than 3,000 registered users across 10 events. In a single event month, more than 500 participants logged their activities.

How it is built

In a small team, I worked on the full stack and the cloud architecture. A Next.js front end talks to a separate Express API on Node.js. In development, Next rewrites /apps/* to the local API on port 8000, so the web app and the API can be deployed separately. The front end uses Chakra UI and Material-UI components, forms use react-hook-form with yup validation, and sign-in uses Firebase Authentication. Each event has a distance, a date and a price. Events included Pharmarun 2022 and the IAE Virtual Run series.

Learning Image Similarities on Clothing Images

Data science · KTH DD2430 course project · 2019

Deep learningComputer visionSiamese networksMetric learning

The task

Learn what “similar clothes” means, so that a query photo can be matched to visually similar items, the kind of feature a webshop uses for “similar items”. The model maps each image to a point in an embedding space, and the images closest to the query are ranked as the most similar. The project compared two Siamese ranking networks, RankNet and a simplified Deep Ranking network.

Architecture

Each image in a triplet (the query, a matching item and a non-matching item) is passed through the embedding network. Inside that network, both models run the image through three parallel paths that are merged at the end.

In RankNet the paths are a VGG19 pretrained on ImageNet, which captures semantics, and two shallow convolutional networks that capture simpler visual appearance. Each of the shallow networks has one convolutional layer and two pooling layers. Each path is L2-normalised, the three are merged in a final embedding layer of 4096 dimensions, and that layer is normalised too. Dropout is applied to the VGG19 path. RankNet trains with a contrastive loss and a momentum optimizer.

The Deep Ranking network is a simplified version of the original design. It uses one VGG16 and two small convolutional networks, because the three-VGG16 version had too many parameters to train, and it trains with a hinge loss.

Data and triplet sampling

Both networks learn from triplets: a query image, an item that matches it and one that does not. Street2Shop was used because its product IDs define which items are the same, which avoided hand-labelling. Fashion-MNIST and DeepFashion were considered and rejected. The triplet sampler pairs every query with its positives, and each pair gets one in-class negative and one out-of-class negative. The data came from four classes: tops, dresses, skirts and pants. Early models mostly matched backgrounds, people and text, so the images were cropped to the garment with the dataset’s bounding boxes.

Training and evaluation

The data was about 170,000 training and 30,000 validation triplets. The RankNet run used 20,898 training and 6,718 validation triplets for 25 epochs, about 10 hours, and ended at a validation loss of 0.1594. For retrieval, the images are embedded and ranked with Annoy approximate nearest neighbours. The quantitative measure is the rank of the first image with the same product ID as the query, on 10 sampled validation queries. A second check on 10 validation triplets had the positive closer than the negative in 9 of them.

What the research found

After cropping, colour still dominated style. Grayscale was mixed, and helped somewhat with more data. RankNet gave better results than the Deep Ranking model, both by eye and on the rank measure. Some of the 10 queries had no rank and some ranks were large, so the result is mixed, and it is an indication, not a broad benchmark. The loss and the network depth differ between the two models, so their effects are not separated, and the report suggests an ablation study. Named future work is t-SNE visualisation of the embedding space and using the same loss for both architectures.

A live chart of trending artists

Systems · Student team project · 2019

KafkaSpark StreamingCassandraDash

What it does

A classmate and I wanted to see which artists people were sharing on Twitter at that moment. The pipeline reads the live Twitter stream, keeps the tweets that carry a Spotify link, and counts the shares per artist. A chart shows the top 20 artists of the last 60 minutes and redraws every five seconds.

The pipeline

A Tweepy listener filters the stream in two steps. The Twitter API filter keeps tweets that match the keyword “spotify com”. A JSON check then keeps only tweets with a URL and saves just the timestamp and the expanded link. Each record goes to a Kafka topic as a small JSON message.

A PySpark consumer reads that topic. It uses the receiver-less (direct) approach, so it asks Kafka for the latest offsets itself instead of running a separate receiver. For each record it takes the track id from the URL and asks the Spotify Web API for the artist. Records with no match are dropped. The counts go to Cassandra as (artist, timestamp, count) rows. A Dash app queries the table every five seconds, adds up the last hour and redraws the chart.

What I found when I reread it

Years later I reread the code and found two failures that the demo never showed. First, the consumer did not save its offsets, so after a crash it read the whole topic again. Second, the rows were keyed by artist and second, so two shares in the same second could overwrite each other. The write-up goes through both. The demo ran on one laptop with one copy of every component. It worked, but it was not a production system.

Comparing tweet sentiment classifiers

Data science · KTH DM2583 course team project · 2019

Pythonscikit-learnKerasNLP

The task

The task was to label each tweet as positive or negative. With two classmates I compared four approaches on the same cleaned data. The baseline was TextBlob, a lexicon that scores the polarity of each word. The other three were Multinomial Naive Bayes, a linear SVM and a small CNN in Keras.

Data and cleaning

We used two public datasets. The main one was Sentiment140, with 1.6 million tweets. For contrast we also used Amazon product reviews, which are longer. Cleaning became its own experiment, because the text representation mattered as much as the classifier. We removed usernames, URLs and noise, expanded contractions, corrected spelling, removed stopwords and lemmatized with NLTK. Trigram TF-IDF features did better than plain word counts. The cleaned datasets are on Kaggle.

What the numbers said

The linear SVM did best, with 82% accuracy and 86% AUC on the Twitter test set. The CNN reached 77.7% accuracy. However, the comparison is weaker than it looks. Removing the standard stopword list also removed “not”. The CNN was overfitting, so it was not a fair test of a CNN against an SVM. AUC was reported differently across models, and some experiments in the report were never run. The review goes through each of these. On the Amazon reviews the same pipeline scored above 90%, which says more about longer texts than about the models. These are course results from 2019, not a benchmark.

Adding colour to grayscale images

Data science · KTH DD2424 course team project · 2019

TensorFlowKerasInception-ResNet-v2

What it does

The network takes a grayscale photo and predicts its colours. Our team of three reimplemented the approach of Iizuka et al. (2016) and Baldassarre et al. (2017) in TensorFlow and Keras, with some changes.

The network

It has four parts, as in the papers. An encoder takes mid-level features from the grayscale input. A pretrained Inception-ResNet-v2 gives high-level features about the whole scene. A fusion layer adds those scene features to the middle of the network. Then a decoder predicts the a* and b* channels of the Lab colour space. These are combined with the lightness of the input to give the colour image.

How far it got

First we trained the network on one image on purpose until it overfit. If it can recover a single training image, the wiring is correct. Then we trained on a small part of ImageNet, limited to 2,000 images by the project time. When we scaled up with precomputed features stored in TFRecords, the model produced brownish images. We suspected a bug in our TFRecords code but did not confirm the cause. The smaller model coloured grass and sky better than clothing. The repository has the training notebooks, the architecture figure, example outputs and the full report. It is a small reproduction, and it does not show an improvement over a baseline.

Downloading the Street2Shop dataset

Data science · Personal project · 2019, rebuilt 2026

PythonHugging Face datasetsPillow

The problem

Street2Shop pairs photos of people wearing clothes with the same product in an online shop. It has eleven clothing categories and comes from an ICCV 2015 paper. The dataset was published as lists of image URLs plus JSON metadata. The metadata has the train and test pairs, the links from photos to products, and the bounding box of the worn item in each street photo. So to use it, you had to download every image yourself.

The tool

In 2019 I wrote a small Python command-line tool for that. It read the URL lists and metadata, downloaded the images per category with threads, and could crop street photos to their bounding boxes.

Since then the original hosts and many image URLs have gone offline. In 2026 I rebuilt the exporter on a community copy of the dataset on Hugging Face. It keeps the old folder layout and options, so code written for the 2015 files still works. Running an export again skips images already on disk, so an interrupted run can continue.

Limits

The Hugging Face copy is not an official release. Spot checks against the archived original metadata matched, but that is a sample, not a full check. The copy also lacks the original retrieval gallery of about 205k products. The unit tests pass, but I have only run a live export on a few pairs because of Hugging Face rate limits.

Bookio: a community bookshelf

Web · KTH Interaction Programming course team project · 2019

ReactReduxFirebaseAlgoliaGoogle Maps

What it does

People post books they want to lend or give away, with a pick-up time and place. Others browse a searchable shelf and request a book. Everyone needs an account, so people know who they are meeting. When someone adds a book, the Goodreads API fills in the author and the rating.

How it fits together

We built it as a team for the Interaction Programming and Dynamic Web course at KTH. I proposed the core idea, worked across the full stack, built the accounts and designed the UI and UX. The front end is Create React App with Redux, styled in SCSS. Firebase is the whole backend: Authentication for sign-in with a verified email or Facebook, Cloud Firestore for books and requests, and Storage for cover photos. Algolia syncs with Firestore, so full-text search and type filters stay fast. Google Maps shows the pick-up locations. The app has pages for sign-in, the shelf, book details, adding a book, requests and history, and the account.

Treki, a Bluetooth tracker for belongings

Mobile · Bootcamp final project · Hacktiv8 batch 16 · 2018

React NativeNode.jsBluetooth Low Energy

What it does

You attach a small Bluetooth Low Energy (BLE) device to something you do not want to lose, like your keys or wallet, and register it in the app. When the item is close, the near-finder screen reads the device’s signal strength (RSSI) and tells you whether you are getting closer. You can also add photos and mark an item as lost.

How it works

The Treki device only broadcasts its ID and signal strength. Any phone with the app that comes near it, yours or another user’s, sends the device ID and the phone’s location to the Treki server. The server stores the update in Firebase and sends a push notification to the owner. So a lost item gets its last-known location from other users’ phones, because the device itself has no internet connection.

The app is React Native. It talks to the device with react-native-ble-plx, uses Redux with thunks for state and NativeBase for the UI. A thin Node.js API and Firebase hold the users, devices and sightings.

The hard part

Crowd-sourced location only works if phones keep scanning for devices while the app is in the background. Keeping Bluetooth on in the background was the hardest part. Making it power efficient needs work on the hardware side too, not only in the app.

My role and the result

I proposed the idea, led the team of four and was the main developer. Treki won the best presentation award at the end of the bootcamp, and I received the Teacher’s Award for the best student.

Caprica: a connected-helmet safety system

Hardware · Hackathon project · 2017

React NativeBluetooth serialGoogle Maps

What it does

A device on a motorcycle helmet watches for two things: an accident, and the rider going faster than the maximum speed. When either happens, the rider’s phone shows an alert. After an accident, the app also sends the rider, time and location to a monitoring dashboard, which shows recent accidents on Google Maps.

The device

My part was the IoT side. The device is an ESP32 board with motion sensors and a GPS module. It measures speed and acceleration, detects accidents and tracks the location. It pairs with the rider’s phone over Bluetooth serial, and the phone sends the data on to the cloud.

The two-day build

We built it as the SSX_Ceria team at a Gojek hackathon, and it won 2nd place. Besides the device, my teammates built a React Native client and a separate dashboard. The client uses a patched copy of the react-native-android-btserial module, which the repository ships in lib/ to replace the one in node_modules/. The app stays thin: it receives events, shows them and forwards accident reports. Monitoring lives in the dashboard, not on the phone.

Every commit in both repositories is from 25 and 26 March 2017. It was a two-day prototype, and nobody maintained it after the hackathon.
