Systems · Student team project · 2019

A live chart of trending artists

KafkaSpark StreamingCassandraDash

What it does

Watches the live Twitter stream for tweets carrying Spotify links, counts each track share by artist, and keeps a rolling top-20 chart current. The chart re-renders every five seconds and covers the last 60 minutes.

The pipeline

A Tweepy listener filters the stream twice: the API-side keyword “spotify com” so tweets carry a Spotify link, then a JSON check that keeps only tweets with a URL, extracting just the timestamp and the expanded link. Those records land on a Kafka topic as small JSON messages. A PySpark consumer reads the topic receiver-less, querying Kafka directly for the latest offsets, pulls the track id out of each URL, and resolves it to an artist through the Spotify Web API - records with no match are dropped. Counts are written to Cassandra as (artist, timestamp, count) rows. A Dash app re-queries the table every five seconds, aggregates the trailing hour, and redraws the chart.

What rereading it years later exposed

Two quiet failures: the consumer never saved its restart offsets, so any crash replayed the whole topic, and the Cassandra rows could collide on a shared primary key, so one artist’s update could overwrite another’s. Both are written up in detail - the write-up walks through what the original README never said. It was a working team demo, not a production system - and the write-up shows why the difference mattered.

Data science · KTH DM2583 course team project · 2019

Comparing tweet sentiment classifiers

Pythonscikit-learnKerasNLP

The task

Label a tweet’s polarity. With two classmates I compared four approaches on the same cleaned data: a TextBlob lexicon baseline that scores word-by-word polarity, Multinomial Naive Bayes, a linear-kernel SVM, and a small CNN built in Keras.

Data and cleaning

Two public datasets: 1.6 million tweets from Sentiment140 and, for contrast, Amazon product reviews with longer, richer text. Cleaning was its own experiment because the representation mattered as much as the classifier - stripping usernames, URLs and noise, mapping contractions, correcting spelling, removing stopwords, and lemmatizing with NLTK. Trigram TF-IDF features beat a plain count vectorizer. The cleaned datasets are published on Kaggle.

What the numbers said, and what they did not

The linear SVM came out best: 82% accuracy, 86% AUC. The CNN reached 0.777 on the held-out set. But stopword removal had dropped words like “not”, the CNN was overfitting, AUC reporting was inconsistent across models, and some described experiments were never actually run - the linked review documents all of it. The same pipeline scored above 90% on the Amazon reviews, which says more about longer texts than about the models. These are historical course-project results, not a benchmark claim.

Data science · KTH DD2424 course team project · 2019

Adding colour to grayscale images

TensorFlowKerasInception-ResNet-v2

What it does

Takes a grayscale photo and predicts its color channels. A reproduction of the approach from Iizuka et al. (2016) and Baldassarre et al. (2017), with modifications, built in TensorFlow and Keras.

The network

Four components, as in the source papers. An encoder extracts mid-level features from the grayscale input while a pretrained Inception-ResNet-v2 supplies high-level scene features; a fusion step injects those into the middle of the network, and a decoder predicts the a* and b* channels of the Lab colour space, which recombine with the input’s luminance into the final image.

How far it got

First the network was overfit on one image on purpose - recovering a single training image proved the wiring. Then a small ImageNet run: training capped at 2,000 images, a TFRecords bug corrupted many of them, and results came out brownish. Grass and sky colorize better than clothing. The repository carries the training notebooks, the architecture figure, example outputs and a full written report. A small reproduction with honest limits.

Data science · Personal project · 2019

Downloading the Street2Shop dataset

PythonOpenCVHugging Face datasets

The problem it solves

Street2Shop pairs photos of people wearing clothing with the same product in online shops - eleven clothing categories, published with an ICCV 2015 paper. The dataset ships as lists of image URLs plus JSON metadata: train/test splits, shop-product links, and the bounding box of the worn item in each street photo. Many of those URLs are now dead, and nothing downloads or crops the images for you.

The tool

A small Python CLI. It reads the original URL lists and metadata, downloads the images per category with threads, crops street photos to their labeled bounding boxes with OpenCV, and writes the same on-disk layout as the original release so existing pipelines keep running unchanged.

Web · KTH Interaction Programming course team project · 2019

Bookio: a community bookshelf

ReactReduxFirebaseAlgoliaGoogle Maps

What it does

Users post books to lend or give away with pickup time and location, then browse a searchable shelf and request a book. Accounts are required so people know who they are meeting; book details come from the Goodreads API, including ratings.

How it fits together

A Create React App and Redux front end styled in SCSS. Firebase is the whole backend: Authentication (verified email or Facebook sign-in), Cloud Firestore for the books and requests, and Storage for cover photos. Algolia syncs with Firestore so full-text search and type filters stay fast, Google Maps handles pickup locations, and the Goodreads API fills in author and ratings when a book is added. The app ships the full page set: sign-in, shelf overview, book detail, add-book, requests and history, and account management.

Hardware · Hackathon project · 2017

Caprica: a connected-helmet safety system

React NativeBluetooth serialGoogle Maps

What it does

A hardware module mounted on a motorcycle helmet - built by the teammate’s team - streams data to the rider’s Android app, which alerts the rider and, after an incident, reports the accident with rider, time and location to a public dashboard. The dashboard plots recent accidents on Google Maps. I built the React Native client and the dashboard.

The two-day build

Three pieces that had to fit together: the helmet module, a React Native client, and a separate dashboard repository. The client talks to the helmet over Bluetooth serial through a custom-patched react-native-android-btserial module carried in the repo - the stock library could not do what the module needed - while the rider’s app stays a thin client that receives events, shows them, and forwards accident reports. My part of the stack worked end-to-end by demo time.

Every commit in the client repository falls on March 25-26, 2017 - it was a hackathon sprint, not a maintained product, and it shipped enough for the judges to see the full loop.

Mobile · Bootcamp final project · Hacktiv8 batch 16 · 2018

Treki, a Bluetooth tracker for belongings

React NativeNode.jsBluetooth Low Energy

What it does

You register your BLE tracking tags in the app. Each tag scans for other Treki tags nearby and reports what it sees, so the crowd of tags keeps every tagged item’s last-known position fresh. You can attach photos, mark an item lost, and get the latest crowd-reported sighting back. The near-finder screen pings the tag’s current RSSI - the Bluetooth signal strength - and nudges you warmer or colder as you move.

How we split it

Two applications that only talk over the air. The tag runs its own scanning firmware, and the client app never touches tag internals - it pairs over BLE with react-native-ble-plx, shows the tag’s reported sightings, and keeps scanning in the background so your own phone contributes crowd updates. Redux with thunks drives state, NativeBase supplies the UI kit, tag photos are picked from the camera roll and uploaded, and Firebase plus a thin Node.js API hold the user, device and sighting records.

That boundary is what made the demo credible: the phone and the tag behaved like two products that happened to work together.

Web · Full-stack project · 2021

Icarus: a virtual run platform

Next.jsExpressNode.js

Why it exists

A one-stop page for events by Indonesian student organizations around Europe, so members could find concerts, cultural days and meetups without digging through scattered Facebook groups.

Under the hood

A Next.js front end and a separate Express API on Node.js. In development, Next rewrites /apps/* to the local API on port 8000, so the two deploy and evolve independently. The front end mixes Chakra UI and Material-UI components, forms run on react-hook-form with yup validation, and sign-in is Firebase. Events carry distance, date and price - the homepage listed twelve events across 2021-2022, mostly free.
