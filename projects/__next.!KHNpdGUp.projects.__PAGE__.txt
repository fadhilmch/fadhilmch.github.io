Learn what "similar clothes" means, so that a query photo can be matched to visually similar items, the kind of feature a webshop uses for "similar items". The model maps each image to a point in an embedding space, and the images closest to the query are ranked as the most similar. The project compared two Siamese ranking networks, RankNet and a simplified Deep Ranking network.

## Architecture

Each image in a triplet (the query, a matching item and a non-matching item) is passed through the embedding network. Inside that network, both models run the image through three parallel paths that are merged at the end.

In RankNet the paths are a VGG19 pretrained on ImageNet, which captures semantics, and two shallow convolutional networks that capture simpler visual appearance. Each of the shallow networks has one convolutional layer and two pooling layers. Each path is L2-normalised, the three are merged in a final embedding layer of 4096 dimensions, and that layer is normalised too. Dropout is applied to the VGG19 path. RankNet trains with a contrastive loss and a momentum optimizer.

The Deep Ranking network is a simplified version of the original design. It uses one VGG16 and two small convolutional networks, because the three-VGG16 version had too many parameters to train, and it trains with a hinge loss.

## Data and triplet sampling

Both networks learn from triplets: a query image, an item that matches it and one that does not. Street2Shop was used because its product IDs define which items are the same, which avoided hand-labelling. Fashion-MNIST and DeepFashion were considered and rejected. The triplet sampler pairs every query with its positives, and each pair gets one in-class negative and one out-of-class negative. The data came from four classes: tops, dresses, skirts and pants. Early models mostly matched backgrounds, people and text, so the images were cropped to the garment with the dataset's bounding boxes.

## Training and evaluation

The data was about 170,000 training and 30,000 validation triplets. The RankNet run used 20,898 training and 6,718 validation triplets for 25 epochs, about 10 hours, and ended at a validation loss of 0.1594. For retrieval, the images are embedded and ranked with Annoy approximate nearest neighbours. The quantitative measure is the rank of the first image with the same product ID as the query, on 10 sampled validation queries. A second check on 10 validation triplets had the positive closer than the negative in 9 of them.

## What the research found

After cropping, colour still dominated style. Grayscale was mixed, and helped somewhat with more data. RankNet gave better results than the Deep Ranking model, both by eye and on the rank measure. Some of the 10 queries had no rank and some ranks were large, so the result is mixed, and it is an indication, not a broad benchmark. The loss and the network depth differ between the two models, so their effects are not separated, and the report suggests an ablation study. A classmate and I wanted to see which artists people were sharing on Twitter at that moment. The pipeline reads the live Twitter stream, keeps the tweets that carry a Spotify link, and counts the shares per artist. A chart shows the top 20 artists of the last 60 minutes and redraws every five seconds.

## The pipeline

A Tweepy listener filters the stream in two steps. The Twitter API filter keeps tweets that match the keyword "spotify com". A JSON check then keeps only tweets with a URL and saves just the timestamp and the expanded link. Each record goes to a Kafka topic as a small JSON message.

A PySpark consumer reads that topic. It uses the receiver-less (direct) approach, so it asks Kafka for the latest offsets itself instead of running a separate receiver. For each record it takes the track id from the URL and asks the Spotify Web API for the artist. Records with no match are dropped. The counts go to Cassandra as (artist, timestamp, count) rows. A Dash app queries the table every five seconds, adds up the last hour and redraws the chart.

![Illustrative pipeline diagram: tweets filtered by Tweepy into Kafka, Spark Streaming resolves artists through the Spotify API, counts land in Cassandra, and a Dash chart refreshes every five seconds](/assets/images/projects/streaming-pipeline.svg)

Years later I reread the code and found two failures that the demo never showed. First, the consumer did not save its offsets, so after a crash it read the whole topic again. You attach a small Bluetooth Low Energy (BLE) device to something you do not want to lose, like your keys or wallet, and register it in the app. When the item is close, the near-finder screen reads the device's signal strength (RSSI) and tells you whether you are getting closer. You can also add photos and mark an item as lost.

## How it works

The Treki device only broadcasts its ID and signal strength. Any phone with the app that comes near it, yours or another user's, sends the device ID and the phone's location to the Treki server. The server stores the update in Firebase and sends a push notification to the owner. So a lost item gets its last-known location from other users' phones, because the device itself has no internet connection.

The app is React Native. It talks to the device with react-native-ble-plx, uses Redux with thunks for state and NativeBase for the UI. A thin Node.js API and Firebase hold the users, devices and sightings.

## The hard part

Crowd-sourced location only works if phones keep scanning for devices while the app is in the background. Keeping Bluetooth on in the background was the hardest part. Making it power efficient needs work on the hardware side too, not only in the app.

## My role and the result

I proposed the idea, led the team of four and was the main developer. Treki won the best presentation award at the end of the bootcamp, and I received the Teacher's Award for the best student.
