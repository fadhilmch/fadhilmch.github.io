20:T6e9,<p>With GitOps, a deploy is a commit that pins the image (<a href="/notes/git-sha-versioning/">[[git-sha-versioning]]</a>) and its config (<a href="/notes/config-vs-image/">[[config-vs-image]]</a>) for one <a href="/notes/kubernetes/">[[kubernetes]]</a> environment. Rollback is <code>git revert</code> of that commit. Argo CD syncs the cluster back, and the history keeps both the bad release and the revert.</p>
<p>Rules:</p>
<ul>
<li>One deploy, one commit, image and config together. Then one revert undoes both.</li>
<li>Don’t roll back in the cluster or in the Argo CD UI. With automated sync on, Argo CD refuses a rollback, and a manual change in the cluster drifts from Git.</li>
<li>Ask for an explicit confirmation and an optional target commit. Default to the latest deploy commit for that environment.</li>
<li><code>git log -- k8s/prod/deployment.yaml</code> is your release log.</li>
</ul>
<p>What a revert can’t undo: a refreshed knowledge base, data written in a new shape, and calls already made to other systems. If a release changes stored state, the older image must still read it (<a href="/notes/state-versioning/">[[state-versioning]]</a>). Test that before you need it.</p>
<p>A manual deploy that bypasses Git is not in this history. Redeploy through Git once the normal path works. Rolling back is cheap only if the older image is still in the registry, so check the retention policy before you purge. With <a href="/notes/image-promotion/">[[image-promotion]]</a>, that older image is one the environment already ran.</p>
