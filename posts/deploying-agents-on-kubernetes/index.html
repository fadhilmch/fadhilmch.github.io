Running an agentic chatbot on Kubernetes when a request takes a minute

In a load test, our chatbot's pods restarted under load while CPU stayed low and the autoscaler did nothing. What changes on Kubernetes when every request is slow and waits on the network: probes, autoscaling, shutdown, client lifecycle and how to run the load test itself.

Agents & LLMsML platformSystem design

Before launch, we ran a load test on our chatbot. It is a multi-agent RAG service: one question goes through several agents, a search index and many model calls before an answer comes back. Under load, a single request took from half a minute to well over a minute. That is slow, but we expected it.

What we did not expect was the shape of the failure. Partway through the test, many requests failed with HTTP 503 in bursts. The pods were being restarted by Kubernetes. CPU and memory stayed low the whole time, so the autoscaler never added a pod. I’ll leave out the user counts and latency numbers, which aren’t mine to share.

The cause was a set of defaults that are fine for a normal web API. A normal API answers in milliseconds and burns CPU while it works. Our service answers in tens of seconds and spends almost all of that time waiting on the network. This kind of work is called I/O-bound: the limit is how many slow calls you can keep open, not how fast the processor is. This post goes through what that changed for us on Kubernetes.

How a probe restarted a healthy pod

Kubernetes checks each container with probes. A liveness probe asks “is this process stuck?” If it fails too many times in a row, the kubelet (the agent on each node) restarts the container. A readiness probe asks “should this pod get traffic right now?” If it fails, the pod is taken out of the Service, but it is not restarted.

Our liveness probe called GET /health every 15 seconds, with a 2-second timeout and 3 allowed failures. The endpoint itself is cheap. It returns 200 and checks nothing outside the process.

However, the pod ran one uvicorn worker, so one Python process with one event loop. That loop was handling many concurrent requests, each with long model and search calls. Waiting on the network does not block an event loop. Everything between the waits does: parsing responses, building prompts, framework bookkeeping, and any call that is synchronous by accident. With enough requests in flight, the loop could not get to the probe within 2 seconds.

Three failed probes, 15 seconds apart, is about 45 seconds. Then the kubelet restarted the container. Every request in flight on that pod died with it, and each of them had already used up to a minute of model calls.

The restart made things worse, not better. The new container needs time to start, and while it starts, its share of traffic goes to the other pods. Those pods get busier, their probes start to fail, and the same thing happens to them. The Kubernetes documentation warns about exactly this: a wrong liveness probe can restart containers under high load and cause cascading failures [1].

One limit to state here. At that time we had no metric for event loop lag, so I can’t say which piece of work kept the loop busy. We fixed the conditions around it, which I describe next.

Probes for a slow service

The first fix was to give each probe one job, and to make the liveness probe forgiving. This is close to what we run now:

startupProbe:
  httpGet: { path: /health, port: 8000 }
  periodSeconds: 5
  failureThreshold: 24     # up to 2 minutes to start
livenessProbe:
  httpGet: { path: /health, port: 8000 }
  periodSeconds: 30
  timeoutSeconds: 5
  failureThreshold: 5      # about 2.5 minutes of failures before a restart
readinessProbe:
  httpGet: { path: /ready, port: 8000 }
  periodSeconds: 10
  timeoutSeconds: 5
  failureThreshold: 5

The startup probe runs only while the container starts. Liveness and readiness wait until it has passed once [1]. So the slow start no longer needs a long initialDelaySeconds on the liveness probe, and the liveness probe can stay focused on one question: is the process stuck?

The liveness probe now allows about two and a half minutes of failures. That is longer than our slowest request. A loop that is busy for a minute is not stuck. It is working.

Colin Breck’s post on probes gives the same advice in more detail [2]. Keep liveness cheap and local, never check dependencies in it, and set its timeout close to your client timeout. He also points out that every restart puts more load on the other pods.

We also changed the pod to run more than one uvicorn worker. Each worker is a separate process with its own event loop, so one busy loop no longer means a silent pod. There is a trade-off here. It comes from my own reasoning, not from a measurement. A probe now reaches whichever worker accepts the connection. If one worker is truly stuck, the probe can still pass through another one, and liveness will not catch it. More workers also means more memory, and Prometheus metrics need multiprocess mode so the workers’ counters are added up correctly.

Shutting down without dropping answers

Probes are not the only thing that stops a pod. A rollout, a scale-down and a node drain all do too. When Kubernetes stops a pod, it runs the preStop hook, sends SIGTERM, and waits for the grace period. The default grace period is 30 seconds. After that, any process still running gets SIGKILL [3].

For an API that answers in 100 milliseconds, 30 seconds is plenty. For us it is shorter than one request. So we set a longer terminationGracePeriodSeconds and a short preStop sleep, which gives the gateway time to stop sending new requests before the process gets SIGTERM. On shutdown, the app drains its pending background writes with a bounded timeout, then flushes buffered trace spans before it exits. Without the flush, the last traces of a pod are lost, and those are often the ones you want to read.

Check the arithmetic for your own service. The grace period includes the preStop hook [3]. If your slowest request is longer than the grace period minus the hook, a scale-down can still cut an answer in half. When I last checked, ours was not fully covered.

Why the autoscaler did nothing

The Horizontal Pod Autoscaler (HPA) works from a ratio. It computes desired = ceil(current × currentMetric / targetMetric) [4]. For CPU, the metric is a percentage of the pod’s CPU request. With CPU as the only signal, the HPA can only react to work that uses CPU.

Our pods were full and idle at the same time. They had as many slow requests open as they could handle, and the processor was mostly waiting. From the HPA’s point of view, nothing was happening.

Our quick fix was to lower the CPU and memory targets, add a faster scale-up policy, and allow more replicas. It passed the retest, and production still runs on it. However, it is a stopgap. It scales on a side effect of load, not on load.

The signal that matches an I/O-bound service is the number of in-flight requests: requests that have started and not yet finished. It grows with both traffic and latency. If ten questions arrive each minute and each takes a minute, about ten are open at any moment. If the model gets slower, that number rises even when traffic does not, and that is exactly when you need more pods.

Try it below. Keep the traffic the same and make the model slower, then watch which signal moves. The numbers are an illustration, not our measurements: each answer uses 0.6 CPU seconds, and the target is 8 open requests per pod.

We haven’t built this yet. Here is the plan. The app already exposes Prometheus metrics, and the instrumentation library we use has an opt-in gauge for requests in progress [5]. KEDA is an operator that feeds external metrics to a normal HPA, so the HPA controller still does the scaling [6]. Its Prometheus scaler runs a query and compares the result with a threshold [7]. It also works with Azure’s managed Prometheus through workload identity [7].

apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: chatbot-api
spec:
  scaleTargetRef:
    name: chatbot-api
  minReplicaCount: 2
  triggers:
    - type: prometheus
      metadata:
        serverAddress: http://prometheus:9090
        query: sum(http_requests_inprogress{handler="/query"})
        threshold: "8"   # in-flight requests per pod; pick yours from a load test

The threshold is the number of open requests one pod should hold. A load test is the way to find it: raise the load on a single pod until latency or errors climb, then stay well below that point. There is also a KEDA HTTP add-on that scales on HTTP traffic directly, through its own interceptor. It is still marked beta [8], so I would start with the Prometheus scaler.

Two leaks that only showed up under load

Neither of these is visible with one request at a time. Both appeared with many slow requests at once.

Model clients that were never closed

Each request built a fresh tree of agents, and each agent created its own model clients. Every one of those clients wraps an httpx connection pool. The agent runtime stopped at the end of a request, but stopping it did not close the clients. So every request left several connection pools open for the life of the process. Over time, that means more open sockets and more memory.

The fix closes them in a finally block, even when the request fails:

try:
    answer = await run_agents(question)
finally:
    for client in model_clients:
        try:
            await client.close()
        except Exception:
            logger.warning("failed to close model client", exc_info=True)
    await runtime.stop()

Each closing step has its own try, so a failure while cleaning up never hides the real error of the request. We also keep the clients in a list built at construction, so a renamed or newly added client can’t be forgotten in the cleanup.

The httpx documentation goes one step further [9]. To get the benefit of connection pooling, don’t create many client instances. Create one, share it, and close it when the app stops. A process-wide client per model deployment, closed in the app’s shutdown hook, would remove the problem instead of cleaning up after it.

A thread pool with six threads

Under burst load, reads and writes of conversation history to blob storage started to time out after 20 seconds. The traceback showed something odd. The time was spent before any network call had started.

The storage client uses aiohttp. With proxy settings taken from the environment, which the Azure SDK turns on by default, aiohttp looks up the proxy for every request in a thread through asyncio.to_thread. Token fetches from DefaultAzureCredential also run in threads. Both go to the event loop’s default thread pool. Its default size is min(32, os.cpu_count() + 4) [10]. On a pod with one or two CPUs, that is five or six threads.

So under burst, these small lookups queued behind each other, and the 20-second timeout ran out while they waited for a thread. The fix sets a larger default pool at startup [11]:

from concurrent.futures import ThreadPoolExecutor

@asynccontextmanager
async def lifespan(app):
    loop = asyncio.get_running_loop()
    loop.set_default_executor(
        ThreadPoolExecutor(max_workers=settings.async_executor_max_workers)
    )
    yield

The size is a setting, so it can change without a code change. An async service still has threads in it. Libraries move small blocking calls onto the default pool, and you don’t see it until that pool is full.

Running the load test

Two things made the load tests useful, and both happen before the first request is sent.

Keep test traffic out of production data

The load test runs the full pipeline with the same models and prompts. Without care, it would also fill the trace store with thousands of fake conversations, and the online evaluators would score them as if they were real users.

So the API accepts a test header, X-Test-Mode: true. With it, the request gets a no-op tracer, so no spans are exported. Everything else still runs. The session store works as normal, because the test simulates multi-turn conversations. Conversation history is still written, because we wanted to load that path too. Each record is tagged is_load_test: true, so it can be filtered out or deleted later. The response also returns its own duration in a header.

A header that turns off tracing is also a way to hide traffic. Accept it only from inside your network, or require a secret with it.

Write the pass rule first

Before the retest, we wrote down what “pass” meant:

  • an error rate under an agreed limit
  • p95 and p99 latency under the gateway timeout
  • zero pod restarts during the run
  • the autoscaler adds pods within 2 minutes after the ramp ends
  • the first 2 minutes are ignored, because a burst start is meant to be rough

Writing it first stops you from reading a result as “good enough” after you see it. The latency rule is tied to the gateway. Our gateway route has a total request timeout, and a slightly shorter timeout for each call to the backend. The total must be at least as long as the backend timeout [12]. Any answer slower than that is a failure to the user, even if the pod finished it.

Locust can turn part of this rule into an exit code [13]. A listener on the quitting event reads the final stats and sets environment.process_exit_code, so a pipeline can fail on it:

from locust import events

@events.quitting.add_listener
def check_pass_rule(environment, **kw):
    total = environment.stats.total
    failed = (
        total.fail_ratio > MAX_ERROR_RATE
        or total.get_response_time_percentile(0.95) > GATEWAY_TIMEOUT_MS
    )
    environment.process_exit_code = 1 if failed else 0

Locust can’t see pod restarts or the autoscaler. Check those from the cluster: the restart count in kubectl get pods, and the HPA’s events in kubectl describe hpa. Also give your simulated users a think time between turns. People read a long answer before they ask the next question, and a test without that pause measures a different service.

Identity, briefly

Most of our pods’ calls to the model service, the search index and storage still use keys from Kubernetes Secrets. We have a written plan to move to workload identity on AKS. The pod’s service account token is exchanged for a short-lived Entra token, and each service grants roles instead of keys [14]. I described the same idea on GKE and Azure in an earlier post, so I won’t repeat it. One detail matters for this post: token fetches also run on that default thread pool. Size the pool before you add more of them.

Things to watch

  • A liveness probe stricter than your slowest request. A busy pod is not a dead pod. Restarting it throws away all the work in flight.
  • Dependencies in the liveness probe. If the model service is down, restarting every pod will not bring it back.
  • Readiness under load. Failing readiness when busy moves traffic to the other pods. That is fine if they have room, and a cascade if they don’t.
  • CPU as the only scaling signal. For a service that mostly waits, it measures the wrong thing.
  • A grace period shorter than a request. Every rollout and scale-down then cuts some answers.
  • Per-request clients. Anything that holds a connection pool should live as long as the process, or be closed in a finally.
  • The default thread pool. It is small on small pods, and libraries use it without telling you.
  • Histogram buckets. Default latency buckets often stop at 1 second. Make sure the top bucket is above your gateway timeout, or every slow request lands in +Inf.

What I would try next

  • Scale on in-flight requests with KEDA and a Prometheus query, as above, and remove CPU from the HPA.
  • Measure event loop lag. A small task that sleeps for a fixed time and records how late it wakes up shows how busy the loop is. asyncio’s debug mode can also log any callback that runs longer than slow_callback_duration, 100 milliseconds by default [15]. That would answer the question I couldn’t answer above.
  • Shared model clients per process, as the httpx docs recommend [9].
  • Workload identity, following the plan.

If you move an LLM service onto Kubernetes, start from the length of your slowest request. Set the liveness probe, the grace period and the gateway timeout around it. Then scale on open requests instead of CPU, and write the load test’s pass rule before you run it.
