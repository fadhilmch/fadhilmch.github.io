Running several models in one LLM app, each with its own prompt

An evaluator in our chatbot flagged every reply for three months after a model upgrade, and nothing failed. How we route calls to several models, why each model gets its own prompt file picked by model name, which request parameters change between model families, and why an upgrade is a prompt change plus an eval.

Agents & LLMsML platformModelling

In June we moved an internal chatbot to a newer model. The chatbot is a multi-agent RAG app, and one of its agents is a guardrail evaluator. Some replies, such as a clarifying question or a polite refusal, go through it before the user sees them. It checks each one against three rules. If a reply breaks a rule, the evaluator names the rule and the reply is rewritten.

In October I found that since the June change, it had flagged every reply it checked. The new prompt told the model to answer "none" when no rule was broken. The response schema did not allow "none". It listed only the three rules. With a strict schema, the model can only produce values the schema allows, so it had to pick a rule every time. Nothing raised an error, and no test failed.

The fix was one value in the schema. I replayed 14 captured replies and 6 synthetic unsafe ones, three times each. The false-positive rate went from 1.00 to 0.00 with the schema fix. Adding an example with "none" to the prompt, without the schema fix, changed nothing.

A model is more than a name in a config file. It comes with its own prompt, its own request parameters and its own way of following an output schema. When one app runs several models, each of these has to follow the model. This post is about the operations side of that: routing, prompt files, parameters, upgrades and traces. I’ll leave out sizes and numbers that aren’t mine to share.

Why one app ends up with several models

A deployment is a named instance of a model in your cloud account. You choose the name. On Azure OpenAI, quota is counted per model and region, so deployments of different models don’t share a budget.

One answer from our chatbot needs about 15 model calls. Most are short and structured: detect the language, classify the question, plan the search, filter the results. A few write longer text: the answer, the evaluators, and the step that turns a follow-up into a standalone question. These two kinds of call need different things. The short calls must be quick, so they run with reasoning switched off and a 10-second timeout. The writing calls need more care, so they run at medium reasoning effort with 20 seconds.

Each kind of call also has a fallback deployment of an older model, with its own quota. The fallback and the circuit breaker around it are covered in another post. Here the fallback matters for a simpler reason. It is a second model, and the app has to call it correctly too.

So the app has two routes, each with a primary and a fallback. Both primaries use the same newer model. What differs between the routes is the reasoning effort, the timeout and the fallback. In production that is three models behind four slots, where a slot is one primary or one fallback.

Routing per workload, set in configuration

Model routing is the choice of which deployment serves a call. In our app each call names a route, and the route comes from configuration. Each slot has three settings:

# names simplified
WRITING_DEPLOYMENT_NAME=chat-new-model
WRITING_MODEL_NAME=new-model
WRITING_REASONING_EFFORT=medium
WRITING_FALLBACK_DEPLOYMENT_NAME=chat-old-model
WRITING_FALLBACK_MODEL_NAME=old-model
WRITING_FALLBACK_REASONING_EFFORT=low
# and the same six for the short calls

An empty fallback deployment switches the fallback off for that route. Timeouts and retries stay in code. Deployments differ between environments, so they belong in configuration. The timeouts follow the 60-second limit of the chat window, which is the same everywhere.

The model name is set next to the deployment name on purpose. The deployment says where the request goes. The model name says what will answer, and the app uses it for two other choices.

One prompt file per model

Every prompt in our app lives in a TOML file, one section per agent. There is one file for each model:

Model Prompt file
the newer model its own file
the older fallback models one file each
any reasoning model without its own file a shared reasoning file
anything else the legacy file

The legacy file was written for the older, non-reasoning models. The reasoning file is about half its size: 497 lines against 951. Both cover the same agents.

Why not one prompt for all? Because models read the same prompt differently. OpenAI’s GPT-4.1 guide says that model follows instructions “more closely and more literally than its predecessors”, and that prompts written for other models “may not immediately work” [1]. The GPT-5 guide says that “contradictory or vague instructions can be more damaging” to the newer model than to older ones [2]. A fix that helps one model can hurt another. With one file per model, I can change the prompt for one model and know the others did not move.

Pick the file by model name, not deployment name

A deployment name can be anything. Our CI deployment once had a -cicd suffix, and a deployment could just as well be called prod-default. If the app picked the prompt from the deployment name, a rename in one environment would quietly load a different prompt. So the app picks by model name, and the model name is a required setting for every slot.

Here is the shape of it, simplified:

PER_MODEL = [
    (re.compile(r"new-model"), "prompts_new_model.toml"),
    (re.compile(r"old-model-mini"), "prompts_old_model_mini.toml"),
]

def prompt_file(model_name: str) -> str:
    if not is_reasoning_model(model_name):
        return "prompts_legacy.toml"
    for pattern, path in PER_MODEL:
        if pattern.search(model_name):
            return path
    return "prompts_reasoning.toml"

Two details are easy to miss. First, a prompt loaded without a model name gets the default file, which belongs to the primary of the writing route. Two short-call agents loaded their prompt this way. They ran on one model and read the prompt meant for another, until a fix passed the model name explicitly. Second, when a call falls back, it reuses the messages it already built from the primary’s file. So during a fallback, the older model reads the newer model’s prompt. We accept that, and we have run the app with the primary switched off to check it.

A new model’s file starts as a copy of the closest one. The file for our newest model is still that copy, with a comment at the top saying so. That is fine for a start. The point of the separate file is that it can now change without touching the others.

Keeping the prompt files in step

Several files that should define the same prompts will drift. One file gets a new section, the others don’t, and the code loads a section that is missing for one model. A short test stops that:

def sections(path):
    def walk(node, prefix):
        keys = set()
        for key, value in node.items():
            if isinstance(value, dict):
                keys.add(f"{prefix}.{key}")
                keys |= walk(value, f"{prefix}.{key}")
        return keys
    return walk(tomllib.load(open(path, "rb")), "")

def test_per_model_prompt_files_define_the_same_sections():
    reference = sections(REASONING_FILE)
    for path in PER_MODEL_FILES:
        assert sections(path) == reference, path.name

The test checks structure, not wording. Two other kinds of test check that the files agree with the code:

  • Examples in a prompt must parse into the response schema. Our intent classifier’s examples were missing a field the schema had gained, so a test now loads every example line from the prompt and validates it. It runs on both the legacy and the reasoning file.
  • Some rules must hold for every model. One example is “state the limitation first when the sources don’t answer the question”. A test asserts it in both the legacy and the reasoning file.

The test we didn’t have in June was the one from the opening story: every value the prompt tells the model to output must be allowed by the schema. That is a cheap test, and it would have caught three months of false flags.

Parameters that differ between model families

The same request can be valid for one model and rejected by another. Azure’s reasoning-model page lists the parameters that reasoning models don’t support: temperature, top_p, presence_penalty, frequency_penalty, logprobs, top_logprobs, logit_bias and max_tokens [3]. So one module builds the request arguments for every call, and it changes them by model family:

Parameter Older models Reasoning models What our code does
temperature, top_p, penalties accepted rejected dropped for reasoning models, with a debug log
output limit max_tokens max_completion_tokens renamed, and scaled up
reasoning_effort rejected accepted sent only to reasoning models
verbosity not available accepted sent through extra_body, because our SDK version had no argument for it
system message system system or developer system unless a setting opts in

The output limit is scaled because the limit for reasoning models covers reasoning tokens as well as the visible answer [3]. A limit that was right for an older model can cut a reasoning model’s answer short. Our code multiplies it by 2.5, with a floor of 4,096 tokens.

Sending a parameter or omitting it

An empty reasoning effort in our configuration means the app does not send the parameter at all. Omitting a parameter is a real choice. It means “use this model’s default”, and the default changes between models. Azure’s page notes that one model version changed its default effort to none. Code that relied on the old default would get no reasoning after that upgrade [3]. The span records not-sent in that case, so a trace never shows a default that we did not choose.

A wrong value is worse than a missing one. Azure answers an unknown effort with a 400. A 400 does not trigger our fallback, because it is about the request. So a typo in the effort setting would break every call on that route. The settings now reject an unknown effort when the app starts.

When the app can’t tell the family

The family comes from the model name, matched against patterns. If the name doesn’t match, the code assumes the older family. A comment in the code explains why:

Misclassifying a reasoning deployment as legacy fails fast with a clear “Unsupported parameter” 400; the reverse silently drops parameters the caller expected.

I like this rule. An error you see on the first request is better than a wrong answer you find a month later. There is also a setting to force the family, for a deployment whose name says nothing about the model.

The patterns are not a permanent truth. The same Azure page now lists a newer model family that supports temperature again [3]. A rule like “reasoning models reject temperature” is true for a set of models, not forever.

Structured output

Every model we use supports structured output, so the schema is the same for all of them. The agent framework still asks the app to declare what a model supports, such as JSON and structured output. We declare it once for all deployments. The opening story is the other half of this. A strict schema always wins over the prompt. If the prompt and the schema disagree, the model follows the schema, and nothing tells you.

Keeping the old model working

When we first moved to a reasoning model, a teammate’s change kept the older models working beside it. The compatibility module and the first reasoning prompt file came from that change. Because of it, moving back is a configuration change. Every slot can point at an older model, and the request and the prompt follow.

Backward compatibility also has a cost. Until October, the default in our CI workflow still pointed the model tests at an older model, while production had used the newer one since June. Unless a repository setting overrode that default, those tests checked a different prompt file from the one users got. Keeping the old path working made that easy to miss.

An upgrade is a prompt change and an eval

In production, our June move to the newer model was a four-line configuration change. The prompt file for that model already existed. However, nothing in our tests compared that prompt with the response schemas, and nothing ran the model tests on the new model. That is how the evaluator bug lasted three months.

So now I treat an upgrade as three steps:

  1. Give the new model its own prompt file, copied from the closest one, and tune it there.
  2. Run the eval set with the new model as the primary, and compare it with the current model on the same questions. Run the contract tests on the new file too.
  3. Switch the configuration, and keep the current model as the fallback for a while. Rolling back is then a configuration change.

Azure’s model lifecycle page gives the same advice for a retiring model. Evaluate candidates “against your own application, prompts, and representative data”, and compare quality, latency and cost together [4]. The same page has a warning for anyone who thinks of a deployment name as fixed. Standard deployments are upgraded automatically when a model version retires, and the deployment’s versionUpgradeOption decides when, or whether, that happens [4]. An upgrade like that changes the model without any change in your repository.

Seeing which model answered

With several models and a fallback, “which model answered this?” is a question you will ask often. In June a teammate fixed two agents’ spans that showed no useful model name. Now every routed call writes these on its existing LLM span:

Attribute Example
llm.model_name the deployment that answered
llm.route the route the call used
llm.reasoning_effort none, medium, or not-sent

With these, you can compare p95 latency by model and by route. The same span also records whether a fallback answered, which the post on quota and fallbacks covers. OpenTelemetry’s GenAI conventions make a distinction that I find useful here. gen_ai.request.model is the model you asked for, and gen_ai.response.model is “the name of the model that generated the response” [5]. Our llm.model_name holds a deployment name, so it can’t show an automatic version upgrade.

Things to watch

  • Prompt and schema disagree. Test that every value the prompt asks for is allowed by the schema. A strict schema overrides the prompt without an error.
  • The wrong key for the prompt. Pick the prompt file by model name. Make the model name a required setting, even when it equals the deployment name today.
  • A call site with no model. A default prompt file is convenient, and it is wrong for every agent on a different model.
  • Omitted parameters. An omitted parameter takes the model’s default, and defaults change between versions. Record what you sent.
  • Bad values that don’t fall back. A 400 from a typo in a setting breaks the whole route. Validate settings when the app starts.
  • Tests on a different model. If CI runs another model, it also loads another prompt file.

What others do

A few ideas from outside that I haven’t built:

  • A router library or gateway. LiteLLM can drop the parameters a model does not support. By default it raises an error instead, and you opt in to dropping with drop_params [6]. Our code drops sampling parameters for reasoning models with only a debug log. One option is to raise in tests and drop in production, so a parameter that someone expects to work fails early.
  • Model settings stored with the prompt. Langfuse lets each prompt version carry a config object with the model name and parameters, “versioned together with the prompt” [7]. In our app the prompt is in a TOML file and the effort is in environment settings, so a change can touch one and forget the other.
  • Evals on every change. OpenAI’s evaluation guide suggests continuous evaluation, which runs evals on every change [8]. A model upgrade is one of those changes, and a prompt edit for one model is another.
  • The model that answered, from the response. Record the response model next to the requested one, as the OpenTelemetry conventions suggest [5]. An automatic upgrade would then show up in traces.

If your app calls more than one model, give each model its own prompt file and pick it by model name. Test that the files agree with each other and with your schemas. Then treat the next model upgrade as a prompt change with an eval, and keep the old model ready as a fallback until the new one has proven itself.
