22:T6fe8,<p>In June we moved an internal chatbot to a newer model. The chatbot is a multi-agent RAG app, and one of its agents is a guardrail evaluator. Some replies, such as a clarifying question or a polite refusal, go through it before the user sees them. It checks each one against three rules. If a reply breaks a rule, the evaluator names the rule and the reply is rewritten.</p>
<p>In October I found that since the June change, it had flagged every reply it checked. The new prompt told the model to answer <code>"none"</code> when no rule was broken. The response schema did not allow <code>"none"</code>. It listed only the three rules. With a strict schema, the model can only produce values the schema allows, so it had to pick a rule every time. Nothing raised an error, and no test failed.</p>
<p>The fix was one value in the schema. I replayed 14 captured replies and 6 synthetic unsafe ones, three times each. The false-positive rate went from 1.00 to 0.00 with the schema fix. Adding an example with <code>"none"</code> to the prompt, without the schema fix, changed nothing.</p>
<p>A model is more than a name in a config file. It comes with its own prompt, its own request parameters and its own way of following an output schema. When one app runs several models, each of these has to follow the model. This post is about the operations side of that: routing, prompt files, parameters, upgrades and traces. I’ll leave out sizes and numbers that aren’t mine to share.</p>
<h2>Why one app ends up with several models</h2>
<p>A <strong>deployment</strong> is a named instance of a model in your cloud account. You choose the name. On Azure OpenAI, quota is counted per model and region, so deployments of different models don’t share a budget.</p>
<p>One answer from our chatbot needs about 15 model calls. Most are short and structured: detect the language, classify the question, plan the search, filter the results. A few write longer text: the answer, the evaluators, and the step that turns a follow-up into a standalone question. These two kinds of call need different things. The short calls must be quick, so they run with reasoning switched off and a 10-second timeout. The writing calls need more care, so they run at medium reasoning effort with 20 seconds.</p>
<p>Each kind of call also has a fallback deployment of an older model, with its own quota. The fallback and the circuit breaker around it are covered in <a href="/posts/llm-quota-fallback-circuit-breaker/">another post</a>. Here the fallback matters for a simpler reason. It is a second model, and the app has to call it correctly too.</p>
<p>So the app has two routes, each with a primary and a fallback. Both primaries use the same newer model. What differs between the routes is the reasoning effort, the timeout and the fallback. In production that is three models behind four slots, where a <strong>slot</strong> is one primary or one fallback.</p>
<h2>Routing per workload, set in configuration</h2>
<p><strong>Model routing</strong> is the choice of which deployment serves a call. In our app each call names a route, and the route comes from configuration. Each slot has three settings:</p>
<pre><code class="hljs language-bash"><span class="hljs-comment"># names simplified</span>
WRITING_DEPLOYMENT_NAME=chat-new-model
WRITING_MODEL_NAME=new-model
WRITING_REASONING_EFFORT=medium
WRITING_FALLBACK_DEPLOYMENT_NAME=chat-old-model
WRITING_FALLBACK_MODEL_NAME=old-model
WRITING_FALLBACK_REASONING_EFFORT=low
<span class="hljs-comment"># and the same six for the short calls</span>
</code></pre>
<p>An empty fallback deployment switches the fallback off for that route. Timeouts and retries stay in code. Deployments differ between environments, so they belong in configuration. The timeouts follow the 60-second limit of the chat window, which is the same everywhere.</p>
<p>The model name is set next to the deployment name on purpose. The deployment says where the request goes. The model name says what will answer, and the app uses it for two other choices.</p>

<h2>One prompt file per model</h2>
<p>Every prompt in our app lives in a TOML file, one section per agent. There is one file for each model:</p>

<p>The legacy file was written for the older, non-reasoning models. The reasoning file is about half its size: 497 lines against 951. Both cover the same agents.</p>
<p>Why not one prompt for all? Because models read the same prompt differently. OpenAI’s GPT-4.1 guide says that model follows instructions “more closely and more literally than its predecessors”, and that prompts written for other models “may not immediately work” [1]. The GPT-5 guide says that “contradictory or vague instructions can be more damaging” to the newer model than to older ones [2]. A fix that helps one model can hurt another. With one file per model, I can change the prompt for one model and know the others did not move.</p>
<h3>Pick the file by model name, not deployment name</h3>
<p>A deployment name can be anything. Our CI deployment once had a <code>-cicd</code> suffix, and a deployment could just as well be called <code>prod-default</code>. If the app picked the prompt from the deployment name, a rename in one environment would quietly load a different prompt. So the app picks by model name, and the model name is a required setting for every slot.</p>

<p>Here is the shape of it, simplified:</p>
<pre><code class="hljs language-python">PER_MODEL = [

<span class="hljs-keyword">def</span> <span class="hljs-title function_">prompt_file</span>(<span class="hljs-params">model_name: <span class="hljs-built_in">str</span></span>) -> <span class="hljs-built_in">str</span>:

        <span class="hljs-keyword">return</span> <span class="hljs-string">"prompts_legacy.toml"</span>
    <span class="hljs-keyword">for</span> pattern, path <span class="hljs-keyword">in</span> PER_MODEL:

<p>Two details are easy to miss. First, a prompt loaded without a model name gets the default file, which belongs to the primary of the writing route. Two short-call agents loaded their prompt this way. They ran on one model and read the prompt meant for another, until a fix passed the model name explicitly. Second, when a call falls back, it reuses the messages it already built from the primary’s file. So during a fallback, the older model reads the newer model’s prompt. We accept that, and we have run the app with the primary switched off to check it.</p>
<p>A new model’s file starts as a copy of the closest one. The file for our newest model is still that copy, with a comment at the top saying so. That is fine for a start. The point of the separate file is that it can now change without touching the others.</p>
<h2>Keeping the prompt files in step</h2>
<p>Several files that should define the same prompts will drift. One file gets a new section, the others don’t, and the code loads a section that is missing for one model. A short test stops that:</p>
<pre><code class="hljs language-python"><span class="hljs-keyword">def</span> <span class="hljs-title function_">sections</span>(<span class="hljs-params">path</span>):
    <span class="hljs-keyword">def</span> <span class="hljs-title function_">walk</span>(<span class="hljs-params">node, prefix</span>):
        keys = <span class="hljs-built_in">set</span>()
        <span class="hljs-keyword">for</span> key, value <span class="hljs-keyword">in</span> node.items():
            <span class="hljs-keyword">if</span> <span class="hljs-built_in">isinstance</span>(value, <span class="hljs-built_in">dict</span>):
                keys.add(<span class="hljs-string">f"<span class="hljs-subst">{prefix}</span>.<span class="hljs-subst">{key}</span>"</span>)
                keys |= walk(value, <span class="hljs-string">f"<span class="hljs-subst">{prefix}</span>.<span class="hljs-subst">{key}</span>"</span>)
        <span class="hljs-keyword">return</span> keys
    <span class="hljs-keyword">return</span> walk(tomllib.load(<span class="hljs-built_in">open</span>(path, <span class="hljs-string">"rb"</span>)), <span class="hljs-string">""</span>)

<span class="hljs-keyword">def</span> <span class="hljs-title function_">test_per_model_prompt_files_define_the_same_sections</span>():
    reference = sections(REASONING_FILE)
    <span class="hljs-keyword">for</span> path <span class="hljs-keyword">in</span> PER_MODEL_FILES:
        <span class="hljs-keyword">assert</span> sections(path) == reference, path.name
</code></pre>
<p>The test checks structure, not wording. Two other kinds of test check that the files agree with the code:</p>
<ul>
<li>Examples in a prompt must parse into the response schema. Our intent classifier’s examples were missing a field the schema had gained, so a test now loads every example line from the prompt and validates it. It runs on both the legacy and the reasoning file.</li>
<li>Some rules must hold for every model. One example is “state the limitation first when the sources don’t answer the question”. A test asserts it in both the legacy and the reasoning file.</li>
</ul>
<p>The test we didn’t have in June was the one from the opening story: every value the prompt tells the model to output must be allowed by the schema. That is a cheap test, and it would have caught three months of false flags.</p>
<h2>Parameters that differ between model families</h2>
<p>The same request can be valid for one model and rejected by another. Azure’s reasoning-model page lists the parameters that reasoning models don’t support: <code>temperature</code>, <code>top_p</code>, <code>presence_penalty</code>, <code>frequency_penalty</code>, <code>logprobs</code>, <code>top_logprobs</code>, <code>logit_bias</code> and <code>max_tokens</code> [3]. So one module builds the request arguments for every call, and it changes them by model family:</p>

<h3>Sending a parameter or omitting it</h3>
<p>An empty reasoning effort in our configuration means the app does not send the parameter at all. Omitting a parameter is a real choice. It means “use this model’s default”, and the default changes between models. Azure’s page notes that one model version changed its default effort to <code>none</code>. Code that relied on the old default would get no reasoning after that upgrade [3]. The span records <code>not-sent</code> in that case, so a trace never shows a default that we did not choose.</p>
<p>A wrong value is worse than a missing one. Azure answers an unknown effort with a 400. A 400 does not trigger our fallback, because it is about the request. So a typo in the effort setting would break every call on that route. The settings now reject an unknown effort when the app starts.</p>
<h3>When the app can’t tell the family</h3>
<p>The family comes from the model name, matched against patterns. If the name doesn’t match, the code assumes the older family. A comment in the code explains why:</p>
<blockquote>
<p>Misclassifying a reasoning deployment as legacy fails fast with a clear “Unsupported parameter” 400; the reverse silently drops parameters the caller expected.</p>
</blockquote>
<p>I like this rule. An error you see on the first request is better than a wrong answer you find a month later. There is also a setting to force the family, for a deployment whose name says nothing about the model.</p>
<p>The patterns are not a permanent truth. The same Azure page now lists a newer model family that supports <code>temperature</code> again [3]. A rule like “reasoning models reject temperature” is true for a set of models, not forever.</p>

<h3>Structured output</h3>
<p>Every model we use supports structured output, so the schema is the same for all of them. The agent framework still asks the app to declare what a model supports, such as JSON and structured output. We declare it once for all deployments. The opening story is the other half of this. A strict schema always wins over the prompt. If the prompt and the schema disagree, the model follows the schema, and nothing tells you.</p>
<h2>Keeping the old model working</h2>
<p>When we first moved to a reasoning model, a teammate’s change kept the older models working beside it. The compatibility module and the first reasoning prompt file came from that change. Because of it, moving back is a configuration change. Every slot can point at an older model, and the request and the prompt follow.</p>
<p>Backward compatibility also has a cost. Until October, the default in our CI workflow still pointed the model tests at an older model, while production had used the newer one since June. Unless a repository setting overrode that default, those tests checked a different prompt file from the one users got. Keeping the old path working made that easy to miss.</p>
<h2>An upgrade is a prompt change and an eval</h2>
<p>In production, our June move to the newer model was a four-line configuration change. The prompt file for that model already existed. However, nothing in our tests compared that prompt with the response schemas, and nothing ran the model tests on the new model. That is how the evaluator bug lasted three months.</p>
<p>So now I treat an upgrade as three steps:</p>
<ol>
<li>Give the new model its own prompt file, copied from the closest one, and tune it there.</li>
<li>Run the eval set with the new model as the primary, and compare it with the current model on the same questions. Run the contract tests on the new file too.</li>
<li>Switch the configuration, and keep the current model as the fallback for a while. Rolling back is then a configuration change.</li>
</ol>
<p>Azure’s model lifecycle page gives the same advice for a retiring model. Evaluate candidates “against your own application, prompts, and representative data”, and compare quality, latency and cost together [4]. The same page has a warning for anyone who thinks of a deployment name as fixed. Standard deployments are upgraded automatically when a model version retires, and the deployment’s <code>versionUpgradeOption</code> decides when, or whether, that happens [4]. An upgrade like that changes the model without any change in your repository.</p>

OpenTelemetry’s GenAI conventions make a distinction that I find useful here. <code>gen_ai.request.model</code> is the model you asked for, and <code>gen_ai.response.model</code> is “the name of the model that generated the response” [5]. Our <code>llm.model_name</code> holds a deployment name, so it can’t show an automatic version upgrade.</p>
<h2>Things to watch</h2>
<ul>
<li><strong>Prompt and schema disagree.</strong> Test that every value the prompt asks for is allowed by the schema. A strict schema overrides the prompt without an error.</li>
<li><strong>The wrong key for the prompt.</strong> Pick the prompt file by model name. Make the model name a required setting, even when it equals the deployment name today.</li>
<li><strong>A call site with no model.</strong> A default prompt file is convenient, and it is wrong for every agent on a different model.</li>
<li><strong>Omitted parameters.</strong> An omitted parameter takes the model’s default, and defaults change between versions. Record what you sent.</li>
<li><strong>Bad values that don’t fall back.</strong> A 400 from a typo in a setting breaks the whole route. Validate settings when the app starts.</li>
<li><strong>Tests on a different model.</strong> If CI runs another model, it also loads another prompt file.</li>
</ul>
<h2>What others do</h2>
<p>A few ideas from outside that I haven’t built:</p>
<ul>
<li><strong>A router library or gateway.</strong> LiteLLM can drop the parameters a model does not support. By default it raises an error instead, and you opt in to dropping with <code>drop_params</code> [6]. Our code drops sampling parameters for reasoning models with only a debug log. One option is to raise in tests and drop in production, so a parameter that someone expects to work fails early.</li>
<li><strong>Model settings stored with the prompt.</strong> Langfuse lets each prompt version carry a config object with the model name and parameters, “versioned together with the prompt” [7]. In our app the prompt is in a TOML file and the effort is in environment settings, so a change can touch one and forget the other.</li>
<li><strong>Evals on every change.</strong> OpenAI’s evaluation guide suggests continuous evaluation, which runs evals on every change [8]. A model upgrade is one of those changes, and a prompt edit for one model is another.</li>
<li><strong>The model that answered, from the response.</strong> Record the response model next to the requested one, as the OpenTelemetry conventions suggest [5]. An automatic upgrade would then show up in traces.</li>
</ul>
<p>If your app calls more than one model, give each model its own prompt file and pick it by model name. Test that the files agree with each other and with your schemas. Then treat the next model upgrade as a prompt change with an eval, and keep the old model ready as a fallback until the new one has proven itself.</p>
