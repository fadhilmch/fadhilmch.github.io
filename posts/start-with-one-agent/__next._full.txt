1e:T6322,<p>Our chatbot has an agent called the Orchestration Agent. It reads the JSON that the reception agent wrote and copies five fields into a new JSON. Then it adds one more field: the name of the agent that should speak next. That name is always the same. The Orchestration Agent never calls a model.</p>
<p>It is one of about a dozen agents in three nested group chats. In each group chat, a selector function decides who speaks next. Two of those functions carry the same comment: the selection is deterministic, to avoid LLM calls.</p>
<p>So we had built a multi-agent system, and then written a lot of code to make sure the agents did not decide anything. This post goes through that gap. It covers the difference between a workflow and an agent, what the group chat cost us, and how we are moving to one agent whose steps are fixed in code. I’ll leave out sizes and numbers that aren’t mine to share.</p>
<h2>Workflows and agents</h2>
<p>Anthropic’s post on building effective agents gives each side one sentence [1]. <strong>Workflows</strong> are “systems where LLMs and tools are orchestrated through predefined code paths.” <strong>Agents</strong> are “systems where LLMs dynamically direct their own processes and tool usage.”</p>
<p>I reduce that to one question: who decides the next step? If your code decides, it is a workflow, even when every step calls a model. If the model decides, it is an agent.</p>
<p>So a step that asks a model “is this question in scope?” and then routes on the answer in code is still a workflow. Anthropic calls this pattern <em>routing</em>: it “classifies an input and directs it to a specialized followup task” [1]. The model classifies. The code owns the edge.</p>
<p>Microsoft’s Agent Framework documentation puts the choice in a table [3]. Use an agent when the task is open-ended or conversational, or needs autonomous tool use and planning. Use a workflow when the process has well-defined steps and you need explicit control over the order. Below the table is one line I like: “If you can write a function to handle the task, do that instead of using an AI agent.”</p>
<p>OpenAI’s guide is even stricter [2]. Apps that use LLMs but don’t let them control the workflow are not agents in its definition. Its examples are “simple chatbots, single-turn LLMs, or sentiment classifiers”.</p>

<h2>How the chatbot was built</h2>
<p>The chatbot answers questions from internal documents. It was built in 2025 on AutoGen, as three nested group chats. A reception chat works out what the user is asking. If the question is clear, it passes it to a RAG chat that searches and filters documents. The RAG chat passes the documents to a response chat that writes the answer and checks it. Each inner chat is wrapped as a single agent inside the chat above it.</p>
<p>Each group chat is an AutoGen <code>SelectorGroupChat</code>. By default it asks a model to pick the next speaker. The model reads the conversation and the agents’ descriptions, then names an agent [4]. You can also pass your own <code>selector_func</code>. If it returns a name, that agent speaks. If it returns <code>None</code>, AutoGen falls back to the model [4].</p>
<p>Here is the shape of our RAG chat’s selector. This is a simplified sketch, not our exact code:</p>
<pre><code class="hljs language-python"><span class="hljs-keyword">def</span> <span class="hljs-title function_">select_next</span>(<span class="hljs-params">messages</span>):
    last = messages[-<span class="hljs-number">1</span>]

<p>Every path we know about returns a name. The model is only there for a case nobody planned. So the flow was a fixed graph all along. We had written it by hand, inside a callback whose job was to name the next speaker.</p>

<h2>What the group chat cost us</h2>
<p>The group chat worked, and it answered users for a long time. But it made a fixed flow hard to read and hard to change. Here is where that showed.</p>
<p>The routing was spread out. Each selector also updates counters, such as how many clarifying questions the bot has asked in a row. To answer “why did this user get a fallback?”, you follow the messages through three selectors and the counters they change.</p>
<p>The limits were easy to get wrong. Each group chat has <code>max_turns=25</code>, but the limits that matter are the counters. One clarifier ran after the answer was written, when the answer scored low on relevance. In one dev session it asked four clarifying questions in a row. The reception chat reset its counter on every reply from the RAG chat, so nothing capped the loop. We removed that clarifier. A low-relevance turn now returns the answer, its source links, and a line that tells the user where to get help from a person.</p>
<p>The fallback to a model was invisible. All three selectors are given a small model, and their calls are made outside our LLM spans. Our model router does not trace them, to avoid orphan traces. So if a selector ever fell through to the model, we would pay for a call we could not see.</p>
<p>Agents passed data as text. Each agent writes JSON into a chat message, and the next agent parses it with <code>json.loads</code>. The Orchestration Agent reads the last message, and if that one is not from reception, it reads the one before. The shape of the data between steps lived in prompts and parsing code, not in a type.</p>
<p>The framework’s state leaked into ours. At first, the session store kept the raw output of the team’s <code>save_state()</code>. A change of framework would have broken every live conversation.</p>
<h2>Moving to a workflow, one seam at a time</h2>
<p>We didn’t start with a rewrite. The first step was a <strong>seam</strong>: an interface the rest of the code depends on, so the implementation behind it can change. A decision record we wrote in July 2026 says it directly: decouple the code from AutoGen now, and decide about a migration later, with its own evidence.</p>
<p>A handful of small pull requests did this. They removed dead code and replaced AutoGen’s token-usage types with our own. They also wrapped the session state in a versioned envelope, and put an interface between the API route and the group chats:</p>
<pre><code class="hljs language-python"><span class="hljs-keyword">class</span> <span class="hljs-title class_">ConversationOrchestrator</span>(<span class="hljs-title class_ inherited__">Protocol</span>):
    <span class="hljs-keyword">async</span> <span class="hljs-keyword">def</span> <span class="hljs-title function_">run</span>(<span class="hljs-params">
        self,
        query: <span class="hljs-built_in">str</span>,
        session_state: <span class="hljs-built_in">dict</span>[<span class="hljs-built_in">str</span>, <span class="hljs-built_in">object</span>],
        *,
        context: OrchestrationContext,
    </span>) -> OrchestrationResult: ...
</code></pre>
<p>The route now depends on this protocol only. Its tests use a fake orchestrator and don’t start any agents. A later change replaced the framework’s state with our own small schema: a few counters and the last eight turns. This work is merged. It was useful whether or not we ever changed frameworks.</p>
<h3>The first port did too much</h3>
<p>The first port to Microsoft Agent Framework (MAF) came the same month, on a branch. It replaced the three group chats with one flat graph. In MAF, the nodes of a graph are <strong>executors</strong> and the connections are edges [7]. Reception became the start executor, routing decisions moved to switch-case edges, and every path ended in one terminal executor.</p>
<p>The shape was right. However, the same branch also changed prompts, merged four reception calls into one, and changed how clarification worked. It added an adapter, a runner and a message type for each stage. In an offline eval, answer quality was about the same as before, and latency did not go down.</p>
<p>When a port changes the framework and the behavior together, an eval cannot tell you which change moved a result. Meanwhile the main branch moved on. The pull request was closed in October without merging. The new plan builds from the current code and uses the old branch only as a source of ideas and test cases. It also tags every eval case as either preserved or intentionally changed.</p>
<h3>The current plan is smaller</h3>
<p>The plan from October 2026 has three executors: <code>receive</code>, <code>retrieve</code> and <code>respond</code>. Each one calls ordinary Python functions, and the business rules live in those functions. No model picks the next step. In MAF the workflow is wrapped as a single agent, so the rest of the app talks to one agent instead of a team.</p>
<p>Its first draft didn’t use a graph at all. It recommended a plain Python coordinator, something like this sketch:</p>
<pre><code class="hljs language-python"><span class="hljs-keyword">async</span> <span class="hljs-keyword">def</span> <span class="hljs-title function_">run_turn</span>(<span class="hljs-params">query, state</span>):
    request = <span class="hljs-keyword">await</span> receive(query, state)   <span class="hljs-comment"># understand, check scope</span>
    <span class="hljs-keyword">if</span> request.reply:                       <span class="hljs-comment"># greeting, clarification, refusal</span>
        <span class="hljs-keyword">return</span> request.reply
    sources = <span class="hljs-keyword">await</span> retrieve(request)       <span class="hljs-comment"># plan, search, filter</span>
    <span class="hljs-keyword">if</span> <span class="hljs-keyword">not</span> sources:
        <span class="hljs-keyword">return</span> no_answer(request)
    <span class="hljs-keyword">return</span> <span class="hljs-keyword">await</span> respond(request, sources)  <span class="hljs-comment"># write, check, cite</span>
</code></pre>
<p>The graph won in the end, for reasons the plan writes down. MAF gives each executor its own span in our traces, and a graph follows the framework’s own guidance. The plan also names the cost. Each executor must either send one input to the next step or yield one final result, never both. A guard then checks that exactly one result came out. A plain chain of functions needs neither rule.</p>
<p>This work is still on a branch as I write this.</p>
<h2>What a new orchestrator does not fix</h2>
<p>We expected the first port to make answers faster. It didn’t. When I broke turn latency down by what each turn did, most of the time went to the model writing the answer. Most of the rest grew with the number of documents retrieved. The orchestration itself was a small fixed part.</p>
<p>So change the orchestration to make the flow readable and testable, and to stop paying for routing calls. Don’t change it to make the model write faster. For that, the length of the answer matters much more.</p>
<h2>Where an agent fits</h2>
<p>None of this means agents are a mistake. Anthropic’s post says agents fit “open-ended problems where it’s difficult or impossible to predict the required number of steps, and where you can’t hardcode a fixed path” [1]. The same post warns that agentic systems “often trade latency and cost for better task performance”.</p>
<p>OpenAI’s guide lists where agents earn their place [2]. One case is decisions that need judgment and have many exceptions. Another is rule sets that have become too hard to maintain. A third is work that depends heavily on unstructured data. Then it says: “Otherwise, a deterministic solution may suffice.”</p>
<p>In our chatbot, the model has real freedom in one place: the text of the answer. The other model calls classify, rewrite queries or filter documents, and code acts on what they return.</p>
<p>If you do need an agent, start with one. OpenAI’s guide recommends that you “maximize a single agent’s capabilities first” [2]. It suggests splitting only when prompts fill up with if-then-else branches, or when the agent keeps choosing the wrong tool among overlapping ones.</p>
<h3>Two sides of the multi-agent debate</h3>
<p>Two posts from June 2025 are worth reading together. Cognition’s “Don’t Build Multi-Agents” argues from two principles [5]. Share full context between agents, and remember that “actions carry implicit decisions”. In their example, two subagents each build part of a Flappy Bird clone. One builds a background that looks like Super Mario Bros., and the other builds a bird that doesn’t match it. Their advice is a single-threaded linear agent.</p>
<p>A day later, Anthropic described its multi-agent research system [6]. Parallel subagents search different directions at once, which helps on broad research questions. The post is also clear about where this does not fit: tasks where all agents need the same context, or with many dependencies between agents. I summarized its checklist in a <a href="/notes/multi-agent/">note on multi-agent systems</a>.</p>
<p>The two posts agree more than their titles suggest. Split work across agents only when the parts are independent. A chatbot turn is the opposite case, because each step needs what the step before it produced.</p>
<h2>Questions before you add an agent</h2>
<ul>
<li>Can you draw the flow before you see the input? Write it as code.</li>
<li>Is the decision a choice from a fixed list? Use one model call with structured output, and route on the answer in code.</li>
<li>Does the next step depend on results you can’t predict, like a search that may need several tries? Use one agent with tools and a turn limit.</li>
<li>Do the parts run in parallel, need separate context, and rarely depend on each other? Then consider several agents, and measure the extra tokens against an eval.</li>
</ul>
<h2>Things to watch</h2>
<ul>
<li>A class called an agent that never calls a model is a function. Call it one, so readers don’t look for a prompt.</li>
<li>If a selector can return <code>None</code>, a missing case quietly becomes a model call. In a fixed flow, raise an error instead.</li>
<li>A turn limit per group chat does not stop a loop that spans several user turns. Count the thing you want to cap, and reset the count only where that thing really ends.</li>
<li>Don’t store a framework’s internal state in your session store. Store your own schema, with a version number.</li>
<li>Porting to a new framework and changing behavior in one release makes the eval hard to read. Keep them apart, or label each eval case.</li>
<li>Measure where the time goes before you rewrite the orchestrator for speed.</li>
</ul>
<p>If the flow of your chatbot fits on a whiteboard before any user types a question, write it as a workflow. Use the model for the steps that need language, and keep the decision about what happens next in code you can test.</p>
