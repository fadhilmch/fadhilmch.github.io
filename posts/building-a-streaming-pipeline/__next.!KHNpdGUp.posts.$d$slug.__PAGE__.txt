34:Tb113,<p>In autumn 2019, a classmate and I built a live chart of the artists people were sharing on Twitter. Tweets containing a Spotify link went into Kafka. Spark Streaming looked up each track’s artist on the Spotify API, Cassandra stored the counts, and a Dash page redrew the top twenty every five seconds. It was my first streaming system.</p>
<p>It worked, and <a href="https://youtu.be/eLnKT_aGahk">the recording</a> shows it: bars grow, artists move up and down. Reading the code again a year and a half later, I can see that we had built the <em>shape</em> of a streaming pipeline without most of the things that make one trustworthy. This post starts with the ideas behind data streaming, then goes through what we built, the five things a stream has to get right, and how I’d deploy the same idea on a real cluster.</p>
<figure class="fig">
<img src="/assets/images/projects/streaming-trending-artists.gif" alt="Screen recording of the dashboard: a top-twenty bar chart of trending artists redrawing every five seconds as bars grow and artists swap places" loading="lazy">
</figure>
<h2>Data streaming, briefly</h2>
<p>Most of the data I’d worked with until then sat still: a CSV, a table, a folder of files. Streaming starts from a different assumption. The data never stops arriving, and you want answers while it’s still arriving.</p>
<h3>Batch or stream</h3>
<p>A <strong>batch</strong> job processes a fixed chunk of data on a schedule: every night, every hour. A <strong>stream</strong> processor handles each event as it arrives and keeps its answer continuously up to date.</p>

<p>The purpose is freshness. A batch job’s answer is as old as the time since its last run. A stream’s answer is seconds old, which matters when the question is “what’s happening now”: fraud, monitoring, or a live chart of what people are sharing. The cost is complexity. A batch job sees all its input at once and can simply be rerun if it fails; a stream must keep working, and keep being correct, while data keeps arriving.</p>
<h3>The log in the middle</h3>
<p>Most streaming systems put a <strong>log</strong> between the things that produce events and the things that process them. Kafka is the best-known example. A log is the simplest possible data structure: an ordered list of events that you can only append to. Each event gets a position, its <em>offset</em>.</p>

<p>That simple structure does a lot of work:</p>
<ul>
<li><strong>It decouples producers and consumers.</strong> The producer doesn’t know or care who reads. A slow consumer falls behind without slowing the producer down.</li>
<li><strong>It absorbs bursts.</strong> When a thousand events arrive in one second, they wait in the log instead of being dropped.</li>
<li><strong>It makes history replayable.</strong> Events stay in the log for a retention period. A consumer that crashed, or a new job that needs old data, just starts from an earlier offset.</li>
</ul>
<h3>Spreading the log across machines</h3>
<p>One machine eventually runs out of disk, network or CPU, and one machine can die. So a topic is split into <strong>partitions</strong>, and the partitions are spread across several <strong>brokers</strong>. Each partition is also <strong>replicated</strong>: one broker holds the leader copy, and others keep followers that can take over if that broker fails.</p>

<p>On the reading side, a <strong>consumer group</strong> shares the work: each partition goes to one worker in the group, so adding workers (up to the number of partitions) adds throughput. The price of this parallelism is ordering. Events are in order within a partition but not across partitions. That’s why events are usually partitioned by a key: all events for the same user or the same artist land in the same partition and stay in order.</p>
<p>This is where streaming becomes a distributed-systems problem. Machines fail, networks pause and workers restart, and the system has to keep going without losing or double-counting data.</p>
<h3>Processing: stateless and stateful</h3>
<p>Some processing steps look at one event at a time: filter out tweets without a link, pull out the track id, look up the artist. These are <strong>stateless</strong>, so they’re easy to parallelise and easy to restart.</p>
<p>Counting is different. “Shares per artist in the last minute” needs memory of earlier events: that’s <strong>state</strong>. And because a stream never ends, aggregates are computed over <strong>windows</strong> of time:</p>

<p>Two more ideas matter once there’s state. First, which time? An event has the time it happened (<em>event time</em>) and the time it reached the processor (<em>processing time</em>). They differ whenever something is delayed, and counting by the wrong one puts events in the wrong window. Second, state must survive a crash, so processors periodically <strong>checkpoint</strong> their state and their offsets to durable storage.</p>
<p>Engines differ in how they process: Spark Streaming, which we used, collects events into small <em>micro-batches</em> every few seconds, while engines like Flink process each record as it arrives. Both give you windows, state and checkpoints.</p>
<h3>When things fail</h3>
<p>Failures are where streaming gets hard. Suppose a worker processes an event, updates a count, and crashes before it records that it has finished:</p>
<pre><code class="hljs language-mermaid">sequenceDiagram
  participant K as Kafka
  participant W as Worker
  participant DB as Database
  K->>W: event at offset 41
  W->>DB: count + 1
  Note over W: crashes before saving "done up to 41"
  W->>K: restarted: resume from offset 41
  K->>W: event at offset 41, again
  W->>DB: count + 1 (counted twice)
</code></pre>
<p>Depending on when a consumer saves its position, you get one of three guarantees:</p>
<p>| Guarantee | What can go wrong | How you get it |
| — | — | — |
| At most once | events can be lost | save the offset before processing |
| At least once | events can be counted twice | save the offset after processing |
| Exactly once, in effect | nothing, if done right | at least once, plus writes that are safe to repeat |</p>
<p>In practice, most pipelines choose at least once and make their writes <strong>idempotent</strong>, so that repeating one does no harm. Writing “the count for this artist in this window is 12” is safe to repeat; “add 1 to the count” is not.</p>
<p>Our project had all of these pieces in miniature. Looking back, that’s what makes it useful: I can see which of these ideas it got right and which it skipped.</p>

<p>Each stage had one job:</p>

<p>On paper that’s the textbook architecture: a durable log, a stream processor, a store and a view. In practice every component was a single copy. Kafka had one broker, one partition and replication factor (RF) 1; Spark ran as <code>local[*]</code> on one machine; Cassandra was a single node with replication factor 1. That’s fine for a demo. It also means none of the properties we chose these tools for were actually switched on.</p>
<h2>Five things a stream has to get right</h2>
<h3>1. Know where you resume after a restart</h3>
<p>A batch job that crashes can simply run again. A stream that crashes has to know where it stopped. Our Spark job read Kafka directly but never saved its offsets, so after a restart it started from the latest message. Anything that arrived while it was down was silently skipped. Kafka still held those tweets; we had just lost track of where we were in them.</p>
<p>The fix is to checkpoint offsets together with the processing state, and restart from the checkpoint rather than from “now”.</p>
<h3>2. Make writes idempotent</h3>
<p>The Cassandra table looked like this:</p>
<pre><code class="hljs language-sql"><span class="hljs-keyword">CREATE TABLE</span> artistshare (
  created_at <span class="hljs-type">timestamp</span>, artist text, count <span class="hljs-type">int</span>,
  <span class="hljs-keyword">PRIMARY KEY</span> (artist, created_at)
);
</code></pre>
<p>Each tweet was written as a row with <code>count = 1</code>, keyed by artist and by time to the second. In Cassandra, writing a row with an existing primary key overwrites it. If two people shared the same artist within the same second, the second write replaced the first.</p>

<p>The general lesson is that a streaming sink must produce the same result no matter how many times a record arrives or how records collide. Streams deliver <em>at least once</em> after any failure, so writes need to be idempotent. Here that means aggregating in the stream and writing one count per <code>(window, artist)</code>, which is safe to overwrite, or keying raw rows by tweet id.</p>

<p>Tweets don’t arrive in order. A slow producer, a Kafka backlog or a Spark restart can deliver a tweet minutes late, and by then its minute may already have scrolled out of the window. A stream processor can handle this properly. It groups by the event’s own time, and a <em>watermark</em> says how long to wait for late events before closing a window. That turns “the last 60 minutes” into a definition the pipeline enforces, instead of whatever happened to arrive by the time the dashboard asked.</p>
<h3>4. Keep slow calls off the hot path</h3>
<p>For every tweet, Spark made a blocking HTTP call to the Spotify API. That puts an external service’s latency and rate limits directly on the stream. If Spotify slowed down, the whole batch slowed down; if a call failed, the code returned <code>None</code> and the record was filtered out without being counted.</p>
<p>The same few thousand tracks get shared again and again, so a cache in front of the API would absorb most lookups. The remaining calls can run asynchronously with a rate limiter. Failures shouldn’t vanish: they belong on a <em>dead-letter topic</em>, where they can be counted, inspected and replayed once the cause is fixed.</p>
<h3>5. Decide what one event is</h3>
<p>Every filter in a stream quietly decides what counts:</p>
<ul>
<li><strong>Language:</strong> only English tweets, as detected by Twitter.</li>
<li><strong>First link, first artist:</strong> a tweet sharing two tracks counted once, and a collaboration counted only for whoever Spotify listed first.</li>
<li><strong>Tracks only:</strong> albums and playlists were dropped.</li>
<li><strong>No tweet id:</strong> a retweet was indistinguishable from an original share, and there was no way to remove duplicates.</li>
</ul>
<p>None of these is wrong on its own, but each changes the chart, and none was visible on the page. In a stream, what counts as one event shapes everything downstream, so I’d write that decision down and put a counter on every filter.</p>

<ul>
<li><strong>Ingest:</strong> two small, stateless services hold the Twitter connection, reconnect with backoff, and keep the tweet id. The id is what makes deduplication and idempotent writes possible later.</li>
<li><strong>Kafka:</strong> three brokers with replication factor 3, so losing a machine loses no data. Six partitions let several stream workers read in parallel.</li>
<li><strong>Stream processor:</strong> Flink or Spark Structured Streaming, running several workers. This is where the five fixes live: deduplicate by tweet id, extract every track and every artist, enrich through the cache, window by event time with a watermark, and count per window and artist.</li>
<li><strong>Checkpoints:</strong> processing state and Kafka offsets are saved together to object storage, so a restart resumes exactly where it stopped.</li>
<li><strong>Dead-letter topic:</strong> failed lookups are kept, counted and replayable instead of dropped.</li>
<li><strong>Cassandra:</strong> three nodes with replication factor 3, storing one row per <code>(window, artist)</code>. Rewriting a count is harmless, so replays can’t corrupt it.</li>
<li><strong>Serving:</strong> a small query API caches the current top 20 and pushes updates to the dashboard, instead of every open browser running its own <code>GROUP BY</code> every five seconds.</li>
<li><strong>Metrics:</strong> consumer lag says whether the stream is keeping up; drop counters by reason say how much of the stream the chart actually represents.</li>
</ul>
<p>Looking at that list, the extra machines matter less than the things that make results repeatable: saved offsets, idempotent writes, event time and counted drops. We could have done all four on one laptop.</p>
