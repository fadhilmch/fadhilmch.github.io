1e:T2871,<p>A café has a small admin page for its online menu. Rina opens the iced latte and changes the price from 30 to 32. Budi opened the same item a minute earlier. He marks it as sold out and saves. His form sends the whole item back, including the price it showed him: 30.</p>
<p>Both saves succeed. The latte is now sold out at 30, and Rina’s price change is gone. Nobody saw an error.</p>
<p>This is called a <em>lost update</em>. HTTP has a fix for it built in, using a header most people only know from caching: the ETag. Rina and Budi are made up.</p>

<h2>What an ETag is</h2>
<p>An ETag is a short string the server attaches to a response to name that version of the resource:</p>
<pre><code class="hljs language-http">HTTP/1.1 200 OK
ETag: "v2"

{"name": "Iced latte", "price": 32, "available": true}
</code></pre>
<p>What goes inside the quotes is up to the server: a version number, a hash of the content, a revision ID. The only rule is that when the data changes, the ETag changes. The client doesn’t need to understand it. It keeps the value and sends it back later, in one of two headers:</p>
<ul>
<li><code>If-None-Match: "v2"</code> on a read: “only send it if it’s no longer v2.”</li>
<li><code>If-Match: "v2"</code> on a write: “only save this if it’s still v2.”</li>
</ul>
<h2>Reads: don’t send me what I already have</h2>
<p>The customer-facing menu app asks for the menu every time someone opens it. Most of the time the menu hasn’t changed. With an ETag, the app sends back the one it got last time:</p>
<pre><code class="hljs language-http">GET /menu
If-None-Match: "v2"
</code></pre>
<p>If the menu is still at <code>v2</code>, the server answers <code>304 Not Modified</code> with no body, and the app uses its cached copy. If it changed, the app gets a normal <code>200</code> with the new menu and a new ETag. You still make the request, but most of the time almost nothing comes back.</p>
<h2>Writes: don’t overwrite what I haven’t seen</h2>
<p>Back to Budi. His page loaded the latte at <code>v1</code>, so his save says so:</p>
<pre><code class="hljs language-http">PUT /menu/iced-latte
If-Match: "v1"

{"name": "Iced latte", "price": 30, "available": false}
</code></pre>
<p>The server is at <code>v2</code> now, because Rina saved first. The ETags don’t match, so it refuses:</p>
<pre><code class="hljs language-http">HTTP/1.1 412 Precondition Failed
</code></pre>
<p>Nothing is written. Budi’s page can tell him someone else changed the item, reload it, show him the new price and let him mark it sold out again. This time his save is built on <code>v2</code>.</p>
<p>This pattern is called <em>optimistic concurrency control</em>. Nobody locks the item while editing. You assume conflicts are rare and check at the moment you write. Locking an edit page doesn’t work well on the web anyway: people open a tab and go for lunch.</p>
<h2>The check and the write must be one step</h2>
<p>The obvious server code still has a race:</p>
<pre><code class="hljs language-python">item = db.get(item_id)
<span class="hljs-keyword">if</span> request.headers[<span class="hljs-string">"If-Match"</span>] != item.etag:
    <span class="hljs-keyword">return</span> <span class="hljs-number">412</span>
db.save(item_id, new_data)  <span class="hljs-comment"># another save can sneak in between get and save</span>
</code></pre>
<p>Two requests with the same ETag can both pass the check before either one saves. The fix is to let the database compare and write in one statement:</p>
<pre><code class="hljs language-sql"><span class="hljs-keyword">UPDATE</span> menu_items
<span class="hljs-keyword">SET</span> price <span class="hljs-operator">=</span> <span class="hljs-number">30</span>, available <span class="hljs-operator">=</span> <span class="hljs-literal">false</span>, version <span class="hljs-operator">=</span> version <span class="hljs-operator">+</span> <span class="hljs-number">1</span>
<span class="hljs-keyword">WHERE</span> id <span class="hljs-operator">=</span> <span class="hljs-string">'iced-latte'</span> <span class="hljs-keyword">AND</span> version <span class="hljs-operator">=</span> <span class="hljs-number">1</span>;
</code></pre>
<p>If it updates zero rows, the version moved, so you return 412. If it updates one row, return 200 and the new ETag, <code>"v3"</code>, so the client’s next save doesn’t fail against its own change.</p>
<h2>Where this shows up in ML systems</h2>
<p>ML systems move around large files and small pointers to them. ETags help with both.</p>
<p><strong>Caching model weights.</strong> Model files can be gigabytes, and you don’t want to download them again every time a job starts. The Hugging Face Hub client checks the file’s ETag before downloading. If it matches the copy already in the local cache, it skips the download. It’s the same <code>304</code> idea applied to model weights. Object stores like S3 and Google Cloud Storage return ETags on objects too, so a model server that polls for a new model can compare ETags and only reload when the file has changed.</p>
<p><strong>Promoting a model.</strong> Many setups have a small pointer that serving reads to find the current model, for example a <code>production.json</code> file in a bucket that says <code>{"model": "v41"}</code>. Now two training pipelines finish around the same time. Pipeline A trained on newer data and writes <code>v42</code>. Pipeline B started earlier, is slower and writes <code>v41</code> a few seconds later. B wins, and production quietly goes back to the older model. That’s the menu problem again.</p>
<p>Conditional writes fix it the same way. Each pipeline reads the pointer, decides whether its model is better, and writes back only if the pointer hasn’t moved since it read it. S3 supports <code>If-Match</code> on writes, and Google Cloud Storage has the same check through generation numbers (<code>ifGenerationMatch</code>). If the write fails, the pipeline reads the pointer again and compares itself with the model that’s there now, instead of blindly replacing it.</p>
<p>The same applies to anything several jobs update: a shared eval leaderboard, a “best checkpoint so far” file, or a feature definition two teams edit.</p>
<h2>A few things to watch</h2>
<ul>
<li><strong>Make <code>If-Match</code> required.</strong> A client that leaves it out still gets last-write-wins. A server can reject unconditional writes with <code>428 Precondition Required</code>.</li>
<li><strong>Don’t retry a 412 automatically.</strong> Sending the same data again with the new ETag just overwrites the other change with extra steps. A 412 means someone, a person or some code, has to look at the new version first.</li>
<li><strong>Watch for weak ETags.</strong> An ETag like <code>W/"v2"</code> is <em>weak</em>, and <code>If-Match</code> never matches a weak one. Some servers turn strong ETags into weak ones, for example nginx when it compresses a response. If every save fails with 412, check for the <code>W/</code> first.</li>
<li><strong>Some data doesn’t need it.</strong> A view counter should be <code>SET views = views + 1</code> in the database. Two increments can’t conflict. Data with a single writer doesn’t need it either.</li>
</ul>
<p>For anything that two people or two jobs can edit, a version column, one header and a 412 handler are enough to stop lost updates.</p>
