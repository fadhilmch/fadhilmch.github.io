22:Tddb0,<p>Say a user asks a chatbot: “How do I fix VPN error 809?” One chunk in the knowledge base is titled “Error 809: VPN blocked by the firewall”. Another is a long VPN setup guide that never mentions 809. A third is about error 806, a different problem with a similar number.</p>
<p>Keyword search finds the first chunk easily. “809” is a rare word, and that chunk contains it. Vector search compares meaning instead of words. To an embedding model, 806 and 809 can look almost the same, so the wrong error page may come first.</p>
<p>Now another user writes: “my laptop can’t reach the office network from home”. No chunk uses those words, so keyword search finds little. Vector search still finds the VPN guide, because the meaning is close.</p>
<p>Many RAG systems run both searches and merge the two result lists. This is called <strong>hybrid search</strong>. The multi-agent RAG chatbot I work on uses Azure AI Search in hybrid mode, with a reranker on top. I’ll explain how each of these parts works with one running example. Then I cover what caused us the most trouble, which was none of them. It was the metadata filter that runs before the search starts. I’ll leave out index sizes and numbers that aren’t mine to share.</p>
<h2>Keyword search: BM25</h2>
<p>Keyword search, also called lexical or full-text search, matches the words of the query against the words of each chunk. The usual scoring function is <strong>BM25</strong>, which comes out of the probabilistic relevance framework described by Robertson and Zaragoza [1]. Azure AI Search uses it for full-text queries [5].</p>
<p>BM25 scores each query term in each chunk and adds the scores up. Three things decide a term’s score. The first is <strong>term frequency</strong>: how often the term appears in the chunk. More is better, but each extra mention adds less than the one before. The second is <strong>inverse document frequency</strong> (IDF): how rare the term is in the whole index. A rare term tells you more than a common one. The third is <strong>length normalization</strong>. A long chunk matches more words by chance, so BM25 scales term frequency down for chunks that are longer than average.</p>

<p>One detail is easy to miss. Azure AI Search splits an index into shards and, by default, computes these statistics per shard. Two near-identical chunks in different shards can then get different scores [5]. Our search call sets <code>scoringStatistics</code> to <code>global</code>, so IDF covers the whole index. It also passes a session id derived from the query, so all searches for one question try to use the same replica. The goal is an order that is stable from run to run, because that order is what the reranker receives.</p>
<h3>Where keyword search fails</h3>
<p>Keyword search needs the same words in the query and the chunk. A paraphrase, a synonym or another language scores zero. Acronyms are a case we hit in practice. A user types “WFH” and the document says “work from home”, or the other way around.</p>
<p>So before the query reaches search, the chatbot expands known acronyms from a small glossary. The query keeps both forms, for example “WFH (Work From Home)”, so keyword search can match either one. The glossary is keyed by acronym, then country, then language, because one acronym can mean different things in different countries. The model that rewrites the query is told not to expand acronyms, so this deterministic step is the only place it happens.</p>
<h2>Vector search: embeddings and nearest neighbours</h2>
<p>An <strong>embedding</strong> model turns a piece of text into a vector, a list of a few hundred or a few thousand numbers. Texts with similar meaning get vectors that point in similar directions. Closeness is usually measured with cosine similarity. At query time you embed the query and look for the chunk vectors nearest to it.</p>
<p>Comparing the query with every chunk is exact, but slow for a large index. So vector search engines use <strong>approximate nearest neighbour</strong> (ANN) search. The common algorithm is <strong>HNSW</strong> (Hierarchical Navigable Small World), from Malkov and Yashunin [2]. It builds a stack of graphs. The top layer has few points with long links. Each lower layer has more points with shorter links. A search starts at the top, moves greedily towards the query, then drops a layer and repeats. The paper reports logarithmic scaling with the size of the index. The result is approximate, so now and then the true nearest chunk is missed. Azure AI Search uses HNSW for its vector indexes [10].</p>
<p>In our call, the search service embeds the query itself and asks for the 50 nearest chunks.</p>
<p>Vector search is good at what keyword search misses: paraphrases, synonyms and, with a multilingual model, questions in a different language from the document. It is weaker on exact tokens such as error codes, product names, internal acronyms and numbers. Anthropic’s write-up on contextual retrieval puts it plainly: embedding models “can miss crucial exact matches”, and BM25 finds the specific string [11].</p>
<p>It also isn’t a safe default on its own. The BEIR benchmark tested retrievers on domains they weren’t trained for. It found that “BM25 is a robust baseline”, and that dense retrievers have “considerable room for improvement” in how they generalize [4]. An off-the-shelf embedding model reading your company’s documents is out of domain too.</p>
<h2>Hybrid search: merging two ranked lists</h2>
<p>You can’t merge the two lists by adding scores. A BM25 score has no upper limit, while a cosine score in Azure lies between 0.333 and 1 [7]. A sum would be decided by whichever scale happens to be larger.</p>

<p>RRF isn’t the only option. Azure lets you give a vector query a weight, which multiplies its part of the score [7]. And when every list is scored on the same scale, for example by the same reranker, keeping each chunk’s best score can work better than fusing ranks. I compared the two for multilingual queries in <a href="/posts/tuning-retrieval-for-multilingual-rag/">an earlier post</a>.</p>
<h2>A reranker on top</h2>
<p>Embeddings are fast because each chunk is embedded once, without ever seeing the query. A <strong>reranker</strong> reads the query and one candidate chunk together and scores how well they match. That is more accurate, and much slower, so it only runs on the top results of the first search. Nogueira and Cho showed early on that BERT, fine-tuned for this, works well as a passage reranker [14].</p>
<p>In Azure, this step is the semantic ranker [8]. It takes the top 50 results of the BM25 or RRF ranking and gives each a score from 0 to 4. A 4 answers the question completely, a 2 is “somewhat relevant” and a 0 is irrelevant. Microsoft only says it uses multilingual models adapted from Bing. Two limits matter in practice. The reranker only reorders what it receives. It “can’t rerun the query over the entire corpus”, so a chunk that missed the top 50 stays missed. And the score distribution can shift a little between runs and model updates, so the documentation warns against fine-grained thresholds.</p>
<p>We drop chunks below a threshold on the reranker score, so the model reads fewer, better chunks. My earlier post has the numbers on what the reranker did for us: recall barely moved, while the right page moved nearer the top.</p>
<h2>Our setup, and how it got there</h2>
<p>The first version of the chatbot used Azure’s agentic retrieval. In that managed feature, a language model plans the sub-queries and the service runs them. We replaced it with our own query planning and plain search calls. One reason was language: we couldn’t make the agentic version search in each country’s languages. In our offline comparison, the plain version found more of the right documents, ran about six times faster and cost about a tenth as much per question.</p>
<p>The first replacement sent a keyword query with the semantic reranker on top, and no vector query. A later change by a teammate added the vector query to the same request, which made it hybrid. Here is the shape of the call today, simplified:</p>
<pre><code class="hljs language-python">results = <span class="hljs-keyword">await</span> client.search(
    search_text=query,                      <span class="hljs-comment"># BM25 side</span>
    vector_queries=[VectorizableTextQuery(  <span class="hljs-comment"># vector side, embedded by the service</span>

    <span class="hljs-built_in">filter</span>=filter_expression,               <span class="hljs-comment"># runs before both</span>

<h2>The filter runs first</h2>
<p>Each chunk in our index carries metadata: a country, a region and a list of cities. The chatbot extracts the geography from the question and builds an OData filter from it. For a question about Sweden, the filter looks like this:</p>
<pre><code class="hljs language-text">((country eq 'se' or country eq 'sweden') and (city/any(c: c eq 'common')))
  or region eq 'global'
</code></pre>
<p>A <strong>filter</strong> is a yes or no test on each chunk. It has no score and no ranking. In Azure, a text filter only succeeds on an exact match, and string comparisons are case-sensitive [9]. For a keyword query, the filter runs before the search. For a vector query, the default on newer indexes is to apply it during the graph search, so you still get <span class="katex"><span class="katex-mathml"><math xmlns="http://www.w3.org/1998/Math/MathML"><semantics><mrow><mi>k</mi></mrow><annotation encoding="application/x-tex">k</annotation></semantics></math></span><span class="katex-html" aria-hidden="true"><span class="base"><span class="strut" style="height:0.6944em;"></span><span class="mord mathnormal" style="margin-right:0.0315em;">k</span></span></span></span> results if that many pass [10].</p>
<p>This makes the filter a quiet place to fail. If it removes the right chunk, no ranking can bring it back. Nothing throws an error either. The search still returns ten chunks, the reranker still scores them, and the model writes a fluent answer from the wrong sources. We had four such bugs, each in a different part of the filter:</p>

<p>I fixed the first one with an alias table, marked as temporary. A teammate fixed the second and the third. The fourth was found by a checker.</p>
<p>None of these showed up as an error. So I built an index quality checker that runs on a schedule against each environment. It doesn’t copy the filter rules. It calls the real filter builder for every location a question can carry and reads the values back out of the generated filter. Then it checks that every document can be reached by the filter for its own country. It also reports when an alias in the temporary table no longer matches any document, so the alias can be deleted. The checker found the fourth bug, and it would catch a new spelling like the first one. Each search span in our traces also records the exact filter it used, so a wrong answer can be traced back to its filter.</p>
<h2>Chunks are not documents</h2>
<p>Search returns chunks, and one document is often split into several. One chunk of a file can pass a later relevance check while another is dropped. Our feedback triage once placed one file in three sections of the same report: “never retrieved”, “removed by the relevance check” and “used in the answer”. Each section was right about one chunk. Collapse chunks to a document identity before you count or report anything.</p>
<h2>Things to watch</h2>
<ul>
<li>If users type codes, product names or acronyms, keep a keyword side. Check how the analyzer splits tokens like “R&#x26;D” or “v2.1”.</li>
<li>Don’t add BM25 scores and cosine similarities. Fuse ranks, or normalize the scores first.</li>
<li>The reranker only reorders the top 50. If the right chunk is at position 80, the reranker can’t save it.</li>
<li>Test that every document can be reached by the filter for its own scope. Watch case, spellings, empty lists and clauses that a refactor might drop.</li>
</ul>
<h2>What I would try next</h2>
<p>These are ideas from the documentation and from others’ work. I haven’t measured them on our system.</p>
<ul>
<li>Add context to each chunk. Anthropic has a model write a short note that places each chunk in its document, and indexes it with the chunk for both BM25 and embeddings. With reranking on top, they report 67% fewer top-20 retrieval failures [11].</li>
<li>Move the glossary into a synonym map. Azure can expand query terms from a synonym map on a field [13]. The catch for us is that a field has only one map, and our acronyms differ by country.</li>
<li>Make filters ignore case. A normalizer on the filterable fields does this [9], which fixes the whole class of bug instead of one call site.</li>
<li>Tune the vector weight on a golden set, instead of leaving the default.</li>
</ul>
<p>If you are building search for a RAG chatbot, start with hybrid search and a reranker, and evaluate it on your own questions. Then spend as much care on the filter as on the ranking, and add a test that every document can be reached by the filter meant to find it.</p>
