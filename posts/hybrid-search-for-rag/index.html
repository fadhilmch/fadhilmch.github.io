Keyword search, vector search, and the filter that runs first

How BM25 and vector search each find chunks for a RAG chatbot, how reciprocal rank fusion merges the two lists, what a reranker adds on top, and why our quietest retrieval bugs were in the metadata filter that runs before all of them.

Agents & LLMsData & exploration

Say a user asks a chatbot: “How do I fix VPN error 809?” One chunk in the knowledge base is titled “Error 809: VPN blocked by the firewall”. Another is a long VPN setup guide that never mentions 809. A third is about error 806, a different problem with a similar number.

Keyword search finds the first chunk easily. “809” is a rare word, and that chunk contains it. Vector search compares meaning instead of words. To an embedding model, 806 and 809 can look almost the same, so the wrong error page may come first.

Now another user writes: “my laptop can’t reach the office network from home”. No chunk uses those words, so keyword search finds little. Vector search still finds the VPN guide, because the meaning is close.

Many RAG systems run both searches and merge the two result lists. This is called hybrid search. The multi-agent RAG chatbot I work on uses Azure AI Search in hybrid mode, with a reranker on top. I’ll explain how each of these parts works with one running example. Then I cover what caused us the most trouble, which was none of them. It was the metadata filter that runs before the search starts. I’ll leave out index sizes and numbers that aren’t mine to share.

Keyword search: BM25

Keyword search, also called lexical or full-text search, matches the words of the query against the words of each chunk. The usual scoring function is BM25, which comes out of the probabilistic relevance framework described by Robertson and Zaragoza [1]. Azure AI Search uses it for full-text queries [5].

BM25 scores each query term in each chunk and adds the scores up. Three things decide a term’s score. The first is term frequency: how often the term appears in the chunk. More is better, but each extra mention adds less than the one before. The second is inverse document frequency (IDF): how rare the term is in the whole index. A rare term tells you more than a common one. The third is length normalization. A long chunk matches more words by chance, so BM25 scales term frequency down for chunks that are longer than average.

score(q,d)=∑t∈qIDF(t)⋅f(t,d) (k1+1)f(t,d)+k1(1−b+b⋅∣d∣avgdl)\text{score}(q, d) = \sum_{t \in q} \text{IDF}(t) \cdot \frac{f(t,d)\,(k_1 + 1)}{f(t,d) + k_1 \left(1 - b + b \cdot \frac{|d|}{\text{avgdl}}\right)}score(q,d)=t∈q∑​IDF(t)⋅f(t,d)+k1​(1−b+b⋅avgdl∣d∣​)f(t,d)(k1​+1)​

Here f(t,d)f(t,d)f(t,d) is how often term ttt appears in chunk ddd, ∣d∣|d|∣d∣ is the chunk’s length and avgdl is the average length. k1k_1k1​ controls how fast term frequency saturates, and bbb controls how much length matters. Azure’s defaults are k1=1.2k_1 = 1.2k1​=1.2 and b=0.75b = 0.75b=0.75 [6]. The exact IDF formula differs a little between engines. The example below uses ln⁡(1+N−nt+0.5nt+0.5)\ln\left(1 + \frac{N - n_t + 0.5}{n_t + 0.5}\right)ln(1+nt​+0.5N−nt​+0.5​), where NNN is the number of chunks and ntn_tnt​ is how many contain the term.

Take an index of 1,000 chunks with an average length of 100 words. “vpn” appears in 200 chunks, “error” in 300, and “809” in only 3. That gives an IDF of 1.61 for “vpn”, 1.20 for “error” and 5.66 for “809”. Now score three chunks for the query “vpn error 809”:

Chunk Length Matching terms BM25 score
A: "Error 809: VPN blocked by the firewall" 50 vpn 1, error 1, 809 1 10.6
C: "Error codes, full list" 200 error 4, 809 1 5.8
B: "VPN setup guide" 300 vpn 6 2.4

The rare term does most of the work. “809” alone gives chunk A 7.1 of its 10.6 points. Chunk B says “VPN” six times and still gets only 2.4. With k1=1.2k_1 = 1.2k1​=1.2, one term can never add more than 2.2 times its IDF, and B’s length pulls it further down.

One detail is easy to miss. Azure AI Search splits an index into shards and, by default, computes these statistics per shard. Two near-identical chunks in different shards can then get different scores [5]. Our search call sets scoringStatistics to global, so IDF covers the whole index. It also passes a session id derived from the query, so all searches for one question try to use the same replica. The goal is an order that is stable from run to run, because that order is what the reranker receives.

Where keyword search fails

Keyword search needs the same words in the query and the chunk. A paraphrase, a synonym or another language scores zero. Acronyms are a case we hit in practice. A user types “WFH” and the document says “work from home”, or the other way around.

So before the query reaches search, the chatbot expands known acronyms from a small glossary. The query keeps both forms, for example “WFH (Work From Home)”, so keyword search can match either one. The glossary is keyed by acronym, then country, then language, because one acronym can mean different things in different countries. The model that rewrites the query is told not to expand acronyms, so this deterministic step is the only place it happens.

Vector search: embeddings and nearest neighbours

An embedding model turns a piece of text into a vector, a list of a few hundred or a few thousand numbers. Texts with similar meaning get vectors that point in similar directions. Closeness is usually measured with cosine similarity. At query time you embed the query and look for the chunk vectors nearest to it.

Comparing the query with every chunk is exact, but slow for a large index. So vector search engines use approximate nearest neighbour (ANN) search. The common algorithm is HNSW (Hierarchical Navigable Small World), from Malkov and Yashunin [2]. It builds a stack of graphs. The top layer has few points with long links. Each lower layer has more points with shorter links. A search starts at the top, moves greedily towards the query, then drops a layer and repeats. The paper reports logarithmic scaling with the size of the index. The result is approximate, so now and then the true nearest chunk is missed. Azure AI Search uses HNSW for its vector indexes [10].

In our call, the search service embeds the query itself and asks for the 50 nearest chunks.

Vector search is good at what keyword search misses: paraphrases, synonyms and, with a multilingual model, questions in a different language from the document. It is weaker on exact tokens such as error codes, product names, internal acronyms and numbers. Anthropic’s write-up on contextual retrieval puts it plainly: embedding models “can miss crucial exact matches”, and BM25 finds the specific string [11].

It also isn’t a safe default on its own. The BEIR benchmark tested retrievers on domains they weren’t trained for. It found that “BM25 is a robust baseline”, and that dense retrievers have “considerable room for improvement” in how they generalize [4]. An off-the-shelf embedding model reading your company’s documents is out of domain too.

Hybrid search: merging two ranked lists

You can’t merge the two lists by adding scores. A BM25 score has no upper limit, while a cosine score in Azure lies between 0.333 and 1 [7]. A sum would be decided by whichever scale happens to be larger.

Reciprocal rank fusion (RRF) avoids the problem by ignoring scores and using only ranks. Cormack, Clarke and Büttcher proposed it in 2009 [3]. Each chunk gets one term for every list it appears in:

RRF(d)=∑r∈R1k+r(d)\text{RRF}(d) = \sum_{r \in R} \frac{1}{k + r(d)}RRF(d)=r∈R∑​k+r(d)1​

Here r(d)r(d)r(d) is the chunk’s rank in list rrr. The constant kkk softens the gap between rank 1 and rank 2. The paper fixed k=60k = 60k=60 in a pilot run and found that the exact value “was not critical”. Azure AI Search uses the same formula for hybrid queries, and its documentation names 60 as a good value [7].

Here is a worked example for our VPN query, with k=60k = 60k=60. Chunk A is the one that answers it.

Chunk Keyword rank Vector rank RRF score
A: Error 809: VPN blocked 1 3 1/61 + 1/63 = 0.0323
B: VPN setup guide 4 1 1/64 + 1/61 = 0.0320
D: Proxy error 806 3 4 1/63 + 1/64 = 0.0315
F: Laptop setup checklist 5 5 1/65 + 1/65 = 0.0308
C: Error codes, full list 2 none 1/62 = 0.0161
E: Home network tips none 2 1/62 = 0.0161

A wins, by a small margin. And F, which is 5th in both lists, ends up far above C, which is 2nd in one list. RRF rewards agreement between the lists. That is often what you want. It also means a mediocre chunk that both searches return can push out a good one that only one search found.

Try it below. Move kkk down towards 0 and watch the single-list chunks rise. Switch off one list and the fused order becomes that list’s order.

        RRF isn’t the only option. Azure lets you give a vector query a weight, which multiplies its part of the score [7]. And when every list is scored on the same scale, for example by the same reranker, keeping each chunk’s best score can work better than fusing ranks. I compared the two for multilingual queries in an earlier post.

        A reranker on top

        Embeddings are fast because each chunk is embedded once, without ever seeing the query. A reranker reads the query and one candidate chunk together and scores how well they match. That is more accurate, and much slower, so it only runs on the top results of the first search. Nogueira and Cho showed early on that BERT, fine-tuned for this, works well as a passage reranker [14].

        In Azure, this step is the semantic ranker [8]. It takes the top 50 results of the BM25 or RRF ranking and gives each a score from 0 to 4. A 4 answers the question completely, a 2 is “somewhat relevant” and a 0 is irrelevant. Microsoft only says it uses multilingual models adapted from Bing. Two limits matter in practice. The reranker only reorders what it receives. It “can’t rerun the query over the entire corpus”, so a chunk that missed the top 50 stays missed. And the score distribution can shift a little between runs and model updates, so the documentation warns against fine-grained thresholds.

        We drop chunks below a threshold on the reranker score, so the model reads fewer, better chunks. My earlier post has the numbers on what the reranker did for us: recall barely moved, while the right page moved nearer the top.

        Our setup, and how it got there

        The first version of the chatbot used Azure’s agentic retrieval. In that managed feature, a language model plans the sub-queries and the service runs them. We replaced it with our own query planning and plain search calls. One reason was language: we couldn’t make the agentic version search in each country’s languages. In our offline comparison, the plain version found more of the right documents, ran about six times faster and cost about a tenth as much per question.

        The first replacement sent a keyword query with the semantic reranker on top, and no vector query. A later change by a teammate added the vector query to the same request, which made it hybrid. Here is the shape of the call today, simplified:

        results = await client.search(
    search_text=query,                      # BM25 side
    vector_queries=[VectorizableTextQuery(  # vector side, embedded by the service
        text=query, fields="content_vector", k_nearest_neighbors=50,
    )],
    filter=filter_expression,               # runs before both
    query_type="semantic",                  # reranker on the fused top 50
    semantic_configuration_name=semantic_config,
    scoring_statistics="global",            # IDF over the whole index
    session_id=session_id,                  # same replica for one question
    top=top,
)
chunks = [r for r in results if r["@search.reranker_score"] >= threshold]

        One question can fan out into several such calls, one per topic and language.

        The filter runs first

        Each chunk in our index carries metadata: a country, a region and a list of cities. The chatbot extracts the geography from the question and builds an OData filter from it. For a question about Sweden, the filter looks like this:

        ((country eq 'se' or country eq 'sweden') and (city/any(c: c eq 'common')))
  or region eq 'global'

        A filter is a yes or no test on each chunk. It has no score and no ranking. In Azure, a text filter only succeeds on an exact match, and string comparisons are case-sensitive [9]. For a keyword query, the filter runs before the search. For a vector query, the default on newer indexes is to apply it during the graph search, so you still get kkk results if that many pass [10].

        This makes the filter a quiet place to fail. If it removes the right chunk, no ranking can bring it back. Nothing throws an error either. The search still returns ten chunks, the reranker still scores them, and the model writes a fluent answer from the wrong sources. We had four such bugs, each in a different part of the filter:

        What went wrong Effect
        Documents for one country were tagged with two spellings of its name. The filter only sent the standard spelling. Most of that country's documents could not be found.
        The filter sent an upper-case country code, and the index held lower-case values. That clause never matched. The country name in the same filter still did.
        A refactor for city filtering dropped the region clause. Documents written for a whole region were not found for a question about one of its countries.
        A chunk with an empty city list was tested with city/any(c: c eq 'common'). any over an empty list is false [12], so dozens of documents for one office could never be found.

        I fixed the first one with an alias table, marked as temporary. A teammate fixed the second and the third. The fourth was found by a checker.

        None of these showed up as an error. So I built an index quality checker that runs on a schedule against each environment. It doesn’t copy the filter rules. It calls the real filter builder for every location a question can carry and reads the values back out of the generated filter. Then it checks that every document can be reached by the filter for its own country. It also reports when an alias in the temporary table no longer matches any document, so the alias can be deleted. The checker found the fourth bug, and it would catch a new spelling like the first one. Each search span in our traces also records the exact filter it used, so a wrong answer can be traced back to its filter.

        Chunks are not documents

        Search returns chunks, and one document is often split into several. One chunk of a file can pass a later relevance check while another is dropped. Our feedback triage once placed one file in three sections of the same report: “never retrieved”, “removed by the relevance check” and “used in the answer”. Each section was right about one chunk. Collapse chunks to a document identity before you count or report anything.

        Things to watch

        • If users type codes, product names or acronyms, keep a keyword side. Check how the analyzer splits tokens like “R&D” or “v2.1”.
        • Don’t add BM25 scores and cosine similarities. Fuse ranks, or normalize the scores first.
        • The reranker only reorders the top 50. If the right chunk is at position 80, the reranker can’t save it.
        • Test that every document can be reached by the filter for its own scope. Watch case, spellings, empty lists and clauses that a refactor might drop.

        What I would try next

        These are ideas from the documentation and from others’ work. I haven’t measured them on our system.

        • Add context to each chunk. Anthropic has a model write a short note that places each chunk in its document, and indexes it with the chunk for both BM25 and embeddings. With reranking on top, they report 67% fewer top-20 retrieval failures [11].
        • Move the glossary into a synonym map. Azure can expand query terms from a synonym map on a field [13]. The catch for us is that a field has only one map, and our acronyms differ by country.
        • Make filters ignore case. A normalizer on the filterable fields does this [9], which fixes the whole class of bug instead of one call site.
        • Tune the vector weight on a golden set, instead of leaving the default.

        If you are building search for a RAG chatbot, start with hybrid search and a reranker, and evaluate it on your own questions. Then spend as much care on the filter as on the ranking, and add a test that every document can be reached by the filter meant to find it.
