3a:T6b74,<p>In June we moved our chatbot’s production environment to a newer model. The pull request changed two lines in each of two config files: the model deployment name and the model name, for UAT and for production. No Python file changed.</p>
<p>It still went to production the same way a code change does. It merged, deployed to UAT, got a version tag and waited for an approval. Then the production deploy copied an image that UAT had already run, and pointed the cluster at it together with the new config. Nothing was built for production.</p>
<p>This post is about that release model. You build the container image once, name it after the commit, and move that exact image from one environment to the next. Everything that differs between environments stays outside the image. This is usually called <strong>image promotion</strong>, or “build once, deploy many”. To roll back, you point back at an older image. I’ll go through how our pipeline does it, where it still falls short, and what an LLM service adds. I’ll leave out the names of registries, repositories and models, which aren’t mine to share.</p>
<h2>A build, a release and a run</h2>
<p>The Twelve-Factor App splits shipping into three stages [1]. The build turns code into an executable bundle. The release combines that build with the config of one deploy. The run starts the release in its environment. Every release has a unique ID and is never changed after it is created. If you need a change, you make a new release.</p>
<p>For a container service, the build is the image. The release is the image plus one environment’s config. In our setup, a release is one commit in a Git repo that Argo CD watches. More on that below.</p>
<p>Why not build again for each environment? Humble and Farley answer it in <em>Continuous Delivery</em>: “Every time you compile the code, you run the risk of introducing some difference” [2]. A rebuild can pick up a newer base image, a newer system package or a different tool version. Then production runs an image nobody tested. They call binaries built for one environment “a very bad practice” [2].</p>
<h2>What our pipeline does</h2>
<p>We have three environments: dev, UAT and production. A deploy goes through three repos. The app repo has small workflows that run tests and start a deploy. A shared repo holds the reusable workflows that do the dispatch. A separate infra repo builds the image, pushes it to the registry and updates the Kubernetes manifests. Argo CD watches the infra repo and applies it to the cluster.</p>

<p>Each environment has its own trigger:</p>
<ul>
<li>A merge into <code>development</code> runs smoke tests, then builds an image and deploys it to dev.</li>
<li>A promotion PR from <code>development</code> into <code>main</code> builds a fresh image from <code>main</code> and deploys it to UAT. A small workflow fills the PR body with the list of commits it carries.</li>
<li>A version tag such as <code>v1.4.0</code> on <code>main</code> deploys to production. A person must approve it in a GitHub environment first. Then the infra repo copies the UAT image into the production registry with <code>az acr import</code> and pins the manifest to it.</li>
</ul>
<p>Before it asks for approval, the production workflow checks that the tagged commit is on <code>main</code> and has an exact version tag.</p>

<h3>Where we stopped short</h3>
<p>Our design record for this, ADR-002, describes a stricter version. It builds once, when code merges into <code>development</code>, and promotes that one image to UAT and then to production. The record still has the status “Proposed”. The workflows went a different way, and UAT gets its own build.</p>
<p>The merge commit is one reason this is hard. A promotion PR into <code>main</code> creates a new commit with a new SHA. The code is the same, but the name is not. So the dev image and the UAT image are two builds with two names.</p>
<p>So in our pipeline, “build once” holds from UAT to production and not from dev to UAT. UAT to production is the step that matters most, because production must run what the testers saw. Two things in our Dockerfile make the second build less risky. The Python base image is pinned by digest, and dependencies come from a lock file with <code>uv sync --frozen</code>. One step still installs system packages without a version, so two builds of the same code can still differ a little.</p>
<p>Microsoft’s guide to image tags makes the same point about git SHAs. It calls a git commit tag “semi-stable”, because a rebuild of the same commit can pick up a new base image [5].</p>
<h2>Name the image after the commit</h2>
<p>Every image is tagged with the 7-character git SHA of the commit it was built from. ADR-001 compared this with semantic versions, build numbers and timestamps. The SHA won because any workflow can compute it from its own checkout. The build and deploy workflows don’t need to pass a version between them. And <code>git show a1b2c3d</code> shows exactly what is running.</p>
<p>Each build also gets a second tag with the environment name, such as <code>:uat</code>. That tag moves on every deploy. It is only there for people browsing the registry. The manifests always pin the SHA tag.</p>
<p>The running app also needs to say what it is. The deploy step writes an <code>APP_VERSION</code> variable into the manifest: the short SHA on dev and UAT, the release tag on production. The app reports it on a <code>/version</code> endpoint and in a response header. We dropped our release tool in June. The version in <code>pyproject.toml</code> is now a fixed <code>0.0.0</code>, and the deploy is the only source of the version.</p>
<p>A tag is still only a name. The Kubernetes documentation says: “Tags can be moved to point to different images, but digests are fixed” [4]. A <strong>digest</strong> is the SHA-256 hash of the image manifest. If a manifest pins <code>app@sha256:...</code>, the cluster runs the same bytes even if someone pushes a new image under the old tag. We pin tags, and they stay fixed by convention. Nothing in the workflows I read locks them.</p>
<h2>Config stays outside the image</h2>
<p>If one image runs everywhere, everything that differs must come from outside: endpoints, model deployment names, index names, log levels and secrets. Twelve-Factor defines config as “everything that is likely to vary between deploys” [1].</p>
<p>Ours lives in the app repo, in one plain YAML file per environment:</p>
<pre><code class="hljs language-yaml"><span class="hljs-comment"># config/uat.yaml (values are placeholders)</span>
<span class="hljs-attr">ENVIRONMENT:</span> <span class="hljs-string">"uat"</span>

</code></pre>
<p>Secrets never go in this file. They live in a key vault, and an <code>ExternalSecret</code> resource in the infra repo pulls them into the cluster.</p>

  k8s/prod/deployment.yaml
<span class="hljs-comment"># also set APP_VERSION=v1.4.0 in the same manifest</span>
yq -i <span class="hljs-string">'.data = load("source/config/prod.yaml")'</span> k8s/prod/configmap.yaml
<span class="hljs-comment"># if the ConfigMap changed, bump an annotation on the pod template</span>
git commit -am <span class="hljs-string">"deploy(prod): app:<span class="hljs-variable">$SHA</span>"</span> &#x26;&#x26; git push   <span class="hljs-comment"># Argo CD syncs from here</span>
</code></pre>
<p>The annotation is needed because a Deployment doesn’t restart its pods when a ConfigMap changes. Helm’s docs show the usual fix: put a checksum of the ConfigMap in the pod template, so a config change also changes the template [6]. Ours writes a timestamp instead, and only when the config changed.</p>
<p>Two of our choices differ from the textbook. First, Twelve-Factor says not to group config into named environments, because that “does not scale cleanly” [1]. We do group it, in three files. With three fixed environments, that has been fine so far.</p>
<p>Second, the config file comes from the same commit as the image. So the image and its config go through review and promotion together. Google’s SRE book describes this option: teams “snapshot and release configuration files alongside their binaries”. It also warns that config read from the head of the main branch “often leads to skew” with what is running [3].</p>
<p>The cost is that every config change needs a commit, a new SHA and a new release. The model change at the top of this post went through UAT and a version tag like any code change. I think that is right for an LLM service. One config line can change the model, and that changes behaviour as much as code does.</p>
<h2>What a version means for an LLM service</h2>
<p>For a plain web service, the image SHA and the config describe most of what runs. An LLM service has more parts that change.</p>
<p>Prompts are code. Ours are TOML files in the image, one per model, picked by the model name in config. So a config change that switches the model needs the prompt file for that model to be in the image already. The image has to ship first, or in the same release.</p>
<p>Deployment names differ between environments. The same model can have one deployment name in dev and another in production. That is why the name is config, and the prompt is picked by model name instead of deployment name.</p>
<p>The knowledge base changes without a deploy. The search index is refreshed on its own schedule, so the same image and config can give a different answer next week. Our <code>/version</code> endpoint returns three fields for this reason:</p>
<pre><code class="hljs language-json"><span class="hljs-punctuation">{</span> <span class="hljs-attr">"version"</span><span class="hljs-punctuation">:</span> <span class="hljs-string">"v1.4.0"</span><span class="hljs-punctuation">,</span> <span class="hljs-attr">"kb_index"</span><span class="hljs-punctuation">:</span> <span class="hljs-string">"docs-live"</span><span class="hljs-punctuation">,</span> <span class="hljs-attr">"kb_version"</span><span class="hljs-punctuation">:</span> <span class="hljs-string">"2026-10-20T03:00:12Z"</span> <span class="hljs-punctuation">}</span>
</code></pre>
<p><code>kb_version</code> is the end time of the indexer’s last run. For evaluation, a request header switches retrieval to a frozen copy of the index, made by a manual workflow. Then <code>/version</code> reports the frozen index and the <code>kb_version</code> it was copied from. An eval score can be tied to one image, one config and one corpus.</p>
<h3>Gates between environments</h3>
<p>Promotion only helps if something checks the image before the next step. Ours, in order:</p>
<ul>
<li>A pull request into <code>development</code> runs unit tests, with no model calls.</li>
<li>A pull request into <code>main</code> runs the full suite, including all the tests that call the model.</li>
<li>Every dev and UAT deploy runs smoke tests first, which include a few real model calls. If they fail, the deploy is skipped.</li>
<li>After a deploy, someone can run a deployment verification test by hand against dev or UAT. It checks health, asks a question, sends feedback, asks a follow-up that depends on the first answer, and sends a malformed request. A model then judges whether the follow-up used the first turn.</li>
<li>Production needs a person to approve it.</li>
</ul>
<p>There is no automated quality score between UAT and production yet. The approval is where a person looks at the evidence.</p>
<h2>Rollback is a git revert</h2>
<p>Every deploy is one commit in the infra repo. That commit changes the image pin, <code>APP_VERSION</code> and the ConfigMap together. So rollback is a <code>git revert</code> of that commit, and Argo CD syncs the cluster back. Our rollback workflow asks for the environment, an optional infra commit, and the word <code>YES</code>.</p>

<p>This is also what Argo CD expects. Its docs say “Rollback cannot be performed against an application with automated sync enabled” [7]. Git is the source of truth, so the undo happens in Git. A side effect is a free deploy log: <code>git log -- k8s/prod/deployment.yaml</code> lists every production release.</p>
<p>A revert only undoes what is in that commit. It doesn’t undo a refreshed knowledge base, or data that the new release wrote in a new shape. If a release changes what the app stores between turns, the older image must still be able to read it, or the rollback breaks open conversations.</p>
<h2>An LLM step in CI should fail soft</h2>
<p>One small story. Our promotion PRs used to start with a generated summary. A workflow step sent the commit list to a hosted model and wrote a short summary into the PR body. At some point the model API began to answer with HTTP 410, <em>Gone</em>.</p>
<p>The step had been written to degrade. On any status other than 200, it wrote one line instead: “AI summary unavailable (HTTP 410). See raw commits below.” So the promotion PRs still opened and deploys were never blocked. However, that line sat at the top of every promotion PR from late August until 22 October. Then we removed the step and kept the plain commit list.</p>
<p>A model call in CI is a call to a service you don’t control. Make it optional, as this one was. But a soft failure is also a quiet one. If nothing reports it, it can stay broken for weeks.</p>
<h2>Things to watch</h2>
<ul>
<li><strong>Environment tags move.</strong> Tags like <code>:uat</code> point somewhere new on every deploy. Never deploy from them.</li>
<li><strong>Short SHAs can clash.</strong> Our infra build named the tag with <code>git rev-parse --short=7</code>, which adds characters when 7 are ambiguous. The promotion cut the full SHA to exactly 7. In the rare case of a clash, the two would disagree.</li>
<li><strong>Tagging a commit UAT never built.</strong> Production copies an existing image. On purpose, a merge into <code>main</code> builds nothing unless it comes from <code>development</code> or a hotfix branch. If you tag one of those, there is nothing to copy, and the promotion fails.</li>
<li><strong>A break-glass path.</strong> We keep a manual workflow that deploys to dev with Helm directly, for when the infra repo or Argo CD is down. That deploy is not in Git. Redeploy through the normal path once it is back.</li>
<li><strong>Moving workflow references.</strong> Our callers use the shared workflows at <code>@v1</code>, a tag that moves with each release of the shared repo. Until July they used <code>@main</code>. GitHub’s hardening guide recommends a full commit SHA, because “a tag can be moved or deleted” [8]. <code>@v1</code> trades some of that safety for getting fixes without editing every caller.</li>
<li><strong>Config ahead of the image.</strong> A config value that needs code the image doesn’t have yet fails at runtime, not at build time. Ship the code first.</li>
</ul>
<h2>What I would try next</h2>
<p>Reading how others do this showed me a few things our pipeline doesn’t do yet.</p>
<ul>
<li><strong>Promote the dev image to UAT.</strong> If <code>main</code> took the exact commit from <code>development</code> instead of a new merge commit, the SHA would stay the same. Then UAT could copy the dev image. Today the promotion PR is merged with a merge commit, so this needs a change in how we merge.</li>
<li><strong>Pin by digest.</strong> Record the digest at build time and pin <code>app@sha256:...</code> in the manifests. The SHA tag can stay for people [4].</li>
<li><strong>Lock deployed tags.</strong> Microsoft’s guide recommends locking every deployed tag, by setting <code>write-enabled</code> to <code>false</code>, as a step in the release pipeline [5].</li>
<li><strong>Build provenance.</strong> SLSA provenance is a record of how an artifact was built: which builder, which inputs and which dependencies [9]. With it, production could check that an image came from our pipeline before it runs.</li>
<li><strong>An eval gate before the tag.</strong> Run the golden set against the frozen index on UAT, and put the scores next to the approval. I wrote about <a href="/posts/golden-datasets-without-the-gold-rush/">golden datasets</a> before.</li>
</ul>
<p>If you run an LLM service on Kubernetes, start with two rules. Tag each image with its commit and never build for production. Then make each deploy one commit that pins the image and its config together, so a rollback is one revert.</p>
