Ship the image you tested: build once, promote, roll back

How we release an LLM chatbot: one image per commit, named after the git SHA, copied to production without a rebuild, with each environment's config kept outside the image. Where our pipeline still rebuilds, what an LLM service adds to a version, and why rollback is a git revert.

ML platformAgents & LLMs

In June we moved our chatbot’s production environment to a newer model. The pull request changed two lines in each of two config files: the model deployment name and the model name, for UAT and for production. No Python file changed.

It still went to production the same way a code change does. It merged, deployed to UAT, got a version tag and waited for an approval. Then the production deploy copied an image that UAT had already run, and pointed the cluster at it together with the new config. Nothing was built for production.

This post is about that release model. You build the container image once, name it after the commit, and move that exact image from one environment to the next. Everything that differs between environments stays outside the image. This is usually called image promotion, or “build once, deploy many”. To roll back, you point back at an older image. I’ll go through how our pipeline does it, where it still falls short, and what an LLM service adds. I’ll leave out the names of registries, repositories and models, which aren’t mine to share.

A build, a release and a run

The Twelve-Factor App splits shipping into three stages [1]. The build turns code into an executable bundle. The release combines that build with the config of one deploy. The run starts the release in its environment. Every release has a unique ID and is never changed after it is created. If you need a change, you make a new release.

For a container service, the build is the image. The release is the image plus one environment’s config. In our setup, a release is one commit in a Git repo that Argo CD watches. More on that below.

Why not build again for each environment? Humble and Farley answer it in Continuous Delivery: “Every time you compile the code, you run the risk of introducing some difference” [2]. A rebuild can pick up a newer base image, a newer system package or a different tool version. Then production runs an image nobody tested. They call binaries built for one environment “a very bad practice” [2].

What our pipeline does

We have three environments: dev, UAT and production. A deploy goes through three repos. The app repo has small workflows that run tests and start a deploy. A shared repo holds the reusable workflows that do the dispatch. A separate infra repo builds the image, pushes it to the registry and updates the Kubernetes manifests. Argo CD watches the infra repo and applies it to the cluster.

Each environment has its own trigger:

  • A merge into development runs smoke tests, then builds an image and deploys it to dev.
  • A promotion PR from development into main builds a fresh image from main and deploys it to UAT. A small workflow fills the PR body with the list of commits it carries.
  • A version tag such as v1.4.0 on main deploys to production. A person must approve it in a GitHub environment first. Then the infra repo copies the UAT image into the production registry with az acr import and pins the manifest to it.

Before it asks for approval, the production workflow checks that the tagged commit is on main and has an exact version tag.

    Where we stopped short

    Our design record for this, ADR-002, describes a stricter version. It builds once, when code merges into development, and promotes that one image to UAT and then to production. The record still has the status “Proposed”. The workflows went a different way, and UAT gets its own build.

    The merge commit is one reason this is hard. A promotion PR into main creates a new commit with a new SHA. The code is the same, but the name is not. So the dev image and the UAT image are two builds with two names.

    So in our pipeline, “build once” holds from UAT to production and not from dev to UAT. UAT to production is the step that matters most, because production must run what the testers saw. Two things in our Dockerfile make the second build less risky. The Python base image is pinned by digest, and dependencies come from a lock file with uv sync --frozen. One step still installs system packages without a version, so two builds of the same code can still differ a little.

    Microsoft’s guide to image tags makes the same point about git SHAs. It calls a git commit tag “semi-stable”, because a rebuild of the same commit can pick up a new base image [5].

    Name the image after the commit

    Every image is tagged with the 7-character git SHA of the commit it was built from. ADR-001 compared this with semantic versions, build numbers and timestamps. The SHA won because any workflow can compute it from its own checkout. The build and deploy workflows don’t need to pass a version between them. And git show a1b2c3d shows exactly what is running.

    Each build also gets a second tag with the environment name, such as :uat. That tag moves on every deploy. It is only there for people browsing the registry. The manifests always pin the SHA tag.

    The running app also needs to say what it is. The deploy step writes an APP_VERSION variable into the manifest: the short SHA on dev and UAT, the release tag on production. The app reports it on a /version endpoint and in a response header. We dropped our release tool in June. The version in pyproject.toml is now a fixed 0.0.0, and the deploy is the only source of the version.

    A tag is still only a name. The Kubernetes documentation says: “Tags can be moved to point to different images, but digests are fixed” [4]. A digest is the SHA-256 hash of the image manifest. If a manifest pins app@sha256:..., the cluster runs the same bytes even if someone pushes a new image under the old tag. We pin tags, and they stay fixed by convention. Nothing in the workflows I read locks them.

    Config stays outside the image

    If one image runs everywhere, everything that differs must come from outside: endpoints, model deployment names, index names, log levels and secrets. Twelve-Factor defines config as “everything that is likely to vary between deploys” [1].

    Ours lives in the app repo, in one plain YAML file per environment:

    # config/uat.yaml (values are placeholders)
ENVIRONMENT: "uat"
LOG_LEVEL: "INFO"
MODEL_DEPLOYMENT_NAME: "chat-primary"
MODEL_FALLBACK_DEPLOYMENT_NAME: "chat-fallback"
AI_SEARCH_INDEX_NAME: "docs-live"
AI_SEARCH_EVAL_INDEX_NAME: "docs-eval-frozen"

    Secrets never go in this file. They live in a key vault, and an ExternalSecret resource in the infra repo pulls them into the cluster.

    At deploy time, the infra workflow copies these values into the environment’s ConfigMap. Here is a simplified sketch of one production deploy, not the exact workflow:

    SHA=e4f5a6b
yq -i ".spec.template.spec.containers[0].image = \"registry.example.com/app:$SHA\"" \
  k8s/prod/deployment.yaml
# also set APP_VERSION=v1.4.0 in the same manifest
yq -i '.data = load("source/config/prod.yaml")' k8s/prod/configmap.yaml
# if the ConfigMap changed, bump an annotation on the pod template
git commit -am "deploy(prod): app:$SHA" && git push   # Argo CD syncs from here

    The annotation is needed because a Deployment doesn’t restart its pods when a ConfigMap changes. Helm’s docs show the usual fix: put a checksum of the ConfigMap in the pod template, so a config change also changes the template [6]. Ours writes a timestamp instead, and only when the config changed.

    Two of our choices differ from the textbook. First, Twelve-Factor says not to group config into named environments, because that “does not scale cleanly” [1]. We do group it, in three files. With three fixed environments, that has been fine so far.

    Second, the config file comes from the same commit as the image. So the image and its config go through review and promotion together. Google’s SRE book describes this option: teams “snapshot and release configuration files alongside their binaries”. It also warns that config read from the head of the main branch “often leads to skew” with what is running [3].

    The cost is that every config change needs a commit, a new SHA and a new release. The model change at the top of this post went through UAT and a version tag like any code change. I think that is right for an LLM service. One config line can change the model, and that changes behaviour as much as code does.

    What a version means for an LLM service

    For a plain web service, the image SHA and the config describe most of what runs. An LLM service has more parts that change.

    Prompts are code. Ours are TOML files in the image, one per model, picked by the model name in config. So a config change that switches the model needs the prompt file for that model to be in the image already. The image has to ship first, or in the same release.

    Deployment names differ between environments. The same model can have one deployment name in dev and another in production. That is why the name is config, and the prompt is picked by model name instead of deployment name.

    The knowledge base changes without a deploy. The search index is refreshed on its own schedule, so the same image and config can give a different answer next week. Our /version endpoint returns three fields for this reason:

    { "version": "v1.4.0", "kb_index": "docs-live", "kb_version": "2026-10-20T03:00:12Z" }

    kb_version is the end time of the indexer’s last run. For evaluation, a request header switches retrieval to a frozen copy of the index, made by a manual workflow. Then /version reports the frozen index and the kb_version it was copied from. An eval score can be tied to one image, one config and one corpus.

    Gates between environments

    Promotion only helps if something checks the image before the next step. Ours, in order:

    • A pull request into development runs unit tests, with no model calls.
    • A pull request into main runs the full suite, including all the tests that call the model.
    • Every dev and UAT deploy runs smoke tests first, which include a few real model calls. If they fail, the deploy is skipped.
    • After a deploy, someone can run a deployment verification test by hand against dev or UAT. It checks health, asks a question, sends feedback, asks a follow-up that depends on the first answer, and sends a malformed request. A model then judges whether the follow-up used the first turn.
    • Production needs a person to approve it.

    There is no automated quality score between UAT and production yet. The approval is where a person looks at the evidence.

    Rollback is a git revert

    Every deploy is one commit in the infra repo. That commit changes the image pin, APP_VERSION and the ConfigMap together. So rollback is a git revert of that commit, and Argo CD syncs the cluster back. Our rollback workflow asks for the environment, an optional infra commit, and the word YES.

    This is also what Argo CD expects. Its docs say “Rollback cannot be performed against an application with automated sync enabled” [7]. Git is the source of truth, so the undo happens in Git. A side effect is a free deploy log: git log -- k8s/prod/deployment.yaml lists every production release.

    A revert only undoes what is in that commit. It doesn’t undo a refreshed knowledge base, or data that the new release wrote in a new shape. If a release changes what the app stores between turns, the older image must still be able to read it, or the rollback breaks open conversations.

    An LLM step in CI should fail soft

    One small story. Our promotion PRs used to start with a generated summary. A workflow step sent the commit list to a hosted model and wrote a short summary into the PR body. At some point the model API began to answer with HTTP 410, Gone.

    The step had been written to degrade. On any status other than 200, it wrote one line instead: “AI summary unavailable (HTTP 410). See raw commits below.” So the promotion PRs still opened and deploys were never blocked. However, that line sat at the top of every promotion PR from late August until 22 October. Then we removed the step and kept the plain commit list.

    A model call in CI is a call to a service you don’t control. Make it optional, as this one was. But a soft failure is also a quiet one. If nothing reports it, it can stay broken for weeks.

    Things to watch

    • Environment tags move. Tags like :uat point somewhere new on every deploy. Never deploy from them.
    • Short SHAs can clash. Our infra build named the tag with git rev-parse --short=7, which adds characters when 7 are ambiguous. The promotion cut the full SHA to exactly 7. In the rare case of a clash, the two would disagree.
    • Tagging a commit UAT never built. Production copies an existing image. On purpose, a merge into main builds nothing unless it comes from development or a hotfix branch. If you tag one of those, there is nothing to copy, and the promotion fails.
    • A break-glass path. We keep a manual workflow that deploys to dev with Helm directly, for when the infra repo or Argo CD is down. That deploy is not in Git. Redeploy through the normal path once it is back.
    • Moving workflow references. Our callers use the shared workflows at @v1, a tag that moves with each release of the shared repo. Until July they used @main. GitHub’s hardening guide recommends a full commit SHA, because “a tag can be moved or deleted” [8]. @v1 trades some of that safety for getting fixes without editing every caller.
    • Config ahead of the image. A config value that needs code the image doesn’t have yet fails at runtime, not at build time. Ship the code first.

    What I would try next

    Reading how others do this showed me a few things our pipeline doesn’t do yet.

    • Promote the dev image to UAT. If main took the exact commit from development instead of a new merge commit, the SHA would stay the same. Then UAT could copy the dev image. Today the promotion PR is merged with a merge commit, so this needs a change in how we merge.
    • Pin by digest. Record the digest at build time and pin app@sha256:... in the manifests. The SHA tag can stay for people [4].
    • Lock deployed tags. Microsoft’s guide recommends locking every deployed tag, by setting write-enabled to false, as a step in the release pipeline [5].
    • Build provenance. SLSA provenance is a record of how an artifact was built: which builder, which inputs and which dependencies [9]. With it, production could check that an image came from our pipeline before it runs.
    • An eval gate before the tag. Run the golden set against the frozen index on UAT, and put the scores next to the approval. I wrote about golden datasets before.

    If you run an LLM service on Kubernetes, start with two rules. Tag each image with its commit and never build for production. Then make each deploy one commit that pins the image and its config together, so a rollback is one revert.
