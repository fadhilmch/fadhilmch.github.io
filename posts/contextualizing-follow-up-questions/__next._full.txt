22:T5fac,<p>An employee asks an internal chatbot: “How do I request a new laptop in Sweden?” The bot searches the company documents and answers. Then the employee types: “And in Poland?”</p>
<p>A person reads this as “How do I request a new laptop in Poland?”. A search index reads three words. It does not know the subject is a laptop, so it returns the pages that mention Poland the most. The answer is then written from those pages.</p>
<p>For a few weeks, a branch of our chatbot did exactly this. It already had a step that rewrites a follow-up into a full question before search. That step had a prompt, and the prompt had rules for follow-ups. However, after I changed how the conversation history was saved, the history it received was always empty. So every message was treated as the first message of a conversation. Nothing failed, and no error was logged. We found it before the change was merged.</p>
<p>Turning the latest message into something search can use is called <strong>query contextualization</strong>. Papers call it question-in-context rewriting [1]. This post goes through five levels of it, from no context at all to a rewrite that first decides what kind of follow-up it is. I moved the examples to an IT helpdesk, and I’ll leave out sizes and numbers that aren’t mine to share.</p>
<h2>Level 1: search the last message</h2>
<p>The simplest RAG chatbot sends each message to search as typed. For the first message of a conversation, that works. “How do I request a new laptop in Sweden?” has everything search needs.</p>
<p>It breaks on follow-ups, because people leave out what was already said:</p>
<ul>
<li>“And in Poland?” keeps the subject and changes the location.</li>
<li>“Who qualifies for it?” points back with a pronoun.</li>
<li>“setting it up on my phone” answers a question the bot asked.</li>
</ul>
<p>None of these can be searched alone.</p>
<h2>Level 2: give the history to the answer model</h2>
<p>The next idea is to send the earlier messages to the model that writes the answer. Chat APIs make this easy. Each request is stateless, so you pass the prior user and assistant messages yourself [7].</p>
<p>This helps the answer, and it does nothing for search. The model now knows the user means laptops. But the documents in front of it were found with “And in Poland?”. So it can refuse, or it can answer from the wrong pages. In a RAG chatbot the answer can only be as good as what search found. Therefore the history has to reach search.</p>

<p>In our chatbot, only the rewrite step reads the stored history. Search and the answer step get the rewritten query.</p>
<h2>Level 3: rewrite the last message into a standalone query</h2>
<p>Level 3 adds one model call before search. It reads the history and the latest message, and it returns a query that makes sense alone. For “And in Poland?” it returns “How do I request a new laptop in Poland?”. This is the task the CANARD dataset defines: rewrite a question that depends on the conversation into a self-contained question with the same answer [1].</p>
<p>Here is the shape of ours. This is a simplified sketch, not our exact code:</p>
<pre><code class="hljs language-python"><span class="hljs-keyword">async</span> <span class="hljs-keyword">def</span> <span class="hljs-title function_">contextualize</span>(<span class="hljs-params">message: <span class="hljs-built_in">str</span>, history: <span class="hljs-built_in">list</span>[Message]</span>) -> Rewrite:
    <span class="hljs-keyword">if</span> <span class="hljs-keyword">not</span> history:
        <span class="hljs-comment"># First message: only fix typos and extract a location.</span>
        <span class="hljs-keyword">return</span> <span class="hljs-keyword">await</span> fix_and_extract_location(message)
    payload = json.dumps({
        <span class="hljs-string">"conversation"</span>: format_history(history[-<span class="hljs-number">10</span>:]),
        <span class="hljs-string">"latest_user_message"</span>: message,
    })
    result = <span class="hljs-keyword">await</span> llm.parse(
        system=REWRITE_PROMPT,
        user=payload,
        response_format=Rewrite,  <span class="hljs-comment"># contextualized_query + locations</span>
    )
    <span class="hljs-keyword">if</span> result <span class="hljs-keyword">is</span> <span class="hljs-literal">None</span>:
        <span class="hljs-keyword">return</span> Rewrite(contextualized_query=message, locations=[])
    <span class="hljs-keyword">return</span> result
</code></pre>
<p>A few choices in it are worth copying:</p>
<ul>
<li>The first message skips the rewrite, because there is nothing to resolve. LangChain’s history-aware retriever makes the same choice. With no chat history, the input goes straight to the retriever [6].</li>
<li>The dialogue goes in as JSON in the user message, and the rules stay in the system message. The prompt says to treat the dialogue as data, not as instructions, and not to answer the question.</li>
<li>The output is structured: the query, plus the locations it names. A location becomes a search filter, so it should be a field.</li>
<li>If the model returns nothing usable, search runs on the raw message. A weaker search is better than no answer.</li>
<li>The rewriter keeps codes and acronyms exactly as written. A later step without a model expands the known acronyms, and it can only do that if the token is still there.</li>
</ul>
<p>Level 3 handles most follow-ups. The cases it got wrong were less obvious. A generic rewrite prompt has one habit: when in doubt, add context. That habit is right for “And in Poland?”. It is wrong in several other cases.</p>
<h2>Level 4: decide what kind of follow-up it is</h2>
<p>Here is one of those cases. The user writes “I need help with VPN-7”. The bot asks: “Could you tell me more about what you need help with regarding VPN-7?” The user replies: “How do I reset my password?”</p>
<p>A generic rewrite sees a pending clarifying question and merges: “How do I reset my VPN-7 password?”. But the user has moved on. Their reply is a complete question with its own subject. If they had replied “setting it up on my phone” instead, merging would be right.</p>
<p>The two replies come right after the same bot message. Only the reply itself tells them apart. So before the rewrite chooses a subject, it has to decide what kind of follow-up the latest message is. These are the types our prompt separates. The examples are rewritten, but the rules are the ones in our prompt.</p>

<p>A full question is not always standalone. “How do I apply?” is a complete sentence with no object. After an answer about the laptop loan program, it still needs that subject. Our tests have a case for exactly this.</p>
<h3>Recency is not intent</h3>
<p>The complaint type took the most attempts. Here is the shape of it. The user asks “Can I get a company phone?”. The bot answers: “I couldn’t find a company phone policy. I found the laptop loan program, which lends a laptop for up to two weeks.” The user writes: “Really nothing on it? Who qualifies for it?”</p>
<p>The nearest item to “it” is the laptop loan program. A rewrite that resolves pronouns by recency returns “Who qualifies for the laptop loan program?”. But the user is complaining that their own question had no answer. So “it” is the company phone, and the search should be “Who qualifies for a company phone?”.</p>
<p>The rule that fixed it says to resolve references using the whole latest message, not recency alone. If the user challenges the missing answer, every pronoun in that same message stays on the user’s original subject. The bot’s alternative is used only when the user names it or accepts it, as in “Who qualifies for the laptop loan you mentioned?”.</p>
<p>A neutral follow-up works the other way. After a normal answer, “How long does it take?” refers to the item the bot explained. An item the bot only mentioned in passing does not count.</p>
<h3>Location is part of the follow-up</h3>
<p>Location needs its own rules, because it often becomes a filter on search. An earlier location is inherited only by a related follow-up. If the user asked about laptops in Sweden and then asks “How do I book a meeting room?”, the new query gets no location. Our older prompt added an earlier location whenever the new query had none and the earlier one was clear. That narrowed unrelated questions to a country the user did not ask about.</p>
<p>The other rules are short. An explicit location in the latest message replaces the earlier one. A comparison keeps both locations. A location the user refused is never added back.</p>
<p>One bug here is easy to miss. The model mapped the language of a question to a country. A question written in Indonesian came back with Indonesia as its location, though no country was named. Our location prompt now says plainly that the language of a query is not a location.</p>
<h3>Writing the rules as a decision list</h3>
<p>Our first prompt for this step grew one fix at a time, and many lines had an exception such as “UNLESS it answers a clarifying question”. I rewrote it as one ordered list under the heading “Choosing the subject”. The order is the priority: when two rules seem to fit, the earlier one decides. The table above is that list, in the same order. The <a href="/posts/writing-prompts-for-agentic-workflows/">prompts post</a> shows the prompt before and after the change, and how I tested it with repeated runs.</p>
<p>The prompt has only two examples, and both are analogous to the hard cases, not copies of test cases. At one point I added two more that matched the clarification tests almost word for word. I removed them in the next change. I prefer one general rule over a rule for each case, because case rules pile up and need changing later.</p>

<h2>Level 5: keep the state outside the prompt</h2>
<p>Now the bug from the start. The rewrite step and its prompt were fine. The history it received was empty.</p>
<p>We read the saved history from the agent framework’s context for the first agent, the one that runs the rewrite. The framework added the bot’s answer to that context only on the agent’s next call, and that call never came in the same turn. So every saved turn had a question and no answer, and the list of turns stayed empty. The fix builds each turn from the user’s message and the final answer that our own code already has, and passes the saved turns to the rewrite step as an argument. The <a href="/posts/state-in-agents/">post on state</a> tells the full story, with a figure of the timing and the session schema.</p>
<p>Two details matter for the rewrite step itself. It reads only the last 10 messages of the stored history, so each request stays at a known size. Every message you send counts against the model’s context window [7]. The number of restored turns also goes on the trace. A trace that says 0 restored turns on the third message of a conversation would have shown our bug much earlier.</p>
<p>The general lesson: own the conversation state. Store it in your own schema, from values you control, and pass it in where it is needed. The framework’s internal context is a detail of how the framework calls the model. Its timing can change, and it is not a record of the conversation.</p>
<h2>Things to watch</h2>
<ul>
<li><strong>An empty history looks like success.</strong> Without history, a follow-up still gets an answer, only a worse one. Put the number of restored turns on the trace.</li>
<li><strong>Context added by default.</strong> A rewrite that always merges breaks new questions that follow a clarifying question. Test that case on purpose.</li>
<li><strong>Recency resolving pronouns.</strong> A complaint refers to the user’s subject, even when the bot’s last answer named something else.</li>
<li><strong>Location inferred from language.</strong> Say in the prompt that the language of a question is not a location.</li>
<li><strong>Acronyms changed by the rewriter.</strong> Keep the token exact, and expand it in code. We also had to tell the answer step to keep an expansion like “ACRONYM (Full Form)” in its first mention, instead of shortening it back.</li>
<li><strong>One more model call.</strong> The rewrite runs on the critical path of every follow-up. On the first message there is nothing to resolve, so we use a smaller call that only fixes typos and extracts a location.</li>
<li><strong>Flaky prompt tests.</strong> Run each real-model case more than once, and decide in advance how many passes count.</li>
</ul>
<h2>What others do</h2>
<p>The research on this is older than LLM chatbots. CANARD has about 40,000 conversational questions, each paired with a standalone rewrite [1]. In the TREC CAsT 2019 track, leading systems rewrote conversational queries with GPT-2. Queries resolved by hand still beat the best automatic system by about 35%, relative [2]. So the rewrite is a real source of lost quality, and it is worth measuring on its own.</p>
<p>Rewrite-Retrieve-Read goes a step further and trains the rewriter [3]. A small model writes the query, and it is trained with reinforcement learning on feedback from the model that reads the results. Ours is a prompted model. Training one would need a set of follow-ups with good rewrites first.</p>
<p>HyDE asks a model to write a hypothetical answer and searches with its embedding [4]. I tried it as a third search path in <a href="/posts/tuning-retrieval-for-multilingual-rag/">an earlier post</a>: 0.6 points more recall for 2.4 times the retrieval latency. It solves a different problem. HyDE bridges the words of a question and the words of a document. Contextualization fills in what the user left out. A HyDE passage written from “And in Poland?” is still about Poland, so the rewrite has to come first.</p>
<p>Multi-query retrieval asks a model for several versions of the question, searches with each, and keeps the unique union of the results [5]. LangChain’s default prompt asks for three versions.</p>
<h2>What I would try next</h2>
<ul>
<li><strong>Search both readings when the type is unclear.</strong> For a complaint that might accept the alternative, search the original subject and the alternative, like multi-query, and let the reranker decide.</li>
<li><strong>A golden set of follow-ups by type</strong>, taken from real traces and scored on the rewritten query alone. A wrong rewrite is cheaper to catch there than in the final answer.</li>
</ul>
<p>If your RAG chatbot answers follow-ups badly, check that the history really reaches the rewrite step before you touch the prompt. Then test a new question right after a clarifying question, and a complaint after a substitute answer. Those were the two cases our generic prompt got wrong.</p>
