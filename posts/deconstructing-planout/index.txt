1d:T8017,<p>Andi opens a checkout page. We want to test two buttons: A is blue, B is pink. He gets blue today. Tomorrow, he opens the page on another server. He should still get blue.</p>
<p>That sounds like a small requirement. It rules out the most obvious implementation: toss a fresh coin on every request. You could save every user’s choice in a database, but then every server needs access to that record. PlanOut offers another way: make the coin toss repeatable from the inputs.</p>
<p>This post takes that idea apart with one shopper, one button and the actual numbers from PlanOut’s archived Python implementation. The user IDs are made up.</p>

<h2>What PlanOut was trying to separate</h2>
<p>The product owns the checkout page. The experiment owns the rule for choosing the button. Those should not become one tangled piece of code.</p>
<p>PlanOut was developed at Facebook as a language and framework for defining online experiments. Its 2014 paper describes how an experiment maps a unit, such as a user ID, to parameter values. A parameter might be a button colour, a piece of text, or a discount. Product code asks for that value and uses it.</p>
<p>So the experiment’s whole job is to say “blue”. Drawing the button, counting purchases and working out whether blue is better all happen somewhere else.</p>

<p>Here is a small definition using PlanOut’s Python API:</p>
<pre><code class="hljs language-python"><span class="hljs-keyword">from</span> planout.experiment <span class="hljs-keyword">import</span> SimpleExperiment
<span class="hljs-keyword">from</span> planout.ops.random <span class="hljs-keyword">import</span> UniformChoice

<span class="hljs-keyword">class</span> <span class="hljs-title class_">CheckoutButton</span>(<span class="hljs-title class_ inherited__">SimpleExperiment</span>):
    <span class="hljs-keyword">def</span> <span class="hljs-title function_">setup</span>(<span class="hljs-params">self</span>):
        <span class="hljs-variable language_">self</span>.salt = <span class="hljs-string">"checkout-v1"</span>

    <span class="hljs-keyword">def</span> <span class="hljs-title function_">assign</span>(<span class="hljs-params">self, params, userid</span>):
        params.button = UniformChoice(
            choices=[<span class="hljs-string">"blue"</span>, <span class="hljs-string">"pink"</span>], unit=userid
        )

experiment = CheckoutButton(userid=<span class="hljs-string">"user-42"</span>)
colour = experiment.get(<span class="hljs-string">"button"</span>)  <span class="hljs-comment"># "blue"</span>
</code></pre>
<p>Andi’s invented ID is <code>user-42</code>. It is the <em>unit</em>: the thing we randomise. If we used a session ID instead, we’d be randomising sessions, and Andi could get a different button on his next visit. Picking the unit is a design decision, and I wouldn’t leave it to whatever the SDK defaults to.</p>
<h2>A coin toss without a coin</h2>
<p>A hash function turns an input string into a fixed-length output. The same input always gives the same output. Small changes to the input usually produce very different outputs.</p>
<p>PlanOut uses SHA-1 as a mixing function for assignment. None of this is about security or hiding which group someone is in. SHA-1 is just a convenient way to get values that repeat exactly and spread evenly.</p>
<p>For this example, PlanOut joins three pieces with dots:</p>
<ol>
<li>The experiment salt: <code>checkout-v1</code>.</li>
<li>The parameter salt: <code>button</code>, supplied from the assigned variable name.</li>
<li>The unit: <code>user-42</code>.</li>
</ol>
<p>The complete key is <code>checkout-v1.button.user-42</code>. The default separator is a dot; explicit salt overrides and multi-part units have their own paths in the source.</p>

<p>SHA-1 produces 40 hexadecimal digits. The Python implementation keeps the first 15. Each hex digit holds four bits, so that prefix gives a 60-bit integer. For Andi:</p>
<pre><code class="hljs language-text">key:          checkout-v1.button.user-42
SHA-1:        3441f9fc514ea2ac8f04b1c44a64d90aa350f4fb
first 15:     3441f9fc514ea2a
integer h:    235347851596851754
h % 2:        0
choices[0]:   blue
</code></pre>
<p><code>%</code> means remainder. Dividing an even number by 2 leaves remainder 0; an odd number leaves 1. With two choices, that is the whole <code>UniformChoice</code> decision: <code>choices[h % 2]</code>.</p>
<p>A thousand servers can repeat it. None needs a stored row saying “Andi got blue”, as long as they agree on the input and implementation.</p>
<h2>The bucket picture, with one important distinction</h2>
<p>It is tempting to explain every assignment as “put the hash on a line from zero to one, then split the line in half”. That is a useful picture for weighted choices. It is not the exact code path for <code>UniformChoice</code>.</p>
<p>The archived Python implementation has two different operations:</p>
<ul>
<li><code>UniformChoice</code>: use the integer’s remainder to select a list position.</li>
<li><code>WeightedChoice</code>: divide the integer by a scale, then compare it with cumulative weights.</li>
</ul>
<p>For the second operation, the scale is <code>2**60 - 1</code>, or <code>1,152,921,504,606,846,975</code>. Andi’s normalized value is about <code>0.2041317216</code>. With weights <code>[0.5, 0.5]</code>, it lands in blue’s half of the line.</p>

<p>Both operations happen to give Andi blue, but they won’t agree for every user. Swap one for the other and some users change groups, even though both are a 50/50 split.</p>
<p>A small source-level detail matters if you want compatibility: PlanOut converts that scale to a floating-point value, and uses <code>&#x3C;=</code> at the weighted boundaries. The mathematical normalization includes 1 at the maximum hash. Replacing the denominator with <code>2**60</code>, changing the comparison, or switching to another port without checking its hash behaviour can quietly move users.</p>
<h2>Salts: same label, same shuffle</h2>
<p>Think of the salt as the label on a shuffled deck. With the same deck label and the same user ID, draw the same card again. Change the label and you get a new shuffle.</p>
<p>Here are computed results for 10,000 invented users, <code>user-0</code> through <code>user-9999</code>, using the same key construction and <code>UniformChoice</code> modulo rule:</p>
<p>| Change | Users whose button changed |
| — | —: |
| Repeat <code>checkout-v1</code>, same choices | 0 / 10,000 |
| Change salt to <code>checkout-v2</code> | 4,984 / 10,000 |
| Keep salt, reverse <code>[blue, pink]</code> | 10,000 / 10,000 |</p>
<p>The original split was 5,004 blue and 4,996 pink. Those exact counts belong to this made-up population. Another set of IDs would land slightly differently.</p>

<h3 id="po-salt-title">Change the shuffle, not the users</h3>
<p>These are the same 200 IDs, <code>user-0</code> through <code>user-199</code>. Each dot uses SHA-1 and the first 15 hex digits, then <code>h % 2</code>. Change only the salt and see which users cross over.</p>

<noscript><p>The static salt comparison above shows the same principle. Enable JavaScript to reshuffle 200 users yourself.</p></noscript>
<p>For Andi, the new salt produces prefix <code>5c87192d9dc8829</code>, integer <code>416707841066043433</code>, and remainder 1. He moves to pink. Reversing the original choices also gives him pink, but for a different reason: his original index is still 0; index 0 now means pink.</p>
<p>That last row is the trap. The hash didn’t change at all, but what its output points to did, and every single user moved.</p>
<p>A new experiment can use a new salt deliberately. A live experiment should not casually rename its salt, change ID formatting, reorder choices, edit weights, or switch hashing algorithms. Any of those can change the experience for people already enrolled. Hashing only repeats the same answer while the definition stays the same. If assignments have to survive a definition change, you need to store them.</p>
<p>The parameter name acts as a salt too. <code>button</code> and <code>hint</code> get different hash keys for the same user, unless you intentionally share an explicit salt. This keeps two parameters from being perfectly tied to each other by accident.</p>
<h2>Namespaces: pick the experiment before the button</h2>
<p>Now suppose two teams both want to test the checkout page. One tests the button; the other tests the layout. We do not want Andi in both at the same time.</p>
<p>A namespace is a shared allocation space. In the Python implementation, a user hashes into an integer segment. Experiments reserve disjoint sets of segment IDs. The user’s segment decides which experiment, if any, runs. Only then does that experiment choose its parameter values.</p>

<p>The numbered tiles above are only a sketch. I didn’t compute Andi’s real segment. The real <code>add_experiment()</code> samples from the available segments, so an experiment’s allocation need not be a neat contiguous range.</p>
<p>Mutual exclusion applies inside that namespace: a segment cannot belong to both checkout experiments at once. A separate namespace for the homepage can also enrol Andi. Namespaces do not automatically prevent interactions between experiments on different surfaces.</p>
<p>The namespace name, unit, segment count and allocation history are part of the routing contract. Preserving only the button’s salt will not preserve routing if those change.</p>
<h2>Exposure logging</h2>
<p>We have computed a button colour. Has Andi seen the button? Not necessarily. The page might fail before rendering it. The application might ask for the colour on a route where checkout is never shown.</p>
<p>PlanOut gives you a logging hook. In the default Python experiment behaviour, the first eligible <code>get()</code> on an instance triggers exposure logging before returning the parameter. The instance remembers that it logged, so repeated <code>get()</code> calls on that same instance do not each emit a new automatic exposure. A new instance starts over, and nothing deduplicates across instances for the same user.</p>

<p>What the hook records is that the code asked for the parameter. Whether a person actually saw the button is a separate question. Automatic logging can be disabled, and an experiment marked out of experiment does not log an exposure. The base experiment delegates the log to your implementation; <code>SimpleExperiment</code> writes JSON to a file. Getting a production event pipeline right is still your job.</p>
<p>A useful record connects the unit, experiment, parameter values and time to the definition that produced them. Upstream also records a checksum when available. In a production system I would make the definition version, override, surface and event ID explicit, then decide where the application should emit the event that analysis treats as exposure.</p>
<p>If you still have the inputs and the definition, you can recompute which button someone was meant to get. You can’t recompute a render that never got logged, or a fallback nobody recorded.</p>

<p>Suppose the button experiment expects an even split, but the logged population contains 700 blue and 300 pink users. That is a sample ratio mismatch, or SRM: the observed group counts are unexpectedly far from the planned allocation.</p>
<p>It tells you to go and look at the experiment. It says nothing yet about whether pink loses. Maybe assignment changed. Maybe one group has missing events. Maybe the eligibility filter is different on the two paths. Check the population you count, the planned allocation, and the logging before reading an effect estimate. A fixed 50/50 check also does not fit a bandit that intentionally moves traffic.</p>
<p>PlanOut won’t do that investigation for you, and it doesn’t estimate lift either. It handles repeatable assignment. Exposure data, outcome definitions and the statistics are left to you.</p>
<h2>The archive badge</h2>
<p>The public repository was archived on June 1, 2021 and is now read-only. I couldn’t find the maintainers saying why.</p>
<p>So I wouldn’t read much into it. It’s tempting to turn it into a story about Facebook giving up on experimentation, or a successor replacing PlanOut, but I haven’t seen evidence for either. Its own documentation described the interpreter as one way to define experiments at Facebook, running on top of QuickExperiment. The public library was never the whole internal platform.</p>
<p>What has changed for someone choosing a tool today is the available scope. A language gives you definitions and operators. Modern experimentation products can also provide configuration delivery, allocation controls, exposure handling, metric definitions and analysis. That’s a good reason to look at a broader platform today, whatever the reason for the archive was.</p>
<h2>What I would use instead today</h2>
<p>PlanOut doesn’t name an official successor, and the right replacement depends on which part of its job you need.</p>
<ul>
<li>For owning the assignment implementation, a small SDK can work, but stable identity, versioned definitions and compatibility tests become your responsibility. GrowthBook’s <a href="https://docs.growthbook.io/lib/build-your-own">build-your-own guide</a> is a useful current example of an SDK contract.</li>
<li>For an experimentation platform, <a href="https://docs.growthbook.io/app/sticky-bucketing">GrowthBook</a> and <a href="https://docs.statsig.com/experiments-plus">Statsig</a> are examples worth evaluating. Compare their allocation, logging, warehouse and analysis paths against your requirements. Neither hashes the way PlanOut does, so a running experiment won’t keep its groups if you switch.</li>
<li>For adaptive allocation, the policy is another layer. A bandit updates traffic based on rewards; a deterministic hash does not learn which button sells more. I covered that distinction in <a href="/posts/thompson-sampling-explained-with-coupons/">Thompson sampling, explained with coupons</a>.</li>
</ul>
<p>If I were moving an existing experiment, I would first make a test set of IDs, salts, definitions, overrides and expected outputs. Run old and new systems against it. Explain every disagreement before moving live traffic. A new SDK producing “roughly half in each group” is not enough if it puts different people in those groups.</p>
<p>What I keep from PlanOut is smaller than a platform: separate the experiment definition from product code, make assignment repeatable, and be explicit about where deciding stops and observing starts. Getting Andi blue twice turned out to be the easy part. Finding out whether blue helped him takes a lot more machinery.</p>
