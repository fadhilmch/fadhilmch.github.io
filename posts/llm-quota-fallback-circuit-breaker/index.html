Keeping a chatbot answering when the model runs out of quota

A chatbot answer needs about 15 model calls, and one 429 can lose the whole answer. Which errors should fall back to a second deployment, how a small circuit breaker stops paying for a primary that keeps failing, and what I would add next.

Agents & LLMsML platform

A user asks our chatbot a question. Before the answer appears, the backend makes about 15 model calls. It detects the language, classifies the question, rewrites it for search, filters what the search returned, and finally writes the answer. Most of these calls run one after another, and the chat window gives up after 60 seconds.

After launch, some of those calls started to fail with HTTP 429, Too Many Requests. Our own traffic was lower than we had planned for. However, the quota for a model is shared by every deployment of that model in the same subscription and region, and other deployments were using it too. When one of the 15 calls fails, the user gets no answer at all.

Two things helped. The first is a second deployment to fall back to. The second is a circuit breaker: a small piece of state that stops calling a deployment for a while when it keeps failing. This post goes through both, with the choices I made and the ones I would change. I’ll leave out quota sizes and traffic numbers, which aren’t mine to share.

Why a 429 is not always your fault

On Azure OpenAI, quota is counted in tokens per minute (TPM). It is given to a subscription per region, per model and per deployment type. Every deployment you create takes a part of that quota. So two teams that deploy the same model in the same subscription and region share one budget, even if their apps have nothing to do with each other.

The rate limit is also stricter than “tokens per minute” sounds. The quota documentation has two details that matter here [6]:

  • The token count is an estimate made when the request arrives. It includes max_tokens, so a request that asks for a large max_tokens uses budget even if the reply is short.
  • The requests-per-minute limit is checked over short windows, typically 1 or 10 seconds. A burst inside one second can get a 429 even if the minute as a whole is under the limit.

There are also two kinds of 429. One says rate limit exceeded: your deployment used its allocation. The other says the service is temporarily unable to process your request: the shared backend is short on capacity, and your quota did not change. The documentation says many people request more quota for the second kind, which doesn’t help. We log the two kinds separately for this reason.

Retrying the same deployment was not enough

The usual first answer to a 429 is to retry with exponential backoff and jitter. Backoff waits longer after each failure. Jitter adds a random part to the wait, so that many clients that failed at the same moment don’t all retry at the same moment too. Marc Brooker’s post explains why with a simulation [4]. The OpenAI Python SDK already does it: it retries twice by default and respects the retry-after header.

For us, retrying alone had two problems.

The first is time. A 429 often comes with a retry-after value of several seconds. The API Management documentation warns that it can be as large as a day [7]. With 15 calls in 60 seconds, each call has a few seconds to spare at most. Waiting for the same deployment to recover uses up the time the rest of the answer needs.

The second is that retries multiply. If the SDK retries twice and your own code retries twice around it, one failing call becomes nine requests. Google’s SRE book recommends retrying at one layer only, and keeping a retry budget per client [5]. A deployment that is out of quota also counts the rejected requests against its limit [6], so more retries make the throttling worse.

So I stopped retrying the primary. Its SDK retries are set to zero, and a different deployment takes the retry instead. A comment in the code says it in one line: the fallback is the retry.

A second deployment to fall back to

The fallback is a deployment of an older model that we already had quota for. Because quota is counted per model, it does not share a budget with the primary. Each kind of call has a primary and an optional fallback, set in configuration. If the fallback is empty, the primary runs alone with a longer timeout.

Not every error should fall back. The question to ask is: would another deployment probably succeed where this one failed?

These errors fall back:

  • connection errors and timeouts, including our own timeout per attempt
  • 404, which here usually means the deployment name is wrong or the deployment was removed
  • 408 and 409
  • 429, both kinds
  • any 5xx

A 400 does not fall back. A content filter rejection, for example, is about the input. The fallback would see the same input and reject it too, and we would have spent time for nothing. A bad output from the model does not fall back either, because the call succeeded. That is a quality problem, and it belongs to evaluation, not to this layer.

Here is the shape of it. This is a simplified sketch, not our exact code:

FALLBACK_STATUS = {404, 408, 409, 429}

def should_fall_back(exc: Exception) -> bool:
    if isinstance(exc, (APIConnectionError, TimeoutError)):
        return True
    if isinstance(exc, APIStatusError):
        return exc.status_code in FALLBACK_STATUS or exc.status_code >= 500
    return False

async def call_with_fallback(route, call):
    breaker = breakers[(route.primary.deployment, route.name)]
    if route.fallback and breaker.is_open():
        return await call(route.fallback)
    started = time.monotonic()
    try:
        result = await call(route.primary)
    except Exception as exc:
        if route.fallback is None or not should_fall_back(exc):
            raise
        breaker.record_failure()
        return await call(route.fallback)
    breaker.record_success(started)
    return result

call is a function that makes the request against one deployment. The same wrapper is used by the plain OpenAI calls and by the agent framework’s chat client, so there is one place where the rule lives.

A fallback has to fit in the time budget

A fallback only helps if it finishes before the user gives up. So every attempt has a hard timeout. The call that writes the answer gets 20 seconds on the primary and 30 on the fallback. The quicker calls get less.

Our first fallback for the answer ran at the same reasoning effort as the primary. In a test with the primary switched off, it took 42.6 seconds for one answer. Together with the other calls, that was over the 60-second limit. The fallback now runs at a lower reasoning effort. The answer is a little less careful, but it arrives.

These timeouts are per attempt, not for the whole request. A slow primary followed by a slow fallback can still go over 60 seconds. A deadline for the whole request, which every call checks before it starts, would be the cleaner fix. I haven’t built that yet.

The circuit breaker

The fallback fixed lost answers, but it left a cost. When the primary is out of quota, every call still tries it first. For a 429 that is a fast failure. For a timeout it is up to 20 seconds per call, spent waiting for something we already know is broken.

A circuit breaker removes that cost. The idea comes from Michael Nygard’s book Release It!, and Martin Fowler’s short article is a good introduction [1, 2]. It works like the breaker in a fuse box. While it is closed, calls go through and failures are counted. When failures reach a limit, it opens, and calls skip the failing deployment and go straight to the fallback. After a cooldown, calls try the primary again.

Ours is small:

TRIP_FAILURES, WINDOW_S, COOLDOWN_S = 2, 30.0, 60.0

class Breaker:
    def __init__(self):
        self.failures: list[float] = []
        self.opened_at = float("-inf")
        self.open_until = 0.0

    def is_open(self) -> bool:
        return time.monotonic() < self.open_until

    def record_failure(self) -> None:
        now = time.monotonic()
        self.failures = [t for t in self.failures if now - t < WINDOW_S] + [now]
        if len(self.failures) >= TRIP_FAILURES:
            self.failures = []
            self.opened_at, self.open_until = now, now + COOLDOWN_S

    def record_success(self, started: float) -> None:
        if started > self.opened_at:
            self.failures, self.open_until = [], 0.0

Two failures within 30 seconds open it for 60 seconds. One failure only sends that one call to the fallback. So a single slow answer that times out on a healthy deployment does not move all the traffic away.

There is one breaker for each primary deployment and each kind of call. A slow answer-writing call should not divert the quick classification calls, even when they use the same deployment.

The check in record_success is easy to miss. Calls overlap. A call can start on the primary, take 15 seconds, and succeed after the breaker has already opened because of other calls. Without the check, that late success would close the breaker right after it opened. So only a call that started after the trip can close it.

With a 429 the breaker saves little time, because the failure is fast. With timeouts the difference is large: without the breaker, every call pays the full timeout before the fallback starts.

Where ours differs from the textbook

The usual circuit breaker has a third state. After the cooldown it goes half-open: it lets one or a few trial calls through, and only closes if they succeed [3]. Ours has no half-open state. When the 60 seconds are over, every call that arrives tries the primary again.

This works for us because the fallback still catches every failure. If the primary is still out of quota, a few calls fail and the breaker opens again after two of them. Those calls still get an answer from the fallback. The cost is a short burst of failed attempts every minute. For a deployment that is overloaded rather than out of quota, that burst could slow its recovery, and half-open would be the better choice.

The breaker state also lives in memory, one copy per pod. With several pods, each one trips on its own, so a broken primary costs two failures per pod instead of two in total. That is a known trade-off. Sharing the state, in Redis for example, would add a network call to every model call. API Management’s built-in breaker makes the same trade: its gateway instances don’t share breaker state either [7].

Prompts follow the model

A fallback is a different model, and a prompt tuned for one model is not always right for another. So each model has its own prompt file, picked by model name. There is a limit here. When a call falls back, it reuses the messages it already built from the primary’s prompt, so the older model runs on the newer model’s prompt. I would not assume that works for every pair of models. Test it with the primary switched off. The post on running several models covers the prompt files in detail.

Seeing fallbacks in traces

A fallback hides the failure from the user, and so it also hides it from you. If the primary has been failing all week, nobody notices unless the traces show it.

So every model call’s span records which deployment answered, and whether a fallback happened:

Attribute Example
llm.model_name the deployment that answered
llm.fallback.used true or false, always set
llm.fallback.reason RateLimitError (429), or CircuitOpen (...) when the breaker skipped the primary
llm.fallback.primary_latency_ms time spent on the primary before it failed

When the primary fails, the span also gets one llm.primary_failed event with the error. The span status stays OK, because the call recovered.

My first version did more. It added a child span for every attempt, so a healthy call had two spans instead of one. That added a cost to every healthy call, to show something that only matters when things go wrong. Attributes and one event on the existing span were enough. Now a healthy call adds nothing.

Grouping by llm.fallback.reason tells you what kind of problem you have. Timeouts and 5xx point to an outage, 429 to quota, and 404 to a wrong configuration. An alert on the fallback share, for example more than 5% of model calls in 15 minutes, tells you when the fallback is doing too much work.

Things to watch

  • Retries at two layers. The SDK retries by default. If you add your own retry or a fallback, set the SDK’s retries for the primary to zero, or one failure turns into many requests.
  • Same region, same problem. A capacity 429 is about the region, not your quota. A fallback in the same region can be throttled at the same moment. A second region or a global deployment type helps here, but data residency may decide whether you can use it.
  • A fallback that doesn’t fit. Measure the fallback with the primary switched off, end to end. Ours was too slow at first.
  • Falling back on the wrong errors. A 400 or a content filter error will fail on the fallback too.
  • A quiet fallback. Without an alert, a broken primary can stay broken for weeks.

What I would try next

Reading about how others do this showed me a few things ours doesn’t do yet.

  • Use retry-after for the cooldown. Our cooldown is always 60 seconds. A 429 tells you how long to wait. API Management’s breaker can take that value as its trip duration [7].
  • Different limits for different errors. The Azure pattern page suggests that timeouts may need more failures to trip than a clear “unavailable” [3]. LiteLLM’s router, for example, cools a deployment down on the first 429 and allows a few other failures before it does [8].
  • A half-open state with one trial call, if the primary is ever overloaded rather than simply out of quota.
  • Slow down before the 429. Azure returns x-ratelimit-remaining-tokens on every response [6]. A client could lower its pace when that gets small instead of waiting to be rejected.
  • A gateway instead of code. If several services share the same quota, a gateway puts the routing in one place for all of them. API Management with a priority pool and the LiteLLM proxy both do this [7, 8]. Doing it in the app has one advantage for us. The app also picks the prompt file and the reasoning effort for the fallback, and a gateway does not know about those.

If you call a hosted model from a service with a time limit, start with a short list of errors that may fall back and one retry layer. Give each attempt a timeout that fits the budget, and add a breaker that stops paying for a deployment that keeps failing. Then put the fallback in your traces, so you can see when it is doing the work.
