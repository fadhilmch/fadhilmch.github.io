22:T7683,<p>Say a user asks an internal chatbot how to book a meeting room. The bot explains the steps. The user then types “and for ten people?”. On its own, that question means nothing. The bot needs the previous turn to understand it.</p>
<p>Our chatbot is a team of agents that pass messages to each other in a group chat. I rewrote how it saves a conversation between turns. The first version of that change saved the history after every turn, and the history was always empty. Every follow-up was handled as if it were the first question of the conversation. Nothing crashed. The counters were saved, the session was written to the store, and only the turns were missing.</p>
<p>That bug made me think more carefully about what an agent should remember, where it should keep it, and what should never be remembered at all. This post goes through the choices we made and what other frameworks recommend. I’ll leave out sizes and numbers that aren’t mine to share.</p>
<h2>Three places state can live</h2>
<p><strong>State</strong> is anything the bot must remember to handle the next step correctly. In an agentic chatbot it lives in three places, and each one has a different lifetime.</p>
<ul>
<li><strong>Turn state</strong> is the messages the agents pass to each other while they answer one question. In our system the team of agents is built fresh for every turn, and these messages are dropped when the turn ends.</li>
<li><strong>Session state</strong> is what the next turn needs: the last few question and answer pairs, a few counters and a short summary of the previous question.</li>
<li><strong>Persisted state</strong> is the session state written to a store between turns. The next request can land on a different pod, so the session can’t live in memory.</li>
<li>Everything else is not state. Configuration, the user’s location from the request, and anything you can compute again belong somewhere else.</li>
</ul>

<p>Both history bugs below came from mixing these layers up.</p>
<h2>Persist a schema you own</h2>
<p>Our first session store saved the agent framework’s own state. The framework, AutoGen, can serialize a whole team with <code>save_state()</code> and load it again with <code>load_state()</code>. That is convenient. It is also the full message history of every agent in the team, and it grows with every turn.</p>
<p>My first fix was to trim it. The code walked the nested dictionary that <code>save_state()</code> returned and cut every list named <code>messages</code> or <code>message_thread</code> to its last 10 items. It also had to take care not to keep a tool result without the tool call that asked for it. It worked. However, it depended on how the framework laid out its internal state, and that layout can change with any upgrade.</p>
<p>So I replaced it with a small schema of our own. The session is now one JSON object with eight fields:</p>
<pre><code class="hljs language-json"><span class="hljs-punctuation">{</span>

  <span class="hljs-attr">"reformulations"</span><span class="hljs-punctuation">:</span> <span class="hljs-number">0</span><span class="hljs-punctuation">,</span>

<p>The first version of this schema is the one with the empty history. It filled <code>turns</code> from the model context of the reception agent, the agent that reads the user’s question first. That looked like the right place, because that agent needs the history. But the group chat ends on the reply agent’s message. AutoGen buffers that reply for the other agents, and it only reaches the reception agent’s model context on that agent’s next call. That call never happens in the same turn. So the context held the user’s message with no answer, and the list of finished turns was always empty.</p>

<p>The fix was to stop reading from the framework. The orchestrator already has the user’s query and the final answer, so it builds the turn from those two strings. It also keeps only the last 8 turns:</p>
<pre><code class="hljs language-python">MAX_PERSISTED_TURNS = <span class="hljs-number">8</span>

<span class="hljs-keyword">def</span> <span class="hljs-title function_">append_turn</span>(<span class="hljs-params">state: <span class="hljs-built_in">dict</span>, user: <span class="hljs-built_in">str</span>, assistant: <span class="hljs-built_in">str</span></span>) -> <span class="hljs-literal">None</span>:
    state[<span class="hljs-string">"version"</span>] = SESSION_SCHEMA_VERSION
    turns = [*state.get(<span class="hljs-string">"turns"</span>, []), {<span class="hljs-string">"user"</span>: user, <span class="hljs-string">"assistant"</span>: assistant}]
    state[<span class="hljs-string">"turns"</span>] = turns[-MAX_PERSISTED_TURNS:]
</code></pre>
<p>On the next turn the orchestrator passes the turns to the reception agent through its constructor, like the counters. Nothing writes into the agent’s private context anymore.</p>
<p>Microsoft Agent Framework, which we are moving to, has its own session object that serializes to a dictionary [1]. Its documentation carries a warning that matches what I learned: “Sessions are agent/service-specific. Reusing a session with a different agent configuration or provider can lead to invalid context.” Framework state is shaped for the framework. If you want state that survives a change of agent setup, or of framework, keep a copy in a shape you own.</p>
<h2>Put a version on it</h2>
<p>A session written by last week’s code will be read by this week’s code. So every change to the schema needs an answer to one question: what happens to the sessions already in the store?</p>
<p>Our answer grew in three steps. First we wrapped the framework state with the framework version it came from. Then we added a check that resets a session with missing or unknown fields instead of loading it. With the new schema, the check is one function:</p>
<pre><code class="hljs language-python"><span class="hljs-keyword">def</span> <span class="hljs-title function_">session_reset_reason</span>(<span class="hljs-params">state: <span class="hljs-built_in">dict</span></span>) -> <span class="hljs-built_in">str</span> | <span class="hljs-literal">None</span>:
    <span class="hljs-keyword">if</span> <span class="hljs-keyword">not</span> state:
        <span class="hljs-keyword">return</span> <span class="hljs-literal">None</span>  <span class="hljs-comment"># a new session</span>
    <span class="hljs-keyword">if</span> state.get(<span class="hljs-string">"version"</span>) != SESSION_SCHEMA_VERSION:
        <span class="hljs-keyword">return</span> <span class="hljs-string">"unknown_session_version"</span>
    <span class="hljs-keyword">if</span> <span class="hljs-keyword">not</span> SESSION_FIELDS.issubset(state):
        <span class="hljs-keyword">return</span> <span class="hljs-string">"missing_session_fields"</span>
    <span class="hljs-keyword">if</span> <span class="hljs-keyword">not</span> all_turns_are_strings(state[<span class="hljs-string">"turns"</span>]):
        <span class="hljs-keyword">return</span> <span class="hljs-string">"invalid_turns"</span>
    <span class="hljs-keyword">return</span> <span class="hljs-literal">None</span>
</code></pre>
<p>If it returns a reason, the turn starts with an empty session. The reason goes to a warning log and to the trace as <code>session.reset</code> and <code>session.reset_reason</code>. We never restore part of a session.</p>
<p>A reset costs the user their last few turns, and they may need to repeat a question. A crash costs every request in that session until it expires. For a chatbot with short sessions, that is the trade we chose. The framework migration plan also keeps a one-time reset at cutover, instead of converting old sessions.</p>
<p>The opposite approach is the <strong>tolerant reader</strong>. Martin Fowler describes it for messages between services: read only the fields you need and ignore the rest, so the other side can change without breaking you [7]. It suits data that many teams produce. Session state has one writer, which is us, and a wrongly restored counter is hard to see. So a strict check and a reset fit better here.</p>
<h2>Counters are loop budgets</h2>
<p>Three of the eight fields are counters, and each one stops a loop that could otherwise go on forever.</p>
<ul>
<li><code>clarifications</code> counts consecutive unclear questions that the bot answered with a question of its own. At 2, the next unclear turn goes to a fallback agent instead of asking again. A clear question resets it.</li>
<li><code>fallbacks</code> counts out-of-scope questions. At 3, the fallback agent takes over. Small talk does not count, and this counter never resets.</li>
<li><code>session_replies</code> counts every reply in the session. Past a fixed limit, every turn goes to the fallback agent.</li>
</ul>
<p>Inside a turn there is a second kind of budget. The inner group chats stop after 25 agent turns, whatever the agents decide. Anthropic’s guide to agents calls these stopping conditions and recommends them “to maintain control” [5]. LangGraph has the same thing as a recursion limit, and its error page says that hitting it usually means a loop in your graph [4].</p>
<p>A counter is only a budget if it survives the turn. So it must be in the persisted state, not in an agent object that is rebuilt every turn. It also matters when you write it. Our orchestrator commits the session only after a turn succeeds. If the turn fails, nothing is saved, and the failed attempt does not use up the user’s budget.</p>
<h2>When the session store is down</h2>
<p>The pods themselves keep no session. The Twelve-Factor App states the rule plainly. Processes are stateless, and “session state data is a good candidate for a datastore that offers time-expiration, such as Memcached or Redis” [8]. Ours is a Redis cluster, and each session expires after a fixed time.</p>
<p>So what happens when Redis is unreachable? My first plan, in June, said: treat the session as empty and keep answering. A pod-local fallback was rejected, because with several pods a local copy can go stale.</p>
<p>In October I changed my mind. With no fallback, a Redis outage dropped the context of every conversation for as long as it lasted. Now each pod has a small in-memory cache, bounded by size and by time. A write that can’t reach Redis goes to this cache. A read checks the cache first and then Redis. A successful Redis write removes the cached copy.</p>
<p>A circuit breaker sits in front of Redis. After 5 failures in a row it opens, and calls go straight to the memory cache for 30 seconds. Then the next call probes Redis again. Without it, every request would wait out the Redis timeouts and retries first. It logs only when its state changes, and every session span carries <code>session.circuit_state</code> and <code>session.fallback</code>, so a degraded hour is visible in the traces.</p>
<p>Two things went wrong on the way.</p>
<p>The first is an exception that didn’t look like a Redis error. When no node of the cluster is reachable, redis-py raises <code>RedisClusterException</code>. That class derives from plain <code>Exception</code>, not from <code>RedisError</code> [10]. Our code caught <code>RedisError</code>, so a Redis that was down when the pod started escaped the fallback on every call. The fix is one more entry in the tuple:</p>
<pre><code class="hljs language-python"><span class="hljs-comment"># RedisClusterException is not a RedisError.</span>
REDIS_UNAVAILABLE = (
    redis_exc.RedisError,
    redis_exc.RedisClusterException,
    asyncio.TimeoutError,
)
</code></pre>

<p>Microsoft’s cache-aside pattern page describes the same risk for any local cache: each instance has its own copy, and the copies “can quickly become inconsistent” [9]. We accepted it. The stale copy can only appear after an outage, and the alternative was losing the context of every conversation during it.</p>
<h2>What should not be state</h2>
<p>Some things look like state but are better kept out of the session.</p>
<ul>
<li>The user’s location arrives with every request, so it is not in the session. If it were stored too, you would need a rule for which copy wins when the two differ.</li>
<li>The limits above are constants in the code. Prompts and model routes come from configuration. If a session carried them, a deploy would not change sessions that were already open.</li>
<li>Retrieved documents and the messages between agents are dropped at the end of the turn. The next turn searches again.</li>
<li>Store a derived value only when computing it again is expensive. A summary that needs a model call can be worth storing. A flag you can derive from the stored turns is not.</li>
</ul>
<p>One way to decide: if this field had the wrong value, would anything correct it? Data from the request and from config is read fresh every turn, so it corrects itself. A stored copy does not.</p>
<h2>What others do</h2>
<p>Other frameworks make different choices about the same layers.</p>
<p>LangGraph saves the graph’s state as checkpoints with a <strong>checkpointer</strong> [3]. Checkpoints are scoped to a thread, and you pass a <code>thread_id</code> with each call. Data that should outlive one thread goes into a separate store. The documentation also warns that the in-memory checkpointer loses everything when the process restarts, and that checkpoints pile up in long conversations unless you prune them. That is the same split as ours: a session store for one conversation, and nothing that outlives it.</p>
<p>Microsoft Agent Framework keeps a session with an id and a state dictionary, and can serialize it with <code>to_dict()</code> [1]. For history growth it offers compaction strategies [2]. A sliding window keeps the most recent messages. Truncation drops the oldest ones once a token budget is passed. Summarization asks a smaller model to replace older messages with a summary. Our 8-turn cap is a sliding window counted in turns.</p>
<p><strong>Event sourcing</strong> stores every change as an event and rebuilds the current state by replaying them. Snapshots make the rebuild fast [6]. Our session is a single snapshot that is overwritten every turn, and the list of turns is a short event log with the old events cut off. We don’t keep a full log. It would let you replay a conversation after a bug fix, at the cost of more storage for data that expires soon anyway.</p>
<h2>Things to watch</h2>
<ul>
<li>Reading state from the framework. Agent frameworks buffer and route messages in ways that are easy to miss. Build the persisted turn from values your own code returned.</li>
<li>Unbounded history. Cap the number of turns. A count cap does not bound size, so one very long message can still make the session large.</li>
<li>No version field. Without one, you can’t tell an old session from a broken one. Add it before the first schema change, not after.</li>
<li>Counters outside the persisted state. A budget that lives in an object rebuilt every turn resets every turn.</li>
<li>Saving a failed turn. Commit only after the turn succeeds, or a failure uses up the user’s budget.</li>
<li>Exception hierarchies. Check what your client raises when the server is completely down. It may not be its usual base class.</li>
<li>A quiet fallback. Tag degraded reads and writes in traces and metrics. Otherwise a Redis outage only shows up as users repeating themselves.</li>
</ul>
<h2>What I would try next</h2>
<p>The first two are in the framework migration I’m working on, which isn’t merged yet. The third is only an idea.</p>
<ul>
<li>A revision number on every write. Each write says which revision it was built on. The store rejects it if the session has moved since. That is the same idea as an ETag (<a href="/posts/etags-and-the-lost-update/">an earlier post</a>), and it is meant to close the stale-copy gap above.</li>
<li>A byte bound as well as a turn bound. Old turns are dropped until the session fits a size limit, and each message is cut to a maximum length.</li>
<li>Fixtures of old sessions in the tests. Each schema version would keep a few stored sessions as test data. The tests would check that the reset logic still handles them.</li>
</ul>
<p>If you build a multi-agent chatbot, start by writing down the session schema. Keep it to a short list of fields you own, with a version number and a cap on history. Then decide what each counter protects against, and what the bot should do when the store is not there.</p>
