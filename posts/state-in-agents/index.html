Where an agentic chatbot keeps its state

A follow-up question only works if the bot remembers the last turn. What state a multi-agent chatbot needs, why I stopped saving the framework's own state, how a version field and a few counters keep sessions safe, and what happens when the session store goes down.

Agents & LLMsSystem design

Say a user asks an internal chatbot how to book a meeting room. The bot explains the steps. The user then types “and for ten people?”. On its own, that question means nothing. The bot needs the previous turn to understand it.

Our chatbot is a team of agents that pass messages to each other in a group chat. I rewrote how it saves a conversation between turns. The first version of that change saved the history after every turn, and the history was always empty. Every follow-up was handled as if it were the first question of the conversation. Nothing crashed. The counters were saved, the session was written to the store, and only the turns were missing.

That bug made me think more carefully about what an agent should remember, where it should keep it, and what should never be remembered at all. This post goes through the choices we made and what other frameworks recommend. I’ll leave out sizes and numbers that aren’t mine to share.

Three places state can live

State is anything the bot must remember to handle the next step correctly. In an agentic chatbot it lives in three places, and each one has a different lifetime.

  • Turn state is the messages the agents pass to each other while they answer one question. In our system the team of agents is built fresh for every turn, and these messages are dropped when the turn ends.
  • Session state is what the next turn needs: the last few question and answer pairs, a few counters and a short summary of the previous question.
  • Persisted state is the session state written to a store between turns. The next request can land on a different pod, so the session can’t live in memory.
  • Everything else is not state. Configuration, the user’s location from the request, and anything you can compute again belong somewhere else.

Both history bugs below came from mixing these layers up.

Persist a schema you own

Our first session store saved the agent framework’s own state. The framework, AutoGen, can serialize a whole team with save_state() and load it again with load_state(). That is convenient. It is also the full message history of every agent in the team, and it grows with every turn.

My first fix was to trim it. The code walked the nested dictionary that save_state() returned and cut every list named messages or message_thread to its last 10 items. It also had to take care not to keep a tool result without the tool call that asked for it. It worked. However, it depended on how the framework laid out its internal state, and that layout can change with any upgrade.

So I replaced it with a small schema of our own. The session is now one JSON object with eight fields:

{
  "version": 1,
  "session_replies": 3,
  "reformulations": 0,
  "fallbacks": 0,
  "clarifications": 1,
  "prev_intent_topic": "...",
  "prev_user_query_summary": "...",
  "turns": [{"user": "...", "assistant": "..."}]
}

The first version of this schema is the one with the empty history. It filled turns from the model context of the reception agent, the agent that reads the user’s question first. That looked like the right place, because that agent needs the history. But the group chat ends on the reply agent’s message. AutoGen buffers that reply for the other agents, and it only reaches the reception agent’s model context on that agent’s next call. That call never happens in the same turn. So the context held the user’s message with no answer, and the list of finished turns was always empty.

The fix was to stop reading from the framework. The orchestrator already has the user’s query and the final answer, so it builds the turn from those two strings. It also keeps only the last 8 turns:

MAX_PERSISTED_TURNS = 8

def append_turn(state: dict, user: str, assistant: str) -> None:
    state["version"] = SESSION_SCHEMA_VERSION
    turns = [*state.get("turns", []), {"user": user, "assistant": assistant}]
    state["turns"] = turns[-MAX_PERSISTED_TURNS:]

On the next turn the orchestrator passes the turns to the reception agent through its constructor, like the counters. Nothing writes into the agent’s private context anymore.

Microsoft Agent Framework, which we are moving to, has its own session object that serializes to a dictionary [1]. Its documentation carries a warning that matches what I learned: “Sessions are agent/service-specific. Reusing a session with a different agent configuration or provider can lead to invalid context.” Framework state is shaped for the framework. If you want state that survives a change of agent setup, or of framework, keep a copy in a shape you own.

Put a version on it

A session written by last week’s code will be read by this week’s code. So every change to the schema needs an answer to one question: what happens to the sessions already in the store?

Our answer grew in three steps. First we wrapped the framework state with the framework version it came from. Then we added a check that resets a session with missing or unknown fields instead of loading it. With the new schema, the check is one function:

def session_reset_reason(state: dict) -> str | None:
    if not state:
        return None  # a new session
    if state.get("version") != SESSION_SCHEMA_VERSION:
        return "unknown_session_version"
    if not SESSION_FIELDS.issubset(state):
        return "missing_session_fields"
    if not all_turns_are_strings(state["turns"]):
        return "invalid_turns"
    return None

If it returns a reason, the turn starts with an empty session. The reason goes to a warning log and to the trace as session.reset and session.reset_reason. We never restore part of a session.

A reset costs the user their last few turns, and they may need to repeat a question. A crash costs every request in that session until it expires. For a chatbot with short sessions, that is the trade we chose. The framework migration plan also keeps a one-time reset at cutover, instead of converting old sessions.

The opposite approach is the tolerant reader. Martin Fowler describes it for messages between services: read only the fields you need and ignore the rest, so the other side can change without breaking you [7]. It suits data that many teams produce. Session state has one writer, which is us, and a wrongly restored counter is hard to see. So a strict check and a reset fit better here.

Counters are loop budgets

Three of the eight fields are counters, and each one stops a loop that could otherwise go on forever.

  • clarifications counts consecutive unclear questions that the bot answered with a question of its own. At 2, the next unclear turn goes to a fallback agent instead of asking again. A clear question resets it.
  • fallbacks counts out-of-scope questions. At 3, the fallback agent takes over. Small talk does not count, and this counter never resets.
  • session_replies counts every reply in the session. Past a fixed limit, every turn goes to the fallback agent.

Inside a turn there is a second kind of budget. The inner group chats stop after 25 agent turns, whatever the agents decide. Anthropic’s guide to agents calls these stopping conditions and recommends them “to maintain control” [5]. LangGraph has the same thing as a recursion limit, and its error page says that hitting it usually means a loop in your graph [4].

A counter is only a budget if it survives the turn. So it must be in the persisted state, not in an agent object that is rebuilt every turn. It also matters when you write it. Our orchestrator commits the session only after a turn succeeds. If the turn fails, nothing is saved, and the failed attempt does not use up the user’s budget.

When the session store is down

The pods themselves keep no session. The Twelve-Factor App states the rule plainly. Processes are stateless, and “session state data is a good candidate for a datastore that offers time-expiration, such as Memcached or Redis” [8]. Ours is a Redis cluster, and each session expires after a fixed time.

So what happens when Redis is unreachable? My first plan, in June, said: treat the session as empty and keep answering. A pod-local fallback was rejected, because with several pods a local copy can go stale.

In October I changed my mind. With no fallback, a Redis outage dropped the context of every conversation for as long as it lasted. Now each pod has a small in-memory cache, bounded by size and by time. A write that can’t reach Redis goes to this cache. A read checks the cache first and then Redis. A successful Redis write removes the cached copy.

A circuit breaker sits in front of Redis. After 5 failures in a row it opens, and calls go straight to the memory cache for 30 seconds. Then the next call probes Redis again. Without it, every request would wait out the Redis timeouts and retries first. It logs only when its state changes, and every session span carries session.circuit_state and session.fallback, so a degraded hour is visible in the traces.

Two things went wrong on the way.

The first is an exception that didn’t look like a Redis error. When no node of the cluster is reachable, redis-py raises RedisClusterException. That class derives from plain Exception, not from RedisError [10]. Our code caught RedisError, so a Redis that was down when the pod started escaped the fallback on every call. The fix is one more entry in the tuple:

# RedisClusterException is not a RedisError.
REDIS_UNAVAILABLE = (
    redis_exc.RedisError,
    redis_exc.RedisClusterException,
    asyncio.TimeoutError,
)

          What should not be state

          Some things look like state but are better kept out of the session.

          • The user’s location arrives with every request, so it is not in the session. If it were stored too, you would need a rule for which copy wins when the two differ.
          • The limits above are constants in the code. Prompts and model routes come from configuration. If a session carried them, a deploy would not change sessions that were already open.
          • Retrieved documents and the messages between agents are dropped at the end of the turn. The next turn searches again.
          • Store a derived value only when computing it again is expensive. A summary that needs a model call can be worth storing. A flag you can derive from the stored turns is not.

          One way to decide: if this field had the wrong value, would anything correct it? Data from the request and from config is read fresh every turn, so it corrects itself. A stored copy does not.

          What others do

          Other frameworks make different choices about the same layers.

          LangGraph saves the graph’s state as checkpoints with a checkpointer [3]. Checkpoints are scoped to a thread, and you pass a thread_id with each call. Data that should outlive one thread goes into a separate store. The documentation also warns that the in-memory checkpointer loses everything when the process restarts, and that checkpoints pile up in long conversations unless you prune them. That is the same split as ours: a session store for one conversation, and nothing that outlives it.

          Microsoft Agent Framework keeps a session with an id and a state dictionary, and can serialize it with to_dict() [1]. For history growth it offers compaction strategies [2]. A sliding window keeps the most recent messages. Truncation drops the oldest ones once a token budget is passed. Summarization asks a smaller model to replace older messages with a summary. Our 8-turn cap is a sliding window counted in turns.

          Event sourcing stores every change as an event and rebuilds the current state by replaying them. Snapshots make the rebuild fast [6]. Our session is a single snapshot that is overwritten every turn, and the list of turns is a short event log with the old events cut off. We don’t keep a full log. It would let you replay a conversation after a bug fix, at the cost of more storage for data that expires soon anyway.

          Things to watch

          • Reading state from the framework. Agent frameworks buffer and route messages in ways that are easy to miss. Build the persisted turn from values your own code returned.
          • Unbounded history. Cap the number of turns. A count cap does not bound size, so one very long message can still make the session large.
          • No version field. Without one, you can’t tell an old session from a broken one. Add it before the first schema change, not after.
          • Counters outside the persisted state. A budget that lives in an object rebuilt every turn resets every turn.
          • Saving a failed turn. Commit only after the turn succeeds, or a failure uses up the user’s budget.
          • Exception hierarchies. Check what your client raises when the server is completely down. It may not be its usual base class.
          • A quiet fallback. Tag degraded reads and writes in traces and metrics. Otherwise a Redis outage only shows up as users repeating themselves.

          What I would try next

          The first two are in the framework migration I’m working on, which isn’t merged yet. The third is only an idea.

          • A revision number on every write. Each write says which revision it was built on. The store rejects it if the session has moved since. That is the same idea as an ETag (an earlier post), and it is meant to close the stale-copy gap above.
          • A byte bound as well as a turn bound. Old turns are dropped until the session fits a size limit, and each message is cut to a maximum length.
          • Fixtures of old sessions in the tests. Each schema version would keep a few stored sessions as test data. The tests would check that the reset logic still handles them.

          If you build a multi-agent chatbot, start by writing down the session schema. Keep it to a short list of fields you own, with a version number and a cap on history. Then decide what each counter protects against, and what the bot should do when the store is not there.
