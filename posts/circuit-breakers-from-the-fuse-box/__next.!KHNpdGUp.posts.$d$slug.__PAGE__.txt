3a:T606f,<p>A kitchen has one electrical circuit for the sockets on the counter. Someone switches on the kettle, the microwave and a heater at the same time. The wire in the wall now carries more current than it was made for, and it starts to get hot. A few seconds later, the breaker in the fuse box trips and the kitchen goes dark.</p>
<p>Nothing is wrong with the kettle. The breaker didn’t trip to protect it. It tripped to protect the wire in the wall, which would otherwise overheat behind the plaster where nobody can see it.</p>
<p>I studied electrical engineering before I moved to software. When I later worked on an experimentation service in Go, a <strong>circuit breaker</strong> in code was one of the patterns that felt familiar right away. It is a small piece of state in front of a call to another service. When that service keeps failing, the breaker stops calling it for a while and uses a fallback instead. This post explains why a busy service needs one, using the electrical version, and then walks through the code we used.</p>
<h2>What goes wrong without one</h2>
<p>The service answered one question per request: which variant of an experiment should this user see? It ran at around 5,000 requests per second on an average day, with a P95 latency under 100 ms. Each pod kept the experiment configuration in memory, with Redis shared between pods and the main config store behind it [8]. The breaker sat in front of the reads from that shared config layer.</p>
<p>Now picture the config layer having a bad minute. It doesn’t return errors. It just gets slow.</p>
<p>This is the dangerous case, and <strong>Little’s law</strong> shows why. The number of requests in flight equals the arrival rate times the time each one takes:</p>
<pre><code>in flight = arrival rate × time per request
</code></pre>
<p>If a read normally takes 5 ms, then 5,000 requests per second keep about 25 reads in flight. If the same read now waits for a 1-second timeout, the same traffic keeps 5,000 reads in flight. The 5 ms and the 1-second timeout are only for illustration, not measurements. But the ratio is the point: the traffic didn’t change, the dependency only got slower, and the service is now holding 200 times more work.</p>

<p>Each request in flight holds a goroutine, some memory and often a connection from a pool. When the pool runs out, requests that don’t even need the slow dependency start to wait for a connection. Latency rises for everyone. Upstream services that call this one now wait too, and the slowness spreads. This is a <strong>cascading failure</strong>, and it is the reason Michael Nygard named the circuit breaker a stability pattern in <em>Release It!</em> [1].</p>
<p>A timeout alone doesn’t solve it. It limits how long one request waits, but every request still waits that long. The breaker is what stops paying that cost again and again.</p>
<h2>The breaker protects the wire</h2>
<p>Back to the kitchen. A breaker protects the circuit, not the device plugged into it [3]. The software version has the same split. It protects the caller: its goroutines, its connection pool and its latency budget. It also gives the struggling dependency room to recover, because the caller stops adding load to it.</p>
<p>That changes how you think about the fallback. While the breaker is open, the caller still has to answer the user. For us, the answer was the last configuration that worked. The previous post on this service describes the same rule: if the config store has a bad minute, assignment keeps working with the last known config [8]. For experiment assignment, a few minutes of old config is a fair price. A paused experiment may keep running a little longer, but no user gets an error.</p>
<p>Not every service can do that. A payment service can’t approve a payment from a cache. So the first question for any breaker is not the threshold. It is: what do we answer while it’s open?</p>
<h2>Two ways to trip</h2>
<p>A household breaker usually has two trip mechanisms in one box [3]:</p>
<ul>
<li>A <strong>bimetallic strip</strong> handles overload. Current heats the strip and it bends slowly. A small overload trips the breaker after a delay. A short surge, such as a motor starting up, passes without a trip.</li>
<li>An <strong>electromagnet</strong> handles a short circuit. A very large current pulls it at once, with no delay.</li>
</ul>
<p>The software breaker in hystrix-go has the same two kinds of protection, though the library doesn’t describe them this way.</p>
<p>The slow one is the error rate over a rolling window. hystrix-go keeps one-second buckets for the last 10 seconds [5]. It opens the circuit only when the window has at least 20 requests and at least 50% of them are errors [4]. One bad second doesn’t trip it, the same way a motor’s start-up surge doesn’t trip the bimetallic strip.</p>
<p>The fast ones work per call. A call that takes longer than the timeout fails at once. A call that arrives when too many calls are already running is rejected at once, without waiting. That limit is a <strong>bulkhead</strong>: it caps how much of the service one dependency can hold.</p>
<h2>The recloser is the half-open state</h2>
<p>A breaker in a house stays off until somebody walks to the fuse box. Power lines outdoors have something smarter: a <strong>recloser</strong>. On overhead lines, most faults are short. Lightning or a branch touching a wire causes a fault that is gone a second later. Of all faults on overhead distribution lines, 80 to 87% are transient like this [2]. So a recloser opens, waits a moment, and closes again by itself. If the fault is still there, it opens again. After a few tries, it stays open and waits for a crew. The standards allow at most four tries [2].</p>
<p>This is exactly the <strong>half-open</strong> state of a software breaker. After a cooldown, let a test request through. If it succeeds, close the circuit. If it fails, stay open and wait again.</p>

<p>The difference at the end is worth a thought. A recloser locks out because a fault that survives several reclosures is probably permanent, and closing again into a permanent fault does damage. hystrix-go never locks out. It sends one probe every sleep window for as long as the dependency is down. For a read from a config store, one probe every 5 seconds is harmless. For something expensive, a limit on retries or an alert after many failed probes would be the recloser’s lesson.</p>
<h2>Selectivity: one breaker per circuit</h2>
<p>A building doesn’t have one breaker for everything. Each circuit has its own, and the main breaker sits above them. They are chosen so that a fault in the kitchen trips the kitchen breaker and leaves the rest of the building on. Electrical engineers call this <strong>selectivity</strong>.</p>
<p>In hystrix-go, every breaker has a name, the <em>command</em>. Use one command per dependency, and sometimes per kind of call. If one breaker wraps both Redis and the main store, a problem in one cuts traffic to both. The Azure pattern page warns about the same thing: one breaker for several independent resources blocks the healthy ones too [7].</p>
<h2>The code</h2>
<p>Here is the shape of what we ran. This is a sketch with simpler names, not the original code. The numbers are the library defaults, not necessarily the values we ran with.</p>
<pre><code class="hljs language-go"><span class="hljs-keyword">const</span> cmdConfigRead = <span class="hljs-string">"config_read"</span>

<span class="hljs-function"><span class="hljs-keyword">func</span> <span class="hljs-title">init</span><span class="hljs-params">()</span></span> {
    hystrix.ConfigureCommand(cmdConfigRead, hystrix.CommandConfig{
        Timeout:                <span class="hljs-number">1000</span>, <span class="hljs-comment">// ms per call</span>
        MaxConcurrentRequests:  <span class="hljs-number">10</span>,   <span class="hljs-comment">// calls running at once</span>
        RequestVolumeThreshold: <span class="hljs-number">20</span>,   <span class="hljs-comment">// calls in the window before it may trip</span>
        ErrorPercentThreshold:  <span class="hljs-number">50</span>,   <span class="hljs-comment">// % errors that trips it</span>
        SleepWindow:            <span class="hljs-number">5000</span>, <span class="hljs-comment">// ms open before one probe</span>
    })
}
</code></pre>
<p>Each field maps to one part of the electrical picture:</p>
<ul>
<li><code>Timeout</code> and <code>MaxConcurrentRequests</code> are the fast protection. A slow call fails after the timeout. A call over the concurrency limit is rejected at once with <code>hystrix: max concurrency</code> [6].</li>
<li><code>RequestVolumeThreshold</code> and <code>ErrorPercentThreshold</code> are the slow one. Together they say: “trip only if there is enough traffic to judge, and enough of it is failing”.</li>
<li><code>SleepWindow</code> is the recloser’s wait before it tries again.</li>
</ul>
<p>The call itself:</p>
<pre><code class="hljs language-go"><span class="hljs-function"><span class="hljs-keyword">func</span> <span class="hljs-params">(s *Service)</span></span> experimentConfig(ctx context.Context, id <span class="hljs-type">string</span>) (Config, <span class="hljs-type">error</span>) {
    <span class="hljs-comment">// The run callback can outlive DoC's timeout. It owns its result and</span>
    <span class="hljs-comment">// sends it to a buffered channel, never to a shared return variable.</span>
    result := <span class="hljs-built_in">make</span>(<span class="hljs-keyword">chan</span> Config, <span class="hljs-number">1</span>)
    err := hystrix.DoC(ctx, cmdConfigRead,
        <span class="hljs-function"><span class="hljs-keyword">func</span><span class="hljs-params">(ctx context.Context)</span></span> <span class="hljs-type">error</span> {
            c, err := s.store.Get(ctx, id)
            <span class="hljs-keyword">if</span> err != <span class="hljs-literal">nil</span> {
                <span class="hljs-keyword">return</span> err
            }
            s.lastGood.Store(id, c)
            result &#x3C;- c
            <span class="hljs-keyword">return</span> <span class="hljs-literal">nil</span>
        },
        <span class="hljs-literal">nil</span>, <span class="hljs-comment">// handle the fallback below, on the calling goroutine</span>
    )
    <span class="hljs-keyword">if</span> err == <span class="hljs-literal">nil</span> {
        <span class="hljs-keyword">return</span> &#x3C;-result, <span class="hljs-literal">nil</span>
    }
    <span class="hljs-keyword">if</span> c, ok := s.lastGood.Load(id); ok {
        <span class="hljs-keyword">return</span> c.(Config), <span class="hljs-literal">nil</span>
    }
    <span class="hljs-keyword">return</span> Config{}, err <span class="hljs-comment">// nothing cached yet: surface the error</span>
}
</code></pre>
<p>The callback is the normal path. It reads the config and, on success, saves a copy as the last good value. The caller handles the fallback after <code>DoC</code> returns an error: a failed read, a timeout, a full concurrency limit or an open circuit [6]. The error keeps the reason, so you can log <code>hystrix: circuit open</code> differently from a real store error.</p>
<p>The result channel has room for one value. On a timeout, the original callback can still finish and send without blocking, but it cannot overwrite the value returned by the fallback. Do not let the callback and fallback assign to the same captured variable: they can run concurrently. The store and the last-good cache must also be safe for concurrent access.</p>
<p>Two details in this code are easy to get wrong.</p>
<p>The fallback must be cheap and must not call the same dependency. Reading from memory is fine. Calling the store again “just once” from the fallback defeats the breaker.</p>
<p>The fallback needs a value to return. Right after a pod starts, there is no last good config yet. Then the only correct answer is the error. In practice the pod should load the config before it reports ready, so this case is rare.</p>

<h2>Things to watch</h2>
<ul>
<li><strong>Low traffic never trips.</strong> With a volume threshold of 20 in a 10-second window, a command that gets one call per second can fail completely and stay closed. Set the threshold from the real traffic of each command, not from the defaults.</li>
<li><strong>A timeout doesn’t stop the work.</strong> When hystrix-go’s timeout fires, it calls the fallback and frees the concurrency slot. The run function keeps running in its goroutine, and its result is thrown away [6]. Pass a context with a deadline to the store client too, so the slow call really ends.</li>
<li><strong>Short-circuits count as errors.</strong> While the circuit is open, the rejected calls are counted as errors in the window [5]. This doesn’t keep it open, because a successful probe closes it and resets the window. But it makes the error rate on a dashboard look worse than the dependency really is.</li>
<li><strong>Every pod has its own breaker.</strong> The state lives in memory. With 20 pods, each one has to see its own 20 requests before it trips. That’s usually fine and much cheaper than sharing state.</li>
<li><strong>hystrix-go is old.</strong> Netflix’s Java Hystrix has been in maintenance mode for years and recommends resilience4j instead [9]. For new Go code, sony/gobreaker is a maintained option with the same three states and a configurable trip rule [10]. If you run a service mesh, Envoy’s outlier detection gives similar protection without code, by removing failing hosts from the pool for a while [11].</li>
</ul>
<h2>What carries over</h2>
<p>I used the same pattern again recently, in front of LLM calls instead of a config store. The details changed: there, the fallback is a second model deployment instead of a cache, and there is no half-open state. I wrote that up in <a href="/posts/llm-quota-fallback-circuit-breaker/">a separate post</a>.</p>
<p>The questions to answer stay the same as for the breaker in a fuse box. What are you protecting? What happens to the user while it’s open? Can it tell a short surge from a real overload? And who closes it again, a person or a recloser? Once you can answer those four, the thresholds are the easy part.</p>
