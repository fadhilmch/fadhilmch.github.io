1e:T8ed9,<p>For a long time, every service we ran on Google Cloud authenticated the same way. Someone created a service account, downloaded a JSON key for it, and put that key somewhere the service could read it: a Kubernetes Secret, a CI variable, occasionally a file on someone’s laptop “just for testing”. The code pointed <code>GOOGLE_APPLICATION_CREDENTIALS</code> at the file and everything worked.</p>
<p>This year we started moving away from that, towards what Azure calls managed identity and Google calls, less memorably, attached service accounts and Workload Identity. I had used both without understanding them. The client library found credentials, the call succeeded, and I moved on. Once I had to explain to the team why we were doing the migration, and debug the first few services that broke during it, I had to learn what actually happens when code “just gets” a token.</p>
<p>This post is that explanation: what problem managed identity solves, how each of Google Cloud’s three versions of it works underneath, how they line up with Azure’s, and what caught us out.</p>
<h2>A note on the name</h2>
<p>“Managed identity” is Azure’s product name. Google Cloud doesn’t have a product called that. It has the same idea split across three features, one for each place your code can run:</p>
<ol>
<li><strong>Service accounts attached to resources</strong>, for code running on Google Cloud’s own compute: a Compute Engine VM, a Cloud Run service, a Cloud Function.</li>
<li><strong>Workload Identity</strong>, for pods on GKE. It gives each Kubernetes service account its own Google identity, instead of every pod sharing the node’s.</li>
<li><strong>Workload Identity Federation</strong>, for code running outside Google Cloud: GitHub Actions, an AWS workload, an on-premises job. It lets them act as a service account without a key.</li>
</ol>
<p>The common thread is that the code never holds a long-lived secret. The platform it runs on vouches for it instead. I’ll use “managed identity” for the idea, cover each of the three in turn, and then map them to their Azure equivalents, since Azure is where most people first meet the term.</p>
<h2>What’s wrong with a key file</h2>
<p>A service account key is a private key. Anyone who has the file can sign a request as that service account, from anywhere on the internet, until someone deletes the key. By default it doesn’t expire.</p>
<p>That on its own is fine. The problem is everything that happens to the file after it’s created:</p>
<ul>
<li><strong>It gets copied.</strong> Into a Secret, then into a second cluster’s Secret, into a CI variable, into a colleague’s Downloads folder. Each copy is one more place it can leak from, and nobody has a list of them.</li>
<li><strong>It outlives its purpose.</strong> The service that needed it is retired, but the key still works. A service account can hold up to ten keys, and it’s common to find several with no idea which are in use.</li>
<li><strong>Rotation is manual work.</strong> Rotating means creating a new key, updating every copy, restarting what reads it, and only then deleting the old one. In practice it happens after an incident, not on a schedule.</li>
<li><strong>It doesn’t say where it’s used.</strong> Audit logs tell you the service account made a call. They can’t tell you whether the call came from your pod or from someone who found the key in an old commit.</li>
</ul>
<p>Most of these problems come from handing the key around. None of them are about cryptography. A key is a secret you have to hand out, and every hand-off is a chance to lose it. Rotating more often shrinks the window but keeps the hand-offs.</p>

<p>Managed identity removes the hand-off. The service account is attached to where the code runs, and the code asks the platform for a token each time it needs one. There is nothing to copy, because there is no file.</p>
<h2>The idea underneath: tokens, not keys</h2>
<p>It helps to separate two things that the key file blurs together.</p>
<p>A <strong>credential</strong> proves who you are. The JSON key is one; so is your password when you run <code>gcloud auth login</code>.</p>
<p>An <strong>access token</strong> is what Google APIs actually accept. It’s a string beginning with <code>ya29.</code> that goes in an <code>Authorization: Bearer</code> header, and it expires after an hour.</p>
<p>Even with a key file, your code never sends the key to Cloud Storage. The client library uses the key to sign a short JSON Web Token, sends that to Google’s OAuth endpoint, and gets an access token back. The access token is what travels with each request.</p>
<p>So the question managed identity answers is narrow: how does code get an access token without holding a credential of its own? The answer is that something trusted, sitting next to the code, asks on its behalf. On Google Cloud that something is the metadata server.</p>
<h2>1. Attached service accounts: VMs, Cloud Run and Functions</h2>
<p>Every Compute Engine VM can reach a metadata server at <code>169.254.169.254</code>, also known as <code>metadata.google.internal</code>. It isn’t a machine on your network. Requests to that address are handled by the host your VM runs on, outside the VM itself. Cloud Run and Cloud Functions provide the same server to your container.</p>
<p>When you create a VM or deploy a Cloud Run service, you choose a service account to attach. The platform remembers that pairing. Later, when code inside asks the metadata server for a token, the host already knows which VM or service is asking, and so which service account it’s allowed to have.</p>
<p>You can do the whole thing by hand with <code>curl</code>:</p>
<pre><code class="hljs language-bash">curl -s -H <span class="hljs-string">"Metadata-Flavor: Google"</span> \
  <span class="hljs-string">"http://metadata.google.internal/computeMetadata/v1/instance/service-accounts/default/token"</span>
</code></pre>
<pre><code class="hljs language-json"><span class="hljs-punctuation">{</span><span class="hljs-attr">"access_token"</span><span class="hljs-punctuation">:</span> <span class="hljs-string">"ya29.c.b0Aa..."</span><span class="hljs-punctuation">,</span> <span class="hljs-attr">"expires_in"</span><span class="hljs-punctuation">:</span> <span class="hljs-number">3599</span><span class="hljs-punctuation">,</span> <span class="hljs-attr">"token_type"</span><span class="hljs-punctuation">:</span> <span class="hljs-string">"Bearer"</span><span class="hljs-punctuation">}</span>
</code></pre>
<p>That’s all a client library does when there’s no key file. The <code>Metadata-Flavor: Google</code> header is required, and requests carrying an <code>X-Forwarded-For</code> header are refused. Both rules make it harder to trick a web application into fetching a token for an attacker, because a browser or a naive proxy won’t add the first header and will add the second.</p>

<p>The same server can also hand out an ID token, which is a signed JWT with an audience of your choosing. Access tokens are for calling Google APIs; ID tokens are for calling your own services behind Cloud Run authentication or Identity-Aware Proxy, where the receiver wants to check who is calling:</p>
<pre><code class="hljs language-bash">curl -s -H <span class="hljs-string">"Metadata-Flavor: Google"</span> \
  <span class="hljs-string">"http://metadata.google.internal/computeMetadata/v1/instance/service-accounts/default/identity?audience=https://orders-abc123-ew.a.run.app"</span>
</code></pre>
<h3>How the client library decides</h3>
<p>The piece of code that makes the switch painless is Application Default Credentials, or ADC. Every Google client library looks for credentials in the same order:</p>
<ol>
<li>The file named by <code>GOOGLE_APPLICATION_CREDENTIALS</code>, if the variable is set.</li>
<li>Your own user credentials, if you’ve run <code>gcloud auth application-default login</code> on this machine.</li>
<li>The metadata server, if there is one.</li>
</ol>
<p>That order is why the same code runs on my laptop and in production without a branch:</p>
<pre><code class="hljs language-python"><span class="hljs-keyword">import</span> google.auth
<span class="hljs-keyword">from</span> google.cloud <span class="hljs-keyword">import</span> storage

credentials, project = google.auth.default()   <span class="hljs-comment"># no path, no key</span>
client = storage.Client(credentials=credentials, project=project)
<span class="hljs-built_in">print</span>([b.name <span class="hljs-keyword">for</span> b <span class="hljs-keyword">in</span> client.list_buckets()])
</code></pre>
<p>Locally it picks up my login. On Cloud Run it reaches step 3 and asks the metadata server. It also explains the most common surprise during migration: if a leftover <code>GOOGLE_APPLICATION_CREDENTIALS</code> is still set in a deployment, step 1 wins, and the service keeps quietly using the old key. Deleting the key is how you find out.</p>
<h2>2. Workload Identity: pods on GKE</h2>
<p>GKE is where most of our services run, and where the story gets more interesting.</p>
<p>A pod runs on a node, and a node is a VM. So without anything else, a pod that asks the metadata server gets the <strong>node’s</strong> service account. Every pod on the node shares it. On many clusters, including some of ours, that was the Compute Engine default service account, which by default is granted the Editor role on the whole project. Access scopes on the node narrowed what that token could do, but the principle was wrong: any container on the node, including a compromised one, could act as the node.</p>
<p>Workload Identity fixes this by giving each Kubernetes service account (KSA) its own mapping to a Google service account (GSA). Setting it up is four steps:</p>
<pre><code class="hljs language-bash"><span class="hljs-comment"># 1. Turn it on for the cluster; this creates the identity pool PROJECT_ID.svc.id.goog</span>
gcloud container clusters update my-cluster --region europe-west1 \
  --workload-pool=my-project.svc.id.goog

<span class="hljs-comment"># 2. Make the node pool serve pods through the GKE metadata server</span>
gcloud container node-pools update default-pool --cluster my-cluster \
  --region europe-west1 --workload-metadata=GKE_METADATA

<span class="hljs-comment"># 3. Allow the KSA orders/orders-api to act as the GSA</span>
gcloud iam service-accounts add-iam-policy-binding \
  orders-api@my-project.iam.gserviceaccount.com \
  --role roles/iam.workloadIdentityUser \
  --member <span class="hljs-string">"serviceAccount:my-project.svc.id.goog[orders/orders-api]"</span>

<span class="hljs-comment"># 4. Tell GKE which GSA the KSA maps to</span>
kubectl annotate serviceaccount orders-api --namespace orders \
  iam.gke.io/gcp-service-account=orders-api@my-project.iam.gserviceaccount.com
</code></pre>
<p>The pod then only needs <code>serviceAccountName: orders-api</code> in its spec. No Secret, no volume, no environment variable. Autopilot clusters have Workload Identity on from the start, so only steps 3 and 4 apply there.</p>
<p>What happens when the pod asks for a token took me a while to piece together. With <code>GKE_METADATA</code> set, GKE runs its own metadata server as a DaemonSet, <code>gke-metadata-server</code>, on every node, and traffic from pods to <code>169.254.169.254</code> is redirected to it instead of the real one. The pod can’t tell the difference. Behind that same address, a lot more is going on:</p>
<figure class="fig">

<figcaption>From the pod's side it's one HTTP call. On the node, it's an identity lookup and two token exchanges, cached so they don't happen on every request.</figcaption>

<ol>
<li>The pod sends the usual metadata request. The GKE metadata server receives it.</li>
<li>It works out which pod is asking from the source IP, and from the pod, which namespace and KSA it runs as.</li>
<li>It obtains a token for that KSA from the cluster, signed by the cluster’s own issuer, and trades it at Google’s Security Token Service for a federated token. STS trusts the cluster because the cluster is registered in the project’s identity pool, <code>my-project.svc.id.goog</code>. At this point Google knows the caller as <code>my-project.svc.id.goog[orders/orders-api]</code>.</li>
<li>It uses the federated token to call the IAM Credentials API and ask for an access token for <code>orders-api@my-project.iam.gserviceaccount.com</code>. This is where the <code>workloadIdentityUser</code> binding from step 3 of the setup is checked. Without it, the call is refused.</li>
<li>The GSA’s access token goes back to the pod, and is cached until shortly before it expires.</li>
</ol>
<p>Two things fell out of seeing it this way. First, the KSA-to-GSA link is enforced by IAM, not by the annotation. The annotation only tells the metadata server which GSA to ask for; the binding decides whether it’s allowed. That’s why one without the other fails. Second, the GKE metadata server only exposes the endpoints a workload needs. A pod can no longer read the node’s token or the node’s instance attributes, which quietly closes the “act as the node” hole above.</p>
<h2>3. Workload Identity Federation: outside Google Cloud</h2>
<p>The last place we had keys was CI. Our GitHub Actions workflows deployed to Google Cloud with a key stored as a repository secret.</p>
<p>Workload Identity Federation is the same trick as step 3 above, applied to an outside issuer. GitHub can mint an OIDC token for each workflow run, signed by GitHub and saying which repository, branch and workflow it came from. You register GitHub as a provider in a workload identity pool, and STS will exchange that token for a Google one, subject to conditions you write on those claims:</p>
<pre><code class="hljs language-yaml"><span class="hljs-attr">permissions:</span>
  <span class="hljs-attr">id-token:</span> <span class="hljs-string">write</span>      <span class="hljs-comment"># lets the job request an OIDC token from GitHub</span>
  <span class="hljs-attr">contents:</span> <span class="hljs-string">read</span>

<span class="hljs-attr">steps:</span>
  <span class="hljs-bullet">-</span> <span class="hljs-attr">uses:</span> <span class="hljs-string">google-github-actions/auth@v1</span>
    <span class="hljs-attr">with:</span>
      <span class="hljs-attr">workload_identity_provider:</span> <span class="hljs-string">projects/123456/locations/global/workloadIdentityPools/github/providers/github</span>
      <span class="hljs-attr">service_account:</span> <span class="hljs-string">deployer@my-project.iam.gserviceaccount.com</span>
  <span class="hljs-bullet">-</span> <span class="hljs-attr">run:</span> <span class="hljs-string">gcloud</span> <span class="hljs-string">run</span> <span class="hljs-string">deploy</span> <span class="hljs-string">orders</span> <span class="hljs-string">--image</span> <span class="hljs-string">europe-docker.pkg.dev/my-project/app/orders:${{</span> <span class="hljs-string">github.sha</span> <span class="hljs-string">}}</span>
</code></pre>
<p>The attribute condition on the provider matters as much as the setup. Without one, any repository on GitHub that knows your pool’s name could try the exchange. We restrict it to our organisation, and bind the deployer service account only to the specific repositories that deploy.</p>
<h2>The same idea on Azure</h2>
<p>Azure is where the name comes from, and it has a counterpart for each of the three pieces above. The underlying mechanism is the same: a local endpoint that only your workload can reach hands out short-lived tokens, and in the federated cases a token from one issuer is traded for another.</p>
<p>| Where the code runs | Google Cloud | Azure |
| — | — | — |
| The cloud’s own compute | Service account attached to a VM, Cloud Run service or function | Managed identity on a VM, App Service, Functions or Container Apps |
| Kubernetes pods | GKE Workload Identity | Azure AD Workload Identity on AKS |
| Outside the cloud | Workload Identity Federation | Workload identity federation (federated identity credentials) |
| How client libraries find it | Application Default Credentials | <code>DefaultAzureCredential</code> |
| The local endpoint | <code>169.254.169.254</code>, header <code>Metadata-Flavor: Google</code> | <code>169.254.169.254</code> (IMDS), header <code>Metadata: true</code> |</p>
<h3>Managed identities: system-assigned and user-assigned</h3>
<p>Azure’s managed identity comes in two kinds, and the difference is worth knowing even if you only use Google Cloud, because it shows a choice Google made for you.</p>
<ul>
<li>A <strong>system-assigned</strong> identity is created with a resource and deleted with it. Turn it on for a VM, and Azure AD gets a service principal whose whole life is tied to that VM. One resource, one identity.</li>
<li>A <strong>user-assigned</strong> identity is a standalone resource. You create it first, grant it roles, and attach it to one or many VMs, apps or functions. It survives when they’re deleted.</li>
</ul>
<p>A Google service account always behaves like the user-assigned kind: it exists on its own, you grant it roles, and you attach it to whatever should run as it. There’s no identity that appears and disappears with a VM. In practice we use it the way Azure people use user-assigned identities, one per service, shared by all instances of that service.</p>
<p>Behind the scenes, an Azure VM asks its Instance Metadata Service for a token, and the request looks very much like the Google one:</p>
<pre><code class="hljs language-bash">curl -s -H <span class="hljs-string">"Metadata: true"</span> \
  <span class="hljs-string">"http://169.254.169.254/metadata/identity/oauth2/token?api-version=2018-02-01&#x26;resource=https://storage.azure.com/"</span>
</code></pre>
<p>The one visible difference is <code>resource</code>. Google hands out one access token that works for any Google API the service account has roles on, narrowed by IAM. Azure asks you to name the API you want a token for, and the token’s audience is that API. App Service and Functions use the same model, but reach it through a local endpoint whose address and secret header are given to your app as the <code>IDENTITY_ENDPOINT</code> and <code>IDENTITY_HEADER</code> environment variables.</p>
<h3>Pods on AKS</h3>
<p>AKS went through the same problem GKE did. The first answer, pod-managed identity (the <code>aad-pod-identity</code> project), intercepted metadata calls from pods on each node, much like the GKE metadata server does. It was deprecated last year, in favour of <strong>Azure AD Workload Identity</strong>, which is in preview on AKS as I write this.</p>
<p>The new approach doesn’t intercept anything. The cluster publishes an OIDC issuer, Kubernetes projects a signed service account token into the pod, and the pod exchanges that token with Azure AD directly for a token as a user-assigned identity. You link the two by adding a federated identity credential to the identity, naming the cluster’s issuer and <code>system:serviceaccount:orders:orders-api</code> as the subject, and annotating the service account with the identity’s client ID. It’s step 3 of the GKE flow, done by the pod’s own client library instead of by a node daemon.</p>
<h3>Outside Azure</h3>
<p>For GitHub Actions and similar, Azure uses the same federated identity credentials. You add one to a user-assigned identity or an app registration, saying “trust tokens from <code>https://token.actions.githubusercontent.com</code> whose subject is <code>repo:my-org/orders:ref:refs/heads/main</code>”, and the <code>azure/login</code> action with OIDC exchanges the workflow’s token for an Azure one. It’s the same exchange as Google’s Workload Identity Federation, with the trust rule written as an exact subject rather than a condition expression.</p>
<h3>Finding credentials</h3>
<p><code>DefaultAzureCredential</code> plays the role of ADC. It tries a chain in order: credentials from environment variables, then managed identity, then the tools a developer is signed into, such as the Azure CLI. The same trap applies. A leftover client secret in the environment wins over the managed identity, and the service keeps using a secret you thought you’d retired.</p>
<p>Seeing the two clouds side by side made the idea clearer to me than either did alone. The names differ and the details differ, but both have settled on the same design: no secrets inside the workload, a trusted local endpoint for code on the cloud’s own compute, and token exchange for everything else.</p>
<h2>Why it matters</h2>
<p>Put together, the changes add up to more than they first seem:</p>
<ul>
<li><strong>Nothing to steal at rest.</strong> No file in a Secret, a repository, a backup or a laptop. The token a pod holds dies within the hour.</li>
<li><strong>Identity follows the workload.</strong> The permission is tied to “this namespace and service account in this cluster” or “this Cloud Run service”, not to whoever has the file.</li>
<li><strong>One identity per workload becomes cheap.</strong> When each identity costs a key to manage, teams share one broad service account. When it costs two commands, giving each service its own narrow one is the easy path.</li>
<li><strong>Rotation stops being a project.</strong> Google rotates the keys that sign these tokens. There’s nothing for us to schedule.</li>
<li><strong>Audit logs mean something.</strong> A call made as <code>orders-api@</code> came from the orders workload, because nothing else can get that token. With federation, the logs also carry the external identity that was exchanged.</li>
</ul>
<p>It doesn’t make IAM design go away. A workload identity with Editor on the project is still a workload with Editor on the project. What changes is that least privilege becomes practical, because the unit of identity finally matches the unit of deployment.</p>
<h2>What caught us out</h2>
<p>A few things we hit during the first services, in the order we hit them:</p>
<ul>
<li><strong>The leftover environment variable.</strong> Covered above: <code>GOOGLE_APPLICATION_CREDENTIALS</code> still set in a Helm values file, so ADC kept using the key. Grep for it before deleting keys.</li>
<li><strong>The first request at startup.</strong> On GKE the metadata server can take a moment to be ready for a freshly scheduled pod. A service that fetched a token as the very first thing in <code>main</code> occasionally failed on startup. A retry with backoff on the first call fixed it.</li>
<li><strong>IAM is eventually consistent.</strong> A new <code>workloadIdentityUser</code> binding or role grant can take a few minutes to take effect. Deploying immediately after <code>terraform apply</code> gave us confusing 403s that fixed themselves.</li>
<li><strong>Identity sameness.</strong> The identity pool is per project, not per cluster. <code>orders/orders-api</code> in our staging cluster and <code>orders/orders-api</code> in another cluster in the same project are the same principal to IAM. Keep environments in separate projects, or at least separate namespaces.</li>
<li><strong><code>hostNetwork</code> pods can’t use it.</strong> Their traffic doesn’t go through the redirect, so they fall back to the node’s identity. We had one such workload and gave it a dedicated node pool.</li>
<li><strong>Old access scopes on VMs.</strong> On Compute Engine, a VM’s access scopes cap what its token can do even when IAM allows more. We set the scope to <code>cloud-platform</code> and let IAM do the restricting, as Google recommends.</li>
</ul>
<h2>How we’re rolling it out</h2>
<p>We’re doing this service by service, not as one big switch:</p>
<ol>
<li><strong>Inventory.</strong> List every user-managed key with <code>gcloud iam service-accounts keys list</code>, and use Activity Analyzer to see when each one last authenticated. Keys unused for months are the easy first deletions.</li>
<li><strong>One GSA per workload.</strong> Create a dedicated service account for each service, with only the roles it needs, and map its KSA or attach it to its Cloud Run service.</li>
<li><strong>Remove the key path.</strong> Drop <code>GOOGLE_APPLICATION_CREDENTIALS</code> and the Secret, deploy, and watch for errors.</li>
<li><strong>Disable, then delete.</strong> Disable the old key first. If nothing breaks for a week, delete it.</li>
<li><strong>Close the door.</strong> Once a project has no keys left, enforce the <code>iam.disableServiceAccountKeyCreation</code> organisation policy on it, so new ones can’t appear.</li>
</ol>
<p>The last step is the one that makes the change stick. Without it, the next person under deadline pressure downloads a key “just for now”, and the whole cycle starts again.</p>
<h2>Summary</h2>
<ul>
<li>An access token and a credential are different things. Managed identity keeps the token and removes the credential.</li>
<li>The metadata server is the platform vouching for you, because it already knows where your code runs.</li>
<li>ADC checks the environment variable, then your login, then the metadata server, which is why one code path works everywhere.</li>
<li>On GKE, the pod still talks to <code>169.254.169.254</code>; the GKE metadata server exchanges a Kubernetes identity for a Google one behind it.</li>
<li>The annotation says which service account; the IAM binding says whether you may.</li>
<li>Federation is the same exchange, with GitHub or another cloud as the issuer.</li>
<li>Azure has the same three pieces under different names: managed identities, AKS workload identity and federated identity credentials.</li>
</ul>
<p>Deleting key files is the visible part of this. Underneath, we’re removing the step where someone hands out a secret, along with everything that tends to go wrong after it.</p>
