Load-test estimator

Set users, response time and think time; read the requests per second the configuration produces, with the assumptions stated. Have a target rate instead? The section below runs the same law backwards.

users

Each user runs its tasks one at a time, then waits before the next.

ms

Best from a short trial run at low load - this number decides the whole estimate.

s

The pause between one task and the next. People read before they click again.

100

estimated requests per second at full load

100 users ÷ (0,5 s response + 0,5 s think) ≈ 100 req/s

  • One request per task; each user works through its tasks one at a time.
  • Steady state once all users have joined; ramp-up only decides how fast you get there.
  • Holds only while the response time holds. Under load it usually rises and the rate falls - finding that point is the test.
  • An estimate of this configuration, not your server's capacity.
Starting from a target rate instead?

200

users needed for 200 req/s at the same response and think time

req/s

The steady-state rate the test should produce.

  • The same law run backwards: users = target rate × (response time + think time).
  • Same assumptions, same limits - it is an estimate, not a measurement.
When one process is not enough
  • One Locust process can use only one CPU core, so run one worker per core. Locust splits the users across workers itself.
  • Locust logs a CPU warning when a generator nears its limit; that warning, not a number here, is the signal to add workers.
  • If response times degrade while no generator warns, the limit is somewhere else - the service, the network or the test setup. Finding out which is the point of the test.
